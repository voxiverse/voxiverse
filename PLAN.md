# Voxiverse rewrite plan

A from-scratch rewrite on the orphan `rewrite` branch. The old prototype (`main`) stays
readable next to it as a reference; nothing is copied over, ideas are re-typed on purpose.

## Why

The audit of the prototype found that its problems are architectural, not local:

- One ~130-field `State` mixing process, session, gameplay, per-frame and debug lifetimes;
  leaving a world reset only half of it.
- "Subsystems" that reach into each other (a 14-pointer `Sim_Ctx`, `rawptr` console
  callbacks, a UI library importing the renderer, the world package driving the network).
- A server that is called authoritative but accepts client positions, damage and spawns.
- Mutable objects stored by value in maps, so edits land on copies and are lost.
- No memory strategy: the server never frees its temp allocator or unloads chunks.
- Broken frame model: double-counted timestep, CPU writing GPU buffers still in use,
  validation-layer messages silently discarded, whole-world re-upload on any edit.

The rules below exist to make those mistakes structurally hard to repeat.

## Decisions

## Ground rules

1. **Lifetimes are structure.** Three tiers, each owning its memory and torn down in one place:
   - `App` (process): settings, platform, GPU device, UI, audio device.
   - `Session` (one world, client or server side): arena-backed; leaving a world frees the arena.
   - `Frame`/`Tick`: scratch arena reset every frame/tick, on every thread that uses one.

   Lower tiers may point into higher ones, never the reverse.
2. **Handles, not pointers or map values, for game objects.** Generational `u32` handles into
   pools (entities, chunks, GPU resources, audio voices). Maps only map keys to handles.
   UUIDs exist only in save files.
3. **Allocating procedures take `allocator := context.allocator, loc := #caller_location`.**
   Enforced in review; no implicit `context.allocator` in long-lived data.
4. **No mutable globals.** Constant tables only; no lazy-initialised globals (they race once
   the server runs on its own thread).
5. **Packages depend downward only** (see layout). A UI or renderer package never imports game
   code; game code never imports platform or GPU code.
6. **Untrusted input is validated at the edge.** Every decoded enum is range-checked, every
   length capped; handlers receive validated types only.
7. **Nothing fails silently.** No silent truncation or dropped work; Vulkan validation on in
   debug and routed to the real logger; asserts on invariants.
8. **One source of truth per fact.** Physics, block rules and RNG live once in shared code;
   the server decides, the client predicts and reconciles.

## Layout

```
base/       handles + pools, arenas, math, rng, log            (depends on nothing)
platform/   window, events, time, paths, dynlib (one file per OS: win32, x11, cocoa)
gpu/        Vulkan: device, swapchain, frames in flight, buffers, images, bindless
            descriptors, pipelines
render/     passes: world (chunks), sky, entities, debug lines, UI; each keeps its own
            per-frame buffers
ui/         immediate-mode UI -> vertices + texture ids (no GPU import)
audio/      device (miniaudio) + mixer + voice pool
game/       shared simulation: blocks, chunk storage, worldgen, lighting, physics,
            entities, protocol (+ codec)
server/     authoritative session: tick, message handlers, streaming, saves
client/     app, session, prediction, meshing jobs, screens, main
tools/      build driver, shader compiler step, asset generators
assets/     font + shader sources (generated output goes to build/, not git)
```

## Core designs

### Main loop
`App` owns platform, GPU, UI, audio. A `Session` exists only inside a world. Each frame:
poll events → map to actions → run fixed ticks (accumulator added once, capped at a few ticks
per frame) → build the UI → each pass records its draws from the session and the UI → render. Tick rate is one constant in
`game/` (30 Hz), announced by the server in the handshake.

### World data
- Chunks 16³, `u16` block ids (room past 256 blocks). In memory a chunk is one block (all
  air, all stone: most chunks) or a flat array from a region reserved for the session's
  maximum, so memory has a hard ceiling; palette + runs on the wire (and on disk). Light
  stored separately.
- One chunk pool plus a coordinate → handle map; explicit chunk states
  (generating, ready, meshed, …) and a dirty-chunk event queue.
- Generation, lighting and meshing run as jobs on worker threads, on immutable padded
  snapshots (18³ for meshing), never on live data.
- Lighting is a pure function in `game/`: a chunk's sky and block light, computed whole from
  its 3x3x3 neighbourhood and the column heights (light travels at most 15 blocks, so that is
  all it depends on), inside the mesh job. No stored light, so no removal pass and nothing to
  go stale: an edit re-meshes the chunks within 15 blocks. (Changed from incremental add and
  removal passes in M4: same results, far fewer ways to be wrong.) The server sends column
  heights (`Column`), since the client cannot see above what it has loaded.
- Interest is a cylinder around each player's chunk, sent nearest first; the client drops
  chunks one past it and the server frees them two past it (hysteresis). Both sides size
  their storage from it once, at join.

### Authority and netcode
- Client sends tick-stamped input commands; the server simulates every player with the shared
  physics and sends snapshots; the client predicts its own player and reconciles.
- Block edits are requests: predicted locally, confirmed or rolled back by the server. Each
  names the input it follows, and the server applies it right after that input, so reach is
  judged from the same position however late it arrives.
- Transport is an interface. First implementation: in-process queues, with the server on its
  own thread (singleplayer keeps a separate client replica on purpose, so authority stays
  honest). Later: UDP (own reliability layer on `core:net`, or ENet behind the interface).
- Protocol has a version handshake, validated decoding, and palette + RLE chunk encoding.

### Renderer
- Retained resources: chunk meshes sub-allocated in one device-local buffer, uploaded per
  chunk through per-frame staging (no whole-world rebuild); textures and meshes by handle.
  Positions relative to the camera's chunk; reverse-Z infinite projection. Greedy meshing
  later (it must respect AO).
- Per frame: a scene buffer (camera, sky, clouds; read by address in the shaders) and each
  pass's own per-frame-in-flight buffers (entity boxes and particles, debug lines, UI
  vertices).
- Swapchain recreation touches only the swapchain and size-dependent images.

### UI
- Immediate mode, one hashed id system with an id stack.
- Hover, keyboard focus and active are separate states; clicks fire on release over the same
  widget.
- Layers (base, popup, modal, tooltip) decide input priority and draw order.
- Per-command scissor clipping; a layout cursor (rows/columns) instead of hand-placed rects.
- Input is a generic event stream (keys, text, pointer), not game actions.
- Output is vertices + texture ids; the renderer draws them.

### Input
Platform events → action map (rebindable) → per-tick input command. Text input is a separate
event stream for UI and console.

### Console and variables
Not a global registry (Quake's cvars, Call of Duty's dvars): every tunable value is a field
of a typed struct with one owner, described once in a table (name, type, range, default,
help) that the console, the tuning panel and save files all use. Code reads plain fields.

| Kind | Examples | Owner | Saved | Changed by |
|---|---|---|---|---|
| Client settings | sensitivity, FOV, UI scale, view distance, volume | App | settings file | the user; never sent |
| Game rules (`game.Rules`) | gravity, speeds, jump, reach, flying | server session | world save | the server only; sent in Welcome and as tick-stamped changes so prediction uses them |
| Debug switches | chunk borders, net trace, simulated latency | the side they affect | no | console, dev builds |

Singleplayer changes rules by sending a command message to its own server, never by writing
server memory. A value becomes a variable only when someone tunes it; design decisions
(tick rate, chunk size, protocol limits) stay constants. Cheat/dev commands only in dev
builds.

### From Quake 3: kept and dropped
Kept: authoritative server, client prediction of its own movement from tick-numbered input
commands, one movement code path for both sides, a local server for singleplayer, fixed
server tick, interpolated (not predicted) remote entities, console + config scripts.
Dropped: global string cvars (see above); everything-on-unreliable-snapshots (chunks and
edits need a reliable ordered stream; entities get snapshots); client-reported frame times
in commands (speed hacks; we tie inputs to server ticks and cap them); sending every entity
to everyone (interest management); QVM; lag-compensated hits until there is combat.

### Assets
Generated by code at startup, deterministic on every machine: block textures (procedural,
palette-quantized), sounds (synthesized; `build sfx` writes them out to listen to), the font
atlas (JetBrains Mono, rasterized by our own `font/` as glyphs are needed). Shaders are the
one build-time asset (SPIR-V, hot reloaded in dev builds).

### Tooling
Setting up a fresh machine is: install odinup, then run `build`. Nothing else.

- The build driver is an Odin program (`tools/build`); `build.sh` / `build.bat` only hand off
  to it.
- **Shader compiler, zero setup:** on first use the driver downloads the pinned official
  glslang release for the host OS (Khronos GitHub release, Windows x64 / Linux x86_64 /
  macOS universal) with the `curl` and `tar` every supported OS ships, verifies its SHA-256
  against hashes committed in the repo, and unpacks it into `build/tools/`. Everyone compiles
  with the same version; bumping it is a one-line change plus hashes.
- Override for unusual hosts (e.g. Linux arm64): `GLSLANG=/path/to/glslangValidator`.
- Shaders recompile only when their source changes; compile errors point at the GLSL file
  and line.
- CI uses exactly the same path, cached between runs.

### Saves
Region files (e.g. 32×32 chunk columns per file), palette + RLE per chunk, versioned, written
only by the server.

## M9-M12: making and changing the world

The world after M8 is grassy hills, one cave noise and a critter; edits are one block at a
time. These four milestones make it worth exploring and easy to reshape, in this order
because each needs the one before: bulk edits are how worldgen is debugged, water is
filled and structures are pasted; worldgen gives water somewhere to be (oceans, lakes) and
structures somewhere to stand.

### M9: bulk edits and explosions

- **One edit pipeline** on the server: a shape (sphere, box) and an operation (set, replace
  A with B, carve: air sparing bedrock). Applied chunk by chunk; each touched chunk is
  marked edited (saved), column tops are recomputed once per touched column, and every
  client that has a touched chunk is sent the whole chunk again (under the network backlog
  budget) instead of thousands of single-block messages.
- **No prediction** for bulk edits: the result arrives as chunks one round trip later. What
  must feel instant (the flash, debris, sound of an explosion) comes from an `Explosion`
  message played on arrival, and locally at once for the one who fired.
- **Client side:** relight and remesh the touched chunks and their neighbours, the visible
  ones urgently (M4's no-x-ray rule), the rest within a per-frame budget.
- **Limits:** a largest edit volume and an edit rate per player; commands are cheats.
- **Selections:** two corners (`pos1`/`pos2` from the aimed block), drawn as a box;
  `fill`, `replace`, `sphere`, `clear` act on them. M12's `structure save` uses them too.
- **The rocket launcher:** a creative hotbar item. The rocket is an M8 entity (ballistic,
  no AI), simulated on the server; on hitting a block or entity it explodes: a sphere is
  carved, entities and players nearby are knocked back (players stay invulnerable), debris
  particles and a synthesized boom play where it happened.
- **Exit check, `blast_test`:** like `fly_test`, a console command that fires a volley of
  radius-6 rockets along a path and fails on a server tick or client frame over budget, a
  see-through hole, memory growth, or a chunk that differs between the server and two
  clients (chunk hashes compared).

### M10: the worldgen framework

- **Generators are pipelines** in their own package (`worldgen/`), chosen per world
  (`world.cfg: generator = earth`), deterministic per chunk from the seed. Stages, each with
  its own seed: climate (temperature, humidity, continentalness, erosion noise) and biome
  lookup; terrain shape (a 3D density: base height from splines over the climate, plus 3D
  noise for cliffs and overhangs); surface rules per biome (grass, sand, snow, stone
  layers); carvers (caves, ravines); features (ores, trees, boulders, plants).
- **Crossing chunk borders without seams:** features are placed from a per-chunk RNG and
  every chunk also runs the placements of its 8 neighbours, writing only its own blocks;
  a feature fits within one chunk's margin (trees, boulders). Bigger things are M12's.
- **Parameters are a variable table** (`worldgen.*`): tunable live from the console or F4,
  saved with the world, and `regen` regenerates the chunks around you after a change.
- **Column tops for sky light** come from the generator (including trees), replacing
  M3's analytic `column_height`: with overhangs, the top is no longer a formula.
- **Noise library:** OpenSimplex2-style gradient noise, fractal sums, domain warping,
  written in integer-friendly ways so every OS gives bit-identical worlds.
- **New blocks:** water (still), snow, ice, clay, log, leaves, coal/iron/copper ore, tall
  grass and flowers (cross-shaped models), cactus. Textures generated, as before.
- **Renderer:** a cutout pass (alpha-tested: leaves, plants) and a translucent pass (water:
  drawn after the opaque world, back to front per chunk, its surface gently moving).
- **Tools:** `build worldmap -seed N -size 4096` renders a top-down map (biomes, heights,
  water) to a PNG in seconds, without the game; per-stage timings in the profiler and F3.
- **Exit check:** map hashes per seed equal on all three CI platforms; chunk generation and
  meshing p99 within budget on worker threads; `fly_test` across every biome stays flat in
  memory and within frame budget; a CI screenshot per biome.

### M11: liquids

- **Water states are block ids:** a source and flow levels 1-7 (and falling), so palettes,
  saves and the protocol need no block metadata.
- **Scheduled block updates** on the server: a queue of (due tick, position), so only what
  changes is looked at; a per-tick budget; updates in unloaded chunks wait with them.
- **Minecraft's rules:** down first, then sideways losing a level per block and preferring
  the nearest way down within 4 blocks; a new source between two sources over solid
  ground; placing or breaking next to water schedules its neighbours.
- **Network:** water changes travel as per-chunk batches of changed blocks each tick, not
  one message per block.
- **Players:** swimming in the shared physics (buoyancy, drag, jump to rise), so
  prediction stays exact; underwater fog and tint; sky light falls off through water.
- **Exit check:** a dam-break test (a filled pool, a wall removed) ends in the same water
  every run and on the server and two clients; 10 000 flowing blocks stay within the tick
  budget; swimming has physics tests like walking's.

### M12: structures

- **Templates:** select a box in-game and `structure save <name>`: a `.vxs` file (palette and
  runs, like region files, plus size, origin and which air should stay air). `structure
  paste <name> [rotation]` goes through M9's pipeline. Templates that ship with the game
  live in `assets/structures` (our own builds: within the assets rule).
- **Placement:** each generator lists structure sets with a spacing; the world is cut into
  cells, each cell picks deterministically whether and where its structure goes, so its box
  is known before any of its chunks is generated. A chunk applies every structure piece
  that overlaps it, after terrain and before features; foundations fill down to the
  ground, and the space inside is cleared.
- **Procedural structures** (dungeons as rooms joined by corridors, towers of any height)
  produce the same pieces through the same placement API.
- **Exit check:** a structure spanning several chunks is identical whichever order its
  chunks are generated in; save, paste and save again gives the same file; placements are
  the same for a seed on every run; `worldmap` marks them.

## M13: players together

Mechanisms, not gameplay: what servers and content will be built on. Each feature is a
permission node from the start.

- **World spawn:** chosen once when a world is made (the generator's search, now standing
  clear of trees and structures) and stored in world.cfg; `setworldspawn` moves it. Joining
  for the first time, `spawn`, and every teleport land through one safe-landing step: wait
  until the column is loaded, then stand on the highest spot with ground under it and two
  blocks of air above.
- **Overlays and focus:** the pause menu, options, tuning panel, quit dialog, console and
  chat become entries on one stack. Each declares whether it takes the keyboard, frees the
  mouse or pauses the world; the top one gets the keys and Escape; game controls run only
  when nothing takes the keyboard. The console's line editing (readline keys, history, Tab)
  is a widget any overlay uses.
- **Chat:** `t` opens it, `/` opens it with a command started. Lines fade over the game when
  closed. The server checks each message (length, rate, mute), formats it (the sender's
  tag, name and permitted codes) and sends it to everyone who does not ignore the sender;
  it logs chat. Chat commands share the command table with the console's server commands.
- **Permissions:** nodes are dotted names (`chat.format`, `chat.delete`, `world.edit.bulk`,
  `server.stop`); grants may end in `*` (everything under) or start with `-` (denied).
  Roles grant nodes and inherit other roles; players get roles and their own grants; the
  most specific grant wins, a denial over an allow at the same depth. Roles and players
  carry metadata (prefix, suffix, name colour, anything later). `permissions.cfg` in the
  world directory; edited with `role` and `user` commands or by hand. The owner of a
  singleplayer world and a dedicated server's `--admin` names get `*`. Every server action
  asks one `allowed(player, node)`; today's cheats switch becomes nodes.
- **Formatted text:** `&0`-`&f`, `&#rrggbb`, `&l` bold, `&o` italic, `&n` underline, `&m`
  strikethrough, `&r` reset, parsed in one place (`game/format.odin`). Each part of a chat
  line (tag, name, message) is formatted on its own, so a tag's colour never leaks into
  the name. The UI draws it (bold: drawn twice a pixel apart; italic: slanted), the console
  too.
- **Commands (EssentialsX-style):** places and teleports (spawn, setworldspawn,
  home/sethome/delhome/homes, warp/setwarp/delwarp/warps, tpa/tpahere/tpaccept/tpdeny,
  back, top, tp); messaging (msg, r, me, broadcast, ignore, nick/realname, motd);
  moderation (mute, kick, ban, tempban, unban, ban-ip, deleting chat messages); who and
  status (list, whois, seen, afk, status: tick time, memory, chunks, players). Homes,
  warps, bans and nicknames are kept with the world.
- **Exit check:** permission resolution tests (wildcards, negation, inheritance,
  specificity); focus routing tests (which overlay gets a key, Escape order); chat over UDP
  between two players with roles, tags, colours, a mute and an ignore; spawn and teleport
  landings never inside blocks (tests on worlds with trees and structures at the spot).

### After M12 (not planned in detail yet)

Survival (items and drops, inventory, health, a hostile mob at night), lava as a second
liquid, greedy meshing and low-detail far terrain for long view distances, and M1b (macOS)
when a Mac is at hand.

Block list semantics; greedy meshing with ambient occlusion; overworld noise approach; DDA
