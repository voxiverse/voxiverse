# Voxiverse rewrite plan

A from-scratch rewrite on the orphan `rewrite` branch. The old prototype (`main`) stays
readable next to it as a reference; nothing is copied over, ideas are re-typed on purpose.

## Why

The audit of the prototype found that its problems are architectural, not local:

- One ~130-field `State` mixing process, session, gameplay, per-frame and debug lifetimes;
  leaving a world reset only half of it.
- "Subsystems" that reach into each other (a 14-pointer `Sim_Ctx`, `rawptr` console
  callbacks, a UI library importing the renderer, the world package driving the network).
- A server that is called authoritative but accepts client positions, damage and spawns.
- Mutable objects stored by value in maps, so edits land on copies and are lost.
- No memory strategy: the server never frees its temp allocator or unloads chunks.
- Broken frame model: double-counted timestep, CPU writing GPU buffers still in use,
  validation-layer messages silently discarded, whole-world re-upload on any edit.

The rules below exist to make those mistakes structurally hard to repeat.

## Decisions

| Area | Decision |
|---|---|
| Language/toolchain | Odin, pinned with odinup (`odinup.toml`) |
| Platform | Our own interface with native backends: Win32 (`core:sys/windows`), AppKit (`core:sys/darwin/Foundation`), X11 (`vendor:x11`). Native Wayland and Linux/macOS gamepads later (XWayland meanwhile). No SDL, no GLFW. |
| GPU | Raw Vulkan 1.3 style (dynamic rendering, synchronization2, bindless descriptors). Loader opened at runtime; nothing ships beside the exe. macOS via MoltenVK inside the `.app` (verify feature coverage early). |
| Audio | miniaudio opens the output device only; mixing/voices/spatialization in Odin. Static link. |
| Multiplayer | Client/server boundary and authoritative server from day one, in-process transport first; remote UDP later. |
| Third-party code | Odin `core:` first, `vendor:` only where C is still needed (miniaudio; the UDP layer and the font rasterizer are our own). No `thirdparty/` directory. |
| Assets | Generated by code: block textures, box models, sound effects, icon. Only third-party file: JetBrains Mono (OFL), one weight. No music yet. |
| Tick rate | 30 Hz, one constant in `game/`, announced by the server. Smaller prediction corrections and smoother remote motion than 20 Hz, at negligible cost for a voxel game. |
| World height | Bounded: y -256..+256 (32 chunks), streamed as 16³ chunks. Sky light comes from a per-column top block; saves and build limits stay simple. |
| Light | Classic: 4-bit block light + 4-bit sky light per block, smooth lighting with AO. |
| Game mode | Creative first (instant break/place, hotbar of all blocks, fly toggle); survival rules later. |
| Movement | Minecraft-like baseline (1.8-block player, walk 4.3 b/s, jump 1.25 blocks), every number a console variable. |
| Shaders | GLSL compiled to SPIR-V by a pinned `glslangValidator`, provisioned by the build driver (see Tooling). |
| License | MIT. |

## Ground rules

1. **Lifetimes are structure.** Three tiers, each owning its memory and torn down in one place:
   - `App` (process): settings, platform, GPU device, UI, audio device.
   - `Session` (one world, client or server side): arena-backed; leaving a world frees the arena.
   - `Frame`/`Tick`: scratch arena reset every frame/tick, on every thread that uses one.

   Lower tiers may point into higher ones, never the reverse.
2. **Handles, not pointers or map values, for game objects.** Generational `u32` handles into
   pools (entities, chunks, GPU resources, audio voices). Maps only map keys to handles.
   UUIDs exist only in save files.
3. **Allocating procedures take `allocator := context.allocator, loc := #caller_location`.**
   Enforced in review; no implicit `context.allocator` in long-lived data.
4. **No mutable globals.** Constant tables only; no lazy-initialised globals (they race once
   the server runs on its own thread).
5. **Packages depend downward only** (see layout). A UI or renderer package never imports game
   code; game code never imports platform or GPU code.
6. **Untrusted input is validated at the edge.** Every decoded enum is range-checked, every
   length capped; handlers receive validated types only.
7. **Nothing fails silently.** No silent truncation or dropped work; Vulkan validation on in
   debug and routed to the real logger; asserts on invariants.
8. **One source of truth per fact.** Physics, block rules and RNG live once in shared code;
   the server decides, the client predicts and reconciles.

## Layout

```
base/       handles + pools, arenas, math, rng, log            (depends on nothing)
platform/   window, events, time, paths, dynlib (one file per OS: win32, x11, cocoa)
gpu/        Vulkan: device, swapchain, frames in flight, buffers, images, bindless
            descriptors, pipelines
render/     passes: world (chunks), sky, entities, debug lines, UI; each keeps its own
            per-frame buffers
ui/         immediate-mode UI -> vertices + texture ids (no GPU import)
audio/      device (miniaudio) + mixer + voice pool
game/       shared simulation: blocks, chunk storage, worldgen, lighting, physics,
            entities, protocol (+ codec)
server/     authoritative session: tick, message handlers, streaming, saves
client/     app, session, prediction, meshing jobs, screens, main
tools/      build driver, shader compiler step, asset generators
assets/     font + shader sources (generated output goes to build/, not git)
```

## Core designs

### Main loop
`App` owns platform, GPU, UI, audio. A `Session` exists only inside a world. Each frame:
poll events → map to actions → run fixed ticks (accumulator added once, capped at a few ticks
per frame) → build the UI → each pass records its draws from the session and the UI → render. Tick rate is one constant in
`game/` (30 Hz), announced by the server in the handshake.

### World data
- Chunks 16³, `u16` block ids (room past 256 blocks). In memory a chunk is one block (all
  air, all stone: most chunks) or a flat array from a region reserved for the session's
  maximum, so memory has a hard ceiling; palette + runs on the wire (and on disk). Light
  stored separately.
- One chunk pool plus a coordinate → handle map; explicit chunk states
  (generating, ready, meshed, …) and a dirty-chunk event queue.
- Generation, lighting and meshing run as jobs on worker threads, on immutable padded
  snapshots (18³ for meshing), never on live data.
- Lighting is a pure function in `game/`: a chunk's sky and block light, computed whole from
  its 3x3x3 neighbourhood and the column heights (light travels at most 15 blocks, so that is
  all it depends on), inside the mesh job. No stored light, so no removal pass and nothing to
  go stale: an edit re-meshes the chunks within 15 blocks. (Changed from incremental add and
  removal passes in M4: same results, far fewer ways to be wrong.) The server sends column
  heights (`Column`), since the client cannot see above what it has loaded.
- Interest is a cylinder around each player's chunk, sent nearest first; the client drops
  chunks one past it and the server frees them two past it (hysteresis). Both sides size
  their storage from it once, at join.

### Authority and netcode
- Client sends tick-stamped input commands; the server simulates every player with the shared
  physics and sends snapshots; the client predicts its own player and reconciles.
- Block edits are requests: predicted locally, confirmed or rolled back by the server. Each
  names the input it follows, and the server applies it right after that input, so reach is
  judged from the same position however late it arrives.
- Transport is an interface. First implementation: in-process queues, with the server on its
  own thread (singleplayer keeps a separate client replica on purpose, so authority stays
  honest). Later: UDP (own reliability layer on `core:net`, or ENet behind the interface).
- Protocol has a version handshake, validated decoding, and palette + RLE chunk encoding.

### Renderer
- Retained resources: chunk meshes sub-allocated in one device-local buffer, uploaded per
  chunk through per-frame staging (no whole-world rebuild); textures and meshes by handle.
  Positions relative to the camera's chunk; reverse-Z infinite projection. Greedy meshing
  later (it must respect AO).
- Per frame: a scene buffer (camera, sky, clouds; read by address in the shaders) and each
  pass's own per-frame-in-flight buffers (entity boxes and particles, debug lines, UI
  vertices).
- Swapchain recreation touches only the swapchain and size-dependent images.

### UI
- Immediate mode, one hashed id system with an id stack.
- Hover, keyboard focus and active are separate states; clicks fire on release over the same
  widget.
- Layers (base, popup, modal, tooltip) decide input priority and draw order.
- Per-command scissor clipping; a layout cursor (rows/columns) instead of hand-placed rects.
- Input is a generic event stream (keys, text, pointer), not game actions.
- Output is vertices + texture ids; the renderer draws them.

### Input
Platform events → action map (rebindable) → per-tick input command. Text input is a separate
event stream for UI and console.

### Console and variables
Not a global registry (Quake's cvars, Call of Duty's dvars): every tunable value is a field
of a typed struct with one owner, described once in a table (name, type, range, default,
help) that the console, the tuning panel and save files all use. Code reads plain fields.

| Kind | Examples | Owner | Saved | Changed by |
|---|---|---|---|---|
| Client settings | sensitivity, FOV, UI scale, view distance, volume | App | settings file | the user; never sent |
| Game rules (`game.Rules`) | gravity, speeds, jump, reach, flying | server session | world save | the server only; sent in Welcome and as tick-stamped changes so prediction uses them |
| Debug switches | chunk borders, net trace, simulated latency | the side they affect | no | console, dev builds |

Singleplayer changes rules by sending a command message to its own server, never by writing
server memory. A value becomes a variable only when someone tunes it; design decisions
(tick rate, chunk size, protocol limits) stay constants. Cheat/dev commands only in dev
builds.

### From Quake 3: kept and dropped
Kept: authoritative server, client prediction of its own movement from tick-numbered input
commands, one movement code path for both sides, a local server for singleplayer, fixed
server tick, interpolated (not predicted) remote entities, console + config scripts.
Dropped: global string cvars (see above); everything-on-unreliable-snapshots (chunks and
edits need a reliable ordered stream; entities get snapshots); client-reported frame times
in commands (speed hacks; we tie inputs to server ticks and cap them); sending every entity
to everyone (interest management); QVM; lag-compensated hits until there is combat.

### Assets
Generated by code at startup, deterministic on every machine: block textures (procedural,
palette-quantized), sounds (synthesized; `build sfx` writes them out to listen to), the font
atlas (JetBrains Mono, rasterized by our own `font/` as glyphs are needed). Shaders are the
one build-time asset (SPIR-V, hot reloaded in dev builds).

### Tooling
Setting up a fresh machine is: install odinup, then run `build`. Nothing else.

- The build driver is an Odin program (`tools/build`); `build.sh` / `build.bat` only hand off
  to it.
- **Shader compiler, zero setup:** on first use the driver downloads the pinned official
  glslang release for the host OS (Khronos GitHub release, Windows x64 / Linux x86_64 /
  macOS universal) with the `curl` and `tar` every supported OS ships, verifies its SHA-256
  against hashes committed in the repo, and unpacks it into `build/tools/`. Everyone compiles
  with the same version; bumping it is a one-line change plus hashes.
- Override for unusual hosts (e.g. Linux arm64): `GLSLANG=/path/to/glslangValidator`.
- Shaders recompile only when their source changes; compile errors point at the GLSL file
  and line.
- CI uses exactly the same path, cached between runs.

### Saves
Region files (e.g. 32×32 chunk columns per file), palette + RLE per chunk, versioned, written
only by the server.

## Nomenclature

One word per thing, in code, docs and UI alike. Where today's code still says otherwise,
the milestone that changes it is named.

**Where things are**

|---|---|---|

**Renames these imply:** M16 turns player files into characters
(`characters/<account>/<character>.json`). M17 renames the client's Worlds screen and
`world <name>` command to universes (the singleplayer list is a list of universes), moves
`world.cfg`'s universe-wide parts to `universe.cfg`, and gives each world its own
`worlds/<id>/world.cfg`, regions and entities. `server.World` (the chunk store) becomes
part of a per-world struct.

## Milestones

Each one is a vertical slice with an exit check; nothing moves on with failing checks.
Sections of finished milestones are in [HISTORY.md](HISTORY.md).

**How a milestone is sized (from M22; revised after M25: see "Why the plan changed").** The work is done by an AI assistant on a plan
with a usage limit. Measured over M19-M21: nearly all of the usage was the assistant
re-reading its own conversation on every step (a session that ran for days, about half a
million tokens re-read per step), not the code it wrote. So:

- **One milestone, one fresh session.** "On to M<n>" starts a new conversation that reads
  this file's section for M<n> and the code it names. A section therefore carries every
  decision: what to build, where, the numbers, what is left out, and the exit check. A
  milestone with an open design question is not ready; the question is settled first, in
  conversation.
- **Small enough to finish in one sitting:** one new system, or one system and the content
  that proves it. Bigger ideas are split (M20, done the old way, would be three).
- **Checked locally first,** with the tests the milestone touches (`odin test <package>
  -define:ODIN_TEST_NAMES=...`), then the whole suite once; pushed once at the end, and CI
  waited on once (a blocking `gh run watch`), not polled.
- **Windows-only code is kept together** (one milestone of it, checked on a Windows
  machine), because each mistake there costs a round trip through CI.
- **Done means:** the exit check passes, the table row says what was done, a line is
  added to the cost table below, committed and pushed; then the session ends. The next
  milestone is the next session. A finished milestone's section moves to HISTORY.md.
- **The model:** a milestone whose section is complete is implemented with a faster,
  cheaper model (Sonnet); planning sessions, design questions and debugging that has
  stalled use the strongest (Opus), whose usage counts several times as much.
- **A milestone that outgrows one usage window stops:** what works is committed, the rest
  becomes a milestone of its own. A long session is the costliest kind.
- **The week:** a planning session first (Opus, about an hour, no code) that settles one
  open question into a milestone section and checks the order; then a milestone a session;
  at the end, a Windows check if anything needs one and a release tag. About a fifth of
  the budget is left free for what players report.
- **The mix:** at least one milestone a week is something only this game has (from the
  open questions: worlds, their peoples and histories). Something Minecraft already has is
  built only when one of those needs it, never for completeness.
- **No more infrastructure** (CI, benchmarks, tooling) unless something breaks or measurably
  slows the work.

## M26: events and counters (the foundation for stats, analytics and an RPG)

Re-planned after M25 (see "Why the plan changed" below). One pipeline; everything that
measures play hangs off it, so nothing is counted twice or in a different way.

- **One call:** `event(kind, actor, fields)` in a new package `telemetry/` (depends on
  `base` only). `Event_Kind` is an enum with a table (name, field names and types, version),
  so a kind cannot be emitted with the wrong fields and every kind is documented in one
  place. An event carries: wall time (ms), server tick, session id, actor (the player's id
  in the world, mapped to an anonymous `pid` on the way out), world address, position (block
  coordinates, when it has one), and up to four typed fields (i64, f64, a short string).
  Emitting is a ring-buffer push; nothing blocks the tick. A burst drops the oldest and
  counts what it dropped (itself an event).
- **Consumers** (each a procedure on the drained batch, in the writer thread, never the
  tick): (1) **counters**: a table maps event kinds to dotted counters (`blocks.mined.stone`,
  `distance.walked`, `items.picked.<item>` ... the list in M29's old text, kept below), a
  parent's total is the sum of its children (asked, not stored); (2) **the local log**:
  JSON lines in `<world or server dir>/telemetry/YYYY-MM-DD.jsonl`, a size cap per day;
  (3) M27's upload spool.
- **What is emitted** (server side; it is authoritative): sessions (join, leave, duration,
  client version/OS/GPU/view distance as told by the client's hello, frame-time and network
  summaries), gameplay (edits with block and position, item picked/dropped/used/**crafted
  later**, entities hit/killed, chat counts, commands, teleports and travel, gate dials,
  explosions, sheep fed/sheared/born), progression hooks (nothing yet, but the kind
  table has room: `xp`, `level`, `death` with cause and place), performance (tick time
  p50/p99 and players online each minute, chunk wait, edit confirmation latency, bytes
  sent), and **position samples** (every 10 s per player: where, in which world, doing
  what: heat maps and "where do players die or leave"). Client events the server cannot see
  (overlays opened and how long, settings changed from what to what, launch to playing,
  menu path) ride in a `Telemetry` client message, rate-capped, size-limited and validated;
  singleplayer takes the same path.
- **Counters stored** with the character (`"stats": {...}`, M16) and the world's totals in
  `<world>/stats.json`, written when dirty; only online players in memory.
- **Seeing it:** `stats [player] [filter]` in chat, and a stats overlay (a command and a
  key): scrollable, searchable tree, numbers by unit; the server sends a player's stats
  on request, paged. Others' stats need `info.stats.others`.
- **What an MMO RPG needs from this** (so the kinds are chosen on purpose): item sources and
  sinks (what enters and leaves the economy, from where), time to progress, deaths by cause
  and place, who plays with whom, session length and return rate, content use (which
  structures, biomes, gates are visited), server health (tick, bandwidth, players).
- **Exit check:** a scripted session (walk, swim, fly, mine, place, pick up, fight, chat,
  teleport, shear, feed) gives exactly the expected counters and the same after save and
  load; the local log has the expected kinds and fields in order; a burst of 100k events
  never stalls the tick (tick p99 within budget) and the drop counter says what was lost;
  the day cap holds; malformed or oversized client reports are refused; many players with
  thousands of counters save and load within budget; UI tests for the overlay's search and
  scrolling; the overlay over UDP shows the server's numbers.

Counter names (from the old M29): `blocks.mined.<block>`, `blocks.placed.<block>`,
`distance.walked` / `flown` / `swum` / `fallen` (cm), `jumps`, `items.picked.<item>`,
`items.dropped.<item>`, `items.used.<item>`, `entities.hit.<kind>`, `entities.killed.<kind>`,
`explosions`, `rockets.fired`, `chat.lines`, `chat.whispers`, `commands.<name>`,
`teleports.<how>`, `time.played`, `time.away`, `time.flying`, `time.underwater` (seconds),
`sessions`, `structures.found.<kind>`, `biomes.visited.<biome>`, `sheep.fed`, `sheep.sheared`,
`sheep.born`.

## M27: remote telemetry (a collector and the lake)

So that play data and crash reports reach the developer without anyone copying files.

- **Transport: our own netcode, not HTTP.** TLS from a native-Odin game with no shipped
  libraries is the expensive part of "send data to a server"; the game already has a
  reliable authenticated UDP protocol with account keys. A **collector** is the dedicated
  server binary in another mode (`voxiverse-server --collector`) that accepts only
  `Telemetry_Batch` messages (a signed batch of M26 events, or a report) and writes them;
  it keeps no worlds and does not log source addresses. The data is not secret (no names,
  no chat text, no addresses: players are an anonymous `pid`, a salted hash of the account
  key), so lack of encryption on the wire is accepted for now; if that changes, the cost is
  in the netcode, once, for everything.
- **Uploading:** the client and any server queue events in M26's spool (`telemetry/spool/*.jsonl`
  beside the settings, size and age capped: 50 MB / 14 days), and send batches of at most
  32 KiB every 30 s and at exit, resending until acknowledged; the collector's address is a
  setting with a default; singleplayer and dedicated servers upload too (their own server
  events as `source=server`).
- **Consent:** off until the player has been asked once, on first launch, in the game's own
  words ("Share anonymous play data to help improve Voxiverse?" Yes / No, changeable in
  Options > Profile); No means nothing is queued, nothing is sent (tested). Reports a player
  sends on purpose (below) are always theirs to send.
- **Crashes and reports:** the crash handler writes a report file (version, OS, GPU, the
  last 200 log lines, the stack); the next launch offers to send it (consent or not: it asks
  that once) as a `report` batch; a `report <text>` command and a menu button send the
  current log tail with the player's note.
- **The lake:** the collector writes `lake/dt=YYYY-MM-DD/source=<client|server|report>/<hour>.jsonl`
  (append-only, rotated hourly, never rewritten). That directory *is* the data lake: files in
  partitioned folders, queried in place with DuckDB (`select ... from read_json_auto('lake/**/*.jsonl')`).
  `tools/analytics` is a thin CLI over it with the questions asked most (sessions and
  retention, funnels from launch to playing, events per kind, slowest moments, economy flow,
  deaths and positions as a heat-map PNG) and `tools/lake-sync` pulls a collector's lake to a
  local directory, so the assistant can be told "sync and summarize" instead of being handed
  files.
- **Operations** (documented in `docs/telemetry.md`, not code): run the collector on a small
  VPS under a service manager, rsync or object-store sync of `lake/` for backup, retention
  policy (raw 180 days, then aggregated), how to delete a `pid`'s data on request.
- **Exit check:** a test with a collector, two clients and a server: batches arrive, verified
  and written to the right partitions; the collector down for a while, the spool keeps and
  resends everything exactly once; a forged signature, an oversized batch, a flood and an
  unknown kind are refused; consent off sends no packets at all; a crash report round-trips;
  `tools/analytics` summarizes a recorded run.

## M28: character attributes, modifiers and health

The part an RPG stands on, and what the equipment slots (M22b) were waiting for.

- **Derived stats:** one function `derive(character) -> Derived` from base attributes,
  worn and held items' modifiers and timed effects, producing the numbers physics and rules
  read (walk, sprint and jump multipliers, extra jumps, max health, reach); the server and
  the client's prediction call it with the same inputs (the equipment is already replicated
  in the inventory), so prediction stays exact.
- **Item modifiers:** `Item_Info.modifiers` (a short list of kind + amount), so boots can
  make you faster and a charm give a double jump, with no code per item (the backlog's
  "item systems" note, done as data).
- **Health, damage, death:** health and a max, fall damage (from the shared physics),
  explosion damage, death and respawn at the world's spawn (what is dropped is a rule); each
  emits M26 events with cause and place. Health shown as a bar by the hotbar.
- **Progression hook:** a table maps M26 events to experience (`xp` per kind, a level curve
  as data), the level and xp are character state, shown in the stats overlay; no rewards
  yet beyond a number, but the pipeline from "something happened" to "the character grew" is
  there and tested.
- **Exit check:** server and client agree on a tick-by-tick run with a speed modifier and a
  double jump (prediction tests, both ways); fall and explosion damage by the rules' numbers;
  death, respawn and the dropped items; xp and level from a scripted session, kept through
  save and load; the events carry the right causes.

## Why the plan changed (after M25)

- **Sizing was wrong by a factor of ten.** Milestones planned as a week each took one to two
  hours (M22 to M25: 60 to 160 assistant steps each). A milestone section may now be several
  times bigger, and a session may take two or three that belong together.
- **What was being built was the content that sits on top of foundations that did not exist
  yet**: sheep genetics, crops and a chest came before any way to know how people play, or to
  reach the developer's eyes without copying files. Content is cheap now, and cheap to
  re-order; measuring is the thing that makes every later decision better, and it is the part
  that cannot be added later for the time already played.
- **Stats were planned as counters for display; an MMO RPG needs them as a stream** (events
  that counters, logs, progression and economy analysis all read), plus the character state
  progression changes (attributes, health, xp). Hence M26 and M28 share one design.
- **Deferred, in the order they will come back**, below: blocks that hold things (chests,
  signs: infrastructure for teleporter blocks and shops), the Windows pass (needs a Windows
  machine), sky and time. Then, as before, the list after M30 (minimap, throwables, ...) and
  nothing from it before the foundation above is done.

## Deferred: blocks that hold things (was M26)

Some blocks need data of their own (a chest's contents, later a sign's text or a
teleporter's name). Minecraft calls these block entities; here they are records kept with
a block.

- **The record:** keyed by the block's position, owned by the server, stored per chunk and
  saved with it (a new section in the region format, versioned). Made when its block is
  placed, removed when it is broken; on load, a record whose block is not there is dropped
  (and logged).
- **To clients:** sent only when needed (a chest's contents when it is opened, then its
  changes while it is open), never with the chunk.
- **The chest:** a block (generated texture; a real chest model later) whose record is a
  server-owned container of 25 slots, the size of the inventory, moved with the existing
  container messages (M14). Using it opens an overlay with the chest above the player's
  inventory. Several players may have it open: each sees the others' moves. Breaking it
  drops everything in it. From the creative catalog for now (there is no crafting).
- **Not here:** double chests, hoppers, locks, signs.
- **Exit check:** a chest filled, saved, quit and loaded holds the same; unloaded and
  reloaded with its chunk, the same; broken, it drops every stack; two players over UDP
  moving items in one chest see each other's moves and end up agreeing with the server; a
  record without its block is dropped on load.

## Deferred until a Windows machine is at hand: Windows behaviour and the new icon (was M27)

Everything that needs a Windows machine, together, checked there once at the end.

- **The icon:** a black cube with a question mark: the same three-faced 16 x 16 cube drawn
  by code (`build icon`), its faces near-black in three shades, a light grey question mark
  (5 x 7 texels) on its left face; scaled texel for texel to each size. It replaces the
  grass block in the executable, the window and the taskbar. If the mark is too busy at
  16 x 16, that size drops it (decided on seeing it).
- **Landing dust:** falling three blocks or more and landing kicks up puffs of the block
  landed on, more for a harder landing; for every player in view (seen from their
  snapshots). Visual only until there is fall damage.
- **Native Windows behaviour** (what SDL3 and GLFW do that we do not yet; per-monitor DPI,
  raw mouse input, cursor clipping and UTF-16 pairs are done):
  - `WM_DPICHANGED`: take the suggested rectangle when moved to a monitor of another scale.
  - `WM_SYSCOMMAND`/`SC_KEYMENU`: Alt and F10 must not open the window menu (which
    freezes the loop until a key).
  - Moving and resizing: Windows runs a modal loop while the frame is dragged and the
    game stops; keep it rendering through it (a timer during the move, as SDL3 does) or
    run the game loop off the window's thread.
  - A dark title bar (`DwmSetWindowAttribute`, `DWMWA_USE_IMMERSIVE_DARK_MODE`).
  - Precise frame pacing: a high-resolution waitable timer
    (`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`) for the menu frame cap, not `Sleep`'s 15 ms.
  - Not slowed in the background: power throttling off for the process
    (`SetProcessInformation`, `ProcessPowerThrottling`); the render thread registered
    with MMCSS as "Games".
  - An AppUserModelID (the taskbar groups the game's windows under its icon).
  - No system error dialogs (`SetErrorMode`); started from a console, logs to it
    (`AttachConsole(ATTACH_PARENT_PROCESS)`).
  - Each checked on a Windows machine (some only show there).
- **Exit check:** the Windows list ticked off on a Windows machine; the icon at every size
  in CI's artifacts; landing dust seen for every player in view.

## Deferred: sky and time (was M28)

Cheap, deterministic astronomy, so a world implies a sky worth observing (one could keep a
lunar calendar by watching): a few trigonometric terms per frame from the world clock.

- **Each world's astronomy** (from its address; the home world Earth-like): day length,
  days in a year, axial tilt, one or more moons with their periods, and a star catalogue.
- **The sun's path:** its height and bearing from the time of day, the day of the year
  (declination from the tilt) and the latitude (from z): longer days in summer, a lower
  sun in winter. Light follows the sun's height as today.
- **Moons:** each at its own period; the phase from the sun and moon's angle, drawn as a
  pixel disc with its lit part; rising and setting at their own times.
- **Stars:** fixed per world (its seed), on a sphere that turns once per sidereal day
  (slightly shorter than a solar day), so the night sky shifts through the year.
- **The calendar:** `calendar` reads the day, month (by the first moon), year and moon
  phases; the server's clock is the only input, so every client sees the same sky.
- **Not here:** seasons changing the land (snow cover, leaves) would mean block updates
  across the world: later, if ever.
- **Exit check:** golden values for the sun, moons and calendar at chosen moments on every
  platform; a moon's phase repeats on its period; star positions drift by the sidereal
  difference night to night; sky screenshots at a few dates.

- **Flying animals:** a flock of birds steering by the three boids rules (separation,
  alignment, cohesion) with the terrain as an obstacle; server-simulated, cheap per bird.
- **Sound, again:** the generated effects reworked for character, not technique (each
  sound designed against a reference recording's shape, then synthesized).
- **Tools:** a pickaxe for soil and stone, an axe for wood (whether hands can break and
  whether breaking takes time is decided then).
- **Itemization (Diablo II style, not enchantments):** items that can be unique get an
  instance of their own (rarity, affixes and suffixes rolled from a seed, flavour text),
  which means stacks carry data (the wire, the player files) and such items stack one. The
  data is there from the first drop but shown only once the character has learned of it
  (a knowledge flag a later mechanic sets). Needs tools and equipment worth rolling;
  the stack data change goes in with tools.
- A dungeon's boss: a boss bar across the top, and its loot thrown out in a burst when it
  dies.
- Lava as a second liquid; greedy meshing and low-detail far terrain for long view
  distances; M1b (macOS) when a Mac is at hand.

### Open questions (to settle in conversation before they become milestones)

- **Music:** composed as notes (MIDI-like: exact pitches and timings a real instrument could
  play) and rendered by our synthesizer at start-up, or written out and recorded? What
  does each world sound like?
- **Worlds that change while you are away:** what happens in a world over the time a
  player spends elsewhere (wars, growth, ruin), how it is computed cheaply when the world
  is loaded again, and whether worlds have histories generated from their seed.
- **Peoples between worlds:** factions and a player's standing with each, per world or
  across worlds; whether worlds near each other by address can be neighbours a people
  spans ("the next world over").
- **A lesson per world:** each world with its own puzzle to solve.
- **Kinds of world:** more generators, and what they are called (scientific names, or
  invented ones).
- **Moving faster:** dash, double jump, a grappling hook: from items, or from something a
  character learns.
- **Items and slots:** how many slots, how that changes as a character goes on, and how
  items stay simple to use as there are more of them.
- **Learning the game in the game:** everything a player needs to know found in the world
  itself (no tutorial, no wiki).
- **Machines:** something to build working machines from (as Minecraft's redstone with its
  slime-block flying machines), but fewer, denser parts.
- **The download site:** voxiverse.net with one Download button that picks the visitor's
  system (M21 has the way there), and the project going private with it.

### From notes, changed or not taken

- Gates are dialed, not built (no portal frames to light), and they are found, one by
  every spawn: discovery is reading and sharing addresses, which needs the address to
  mean something, hence an address decides a world's kind.
- Square slots needed icons more than a new shape: names do not fit squares.
- Landing dust before fall damage is decoration; kept small.
- Real stars and calendars are kept, but computed, not simulated: no orbits integrated,
  no seasons in the blocks.
- Villagers and itemized loot wait for the systems they stand on (attributes, tools); a
  trader without things worth trading would be a stub.
