# Design

How Voxiverse is built and why: the decisions, the rules every change follows, and the core
designs. A cheat sheet: it says what is true of the code now. Terms are in
[glossary.md](glossary.md); the folders and their files in [layout.md](layout.md).

## Ground rules

1. **Lifetimes are structure.** Three tiers, each owning its memory and torn down in one place:
   - `App` (process): settings, platform, GPU device, UI, audio device.
   - `Session` (one world, client or server side): arena-backed; leaving a world frees the arena.
   - `Frame`/`Tick`: scratch arena reset every frame/tick, on every thread that uses one.

   Lower tiers may point into higher ones, never the reverse.
2. **Handles, not pointers or map values, for game objects.** Generational `u32` handles into
   pools (entities, chunks, GPU resources, audio voices). Maps only map keys to handles.
   UUIDs exist only in save files.
3. **Allocating procedures take `allocator := context.allocator, loc := #caller_location`.**
   Enforced in review; no implicit `context.allocator` in long-lived data.
4. **No mutable globals.** Constant tables only; no lazy-initialised globals (they race once
   the server runs on its own thread).
5. **Packages depend downward only** (see layout). A UI or renderer package never imports game
   code; game code never imports platform or GPU code.
6. **Untrusted input is validated at the edge.** Every decoded enum is range-checked, every
   length capped; handlers receive validated types only. Every untrusted input has a fuzz
   target in `build fuzz` (from Q1); a milestone that adds an input adds its target, and one
   that builds a defence marks its threat rows in `docs/threat_model.md` built with their
   covers, in the same commit (from Q5, checked by `lint:quality_docs`).
7. **Nothing fails silently.** No silent truncation or dropped work; Vulkan validation on in
   debug and routed to the real logger; asserts on invariants.
8. **One source of truth per fact.** Physics, block rules and RNG live once in shared code;
   the server decides, the client predicts and reconciles.

## Core designs

### Main loop
`App` owns platform, GPU, UI, audio. A `Session` exists only inside a world. Each frame:
poll events → map to actions → run fixed ticks (accumulator added once, capped at a few ticks
per frame) → build the UI → each pass records its draws from the session and the UI → render. Tick rate is one constant in
`game/` (30 Hz), announced by the server in the handshake.

### World data
- Chunks 16³, `u16` block ids (room past 256 blocks). In memory a chunk is one block (all
  air, all stone: most chunks) or a flat array from a region reserved for the session's
  maximum, so memory has a hard ceiling; palette + runs on the wire (and on disk). Light
  stored separately.
- One chunk pool plus a coordinate → handle map; explicit chunk states
  (generating, ready, meshed, …) and a dirty-chunk event queue.
- Generation, lighting and meshing run as jobs on worker threads, on immutable padded
  snapshots (18³ for meshing), never on live data.
- Lighting is a pure function in `game/`: a chunk's sky and block light, computed whole from
  its 3x3x3 neighbourhood and the column heights (light travels at most 15 blocks, so that is
  all it depends on), inside the mesh job. No stored light, so no removal pass and nothing to
  go stale: an edit re-meshes the chunks within 15 blocks. (Changed from incremental add and
  removal passes in M4: same results, far fewer ways to be wrong.) The server sends column
  heights (`Column`), since the client cannot see above what it has loaded.
- Interest is a cylinder around each player's chunk, sent nearest first; the client drops
  chunks one past it and the server frees them two past it (hysteresis). Both sides size
  their storage from it once, at join.

### Authority and netcode
- Client sends tick-stamped input commands; the server simulates every player with the shared
  physics and sends snapshots; the client predicts its own player and reconciles.
- Block edits are requests: predicted locally, confirmed or rolled back by the server. Each
  names the input it follows, and the server applies it right after that input, so reach is
  judged from the same position however late it arrives.
- Transport is an interface. First implementation: in-process queues, with the server on its
  own thread (singleplayer keeps a separate client replica on purpose, so authority stays
  honest). Later: UDP (own reliability layer on `core:net`, or ENet behind the interface).
- Protocol has a version handshake, validated decoding, and palette + RLE chunk encoding.

### Renderer
- Retained resources: chunk meshes sub-allocated in one device-local buffer, uploaded per
  chunk through per-frame staging (no whole-world rebuild); textures and meshes by handle.
  Positions relative to the camera's chunk; reverse-Z infinite projection. Greedy meshing
  later (it must respect AO).
- Per frame: a scene buffer (camera, sky, clouds; read by address in the shaders) and each
  pass's own per-frame-in-flight buffers (entity boxes and particles, debug lines, UI
  vertices).
- Swapchain recreation touches only the swapchain and size-dependent images.

### UI
- Immediate mode, one hashed id system with an id stack.
- Hover, keyboard focus and active are separate states; clicks fire on release over the same
  widget.
- Layers (base, popup, modal, tooltip) decide input priority and draw order.
- Per-command scissor clipping; a layout cursor (rows/columns) instead of hand-placed rects.
- Input is a generic event stream (keys, text, pointer, and navigation: up, down, left, right,
  confirm, back, previous and next tab, from a pad or the keyboard: M42), not game actions.
- Output is vertices + texture ids; the renderer draws them.
- One look (the `Theme`), no player-chosen themes; a call site overrides it for the widgets it
  draws with a scoped `theme_scope` (colours, metrics, an `opacity` for everything inside: M40).

### Input
Platform events (keyboard, mouse, gamepads: M41) → action map (rebindable, per context: in the
world, in a menu) → per-tick input command. Analog values (sticks, triggers) are actions too.
Text input is a separate event stream for UI and console.

### Console and variables
Not a global registry (Quake's cvars, Call of Duty's dvars): every tunable value is a field
of a typed struct with one owner, described once in a table (name, type, range, default,
help) that the console, the tuning panel and save files all use. Code reads plain fields.

| Kind | Examples | Owner | Saved | Changed by |
|---|---|---|---|---|
| Client settings | sensitivity, FOV, UI scale, view distance, volume | App | settings file | the user; never sent |
| Game rules (`game.Rules`) | gravity, speeds, jump, reach, flying | server session | world save | the server only; sent in Welcome and as tick-stamped changes so prediction uses them |
| Debug switches | chunk borders, net trace, simulated latency | the side they affect | no | console, dev builds |

Singleplayer changes rules by sending a command message to its own server, never by writing
server memory. A value becomes a variable only when someone tunes it; design decisions
(tick rate, chunk size, protocol limits) stay constants. Cheat/dev commands only in dev
builds.

### From Quake 3: kept and dropped
Kept: authoritative server, client prediction of its own movement from tick-numbered input
commands, one movement code path for both sides, a local server for singleplayer, fixed
server tick, interpolated (not predicted) remote entities, console + config scripts.
Dropped: global string cvars (see above); everything-on-unreliable-snapshots (chunks and
edits need a reliable ordered stream; entities get snapshots); client-reported frame times
in commands (speed hacks; we tie inputs to server ticks and cap them); sending every entity
to everyone (interest management); QVM; lag-compensated hits until there is combat.

### Assets
Generated by code at startup, deterministic on every machine: block textures (procedural,
palette-quantized), sounds (synthesized; `build sfx` writes them out to listen to), the font
atlas (JetBrains Mono, rasterized by our own `font/` as glyphs are needed). Shaders are the
one build-time asset (SPIR-V, hot reloaded in dev builds).

### Tooling
Setting up a fresh machine is: install odinup, then run `build`. Nothing else.

- The build driver is an Odin program (`tools/build`); `build.sh` / `build.bat` only hand off
  to it.
- **Shader compiler, zero setup:** on first use the driver downloads the pinned official
  glslang release for the host OS (Khronos GitHub release, Windows x64 / Linux x86_64 /
  macOS universal) with the `curl` and `tar` every supported OS ships, verifies its SHA-256
  against hashes committed in the repo, and unpacks it into `build/tools/`. Everyone compiles
  with the same version; bumping it is a one-line change plus hashes.
- Override for unusual hosts (e.g. Linux arm64): `GLSLANG=/path/to/glslangValidator`.
- Shaders recompile only when their content key changes (below); compile errors point at
  the GLSL file and line.
- **The inner loop is parallel and skips what is unchanged, by content (2026-10-29).** `check` runs the host's type checks and the other targets' object builds in
  one pool, one job per core (`VX_JOBS=n` overrides); `test` runs the packages the same way,
  the slowest last time first, each printing its output whole when it ends; `test
  <package>...` runs only those. A step whose inputs are byte for byte what they were when
  it last succeeded is not repeated: a test package runs its kept binary without compiling,
  a cross-OS object build and a file's formatting check are not redone, a shader is not
  recompiled, and `build.sh`/`build.bat` rebuild the driver only when its own inputs
  changed (`tools/build/cache.odin`, records in `build/cache/`). A key is a 128-bit XXH3 over
  the command, `odin version` and the content of every file the compiler read (its
  `-export-dependencies` list: sources and `#load`s) plus the names in their directories, so
  a file added beside them counts; it is kept only when every input is older than the
  step's start. Modification times alone never decide: a stale result is a wrong one, not a
  speedup. The host's `odin check` is not cached (it has no dependency list) and takes
  seconds in parallel. A test that loops over independent cases that each take seconds (the
  music, the audio scenarios, seeking in each file) is one test per case, so the runner's
  threads share them; a new case needs its test (an `#assert` on the count says so).
- CI uses exactly the same path, cached between runs.
- CI's Linux checks are split into two parallel jobs, "Test · Linux x64" (check, tests, determinism,
  the smoke suite) and "Game · Linux x64" (everything that runs the game or tools under
  xvfb), because the one Linux job alone set CI's length (17 min median, 38 worst). Every
  check still runs on every push. The tests run once, with `ODIN_TEST_RANDOM_SEED` set to the
  run number (a re-run repeats it). `./build.sh test` turns `ODIN_TEST_RANDOM_SEED` and
  `ODIN_TEST_THREADS` from the environment into `-define:` flags (Odin reads them only as
  defines), so `ODIN_TEST_RANDOM_SEED=n ./build.sh test` reproduces a CI failure. A test's big values go on the heap (`new`, `defer free`): the runner's threads have the platform's default stack, 512 KB on macOS against Linux's 8 MB, and a test holding three `engine.App` (237 KB each) died there with a silent exit and no message (CI run 41234007812; the Apps in `client/main` and `client/console` tests moved to the heap; again in run 41364005439, where `client/main`'s two `Frame_Rig` tests held a whole `Harness`, 95 KB, plus `session_start`'s frames: those rigs are on the heap too; `ulimit -s 320` before `./build.sh test client/main` reproduces a stack too small, the test thread taking the shell's limit on Linux; run 41390538806 died again, silently, on macOS: `s^ = {...}` builds the whole literal on the stack before copying, so `session_start` (a 214 KB `Session`), `core.start`, `link_connect`, `conn_init` and `host`'s `handle` held 65-214 KB each, and `for p in h.peers` copied a 64 KB `Peer` per step: those assign `s^ = {}` and then the fields, and loop `for &p`; the tests' `Session` and `Harness` are on the heap; `ulimit -s 160 ./build.sh test client/main` passes, where 300 was needed before). Every `odin test` also gets `-define:ODIN_TEST_FAIL_ON_BAD_MEMORY=true` (tracking stays on): a test that leaks or frees badly fails, naming the allocation's line. Ownership: `registry_build`'s errors and `registry_id_changes`' text belong to the caller (`pack_errors_destroy`, `delete`); a thread started with `thread.create_and_start_with_poly_data` is given `context`, so what it allocates is freed by the owner under the same allocator. A test package's binary, log and timing file are named by its whole path (`build/test/client-music`, `tools-music`; the cross objects of `check` too): by the last element alone `client/music` and `tools/music` shared one file, started the binary while the other still wrote it (`Could not spawn subprocess: Text file busy`) and the passing run's log replaced the failing one's (reproduced with `ODIN_TEST_RANDOM_SEED` runs of the music, audio and ogg packages together; `test_test_packages_keep_their_own_files` keeps names unique). No test asserts a time (T5): a performance budget is a scenario of `build bench` (`chunks`, `telemetry`, `budgets`, the game's `viewmodel` and `audio`) with its limits beside it in code, gated by CI's "Benchmark check" steps in a release-like build, and a test calls the same scene for what it does (`server/core/budgets.odin`: a save that commits, 10 000 blocks flowing, an audit with no lines). A budget is read from `base.thread_cpu_us` (the thread's CPU time), not a wall clock: a core taken from the measured thread is not the work's cost (a 27 ms wall-clock capture of a few ms of work once failed a test). On Windows it is the thread's cycle count over a rate measured against the wall clock: `GetThreadTimes` advances once per 15.6 ms scheduler tick, and read a 2 ms slice as 15625 us (CI run 40590622700). Where the work is big and the runner's speed is the unknown, the budget is a multiple of a reference the scene measures on the same thread in the same run (`counters_ratio`: save and load at most 6 times what building the counters cost, measured at 3), since a fixed 8 s failed at 10.6 s on a slow macOS runner. Ubuntu packages come from a cache of their `.deb` files
  (`.github/actions/apt`), because the package mirror twice took over 20 minutes.
- **A panic must fail a test, never hang it.** The Odin test runner's signal handler
  (`stop_test_callback`) returns without doing anything on a thread the runner did not start;
  the trap then runs again, for ever, at full CPU. A thread a test starts (the server, job
  workers, the telemetry writer, the collector, audio threads) copies the test's context, whose
  `assertion_failure_proc` is the runner's, so a panic there spun (a 29 minute, 575% CPU hang in
  `write_vars`). Every thread we start gets `base.thread_context()` instead: under `odin test`
  its failed assert or panic prints and ends the process (exit 2), so the run fails in
  seconds. A new thread-starting site must use it. Second layer: `./build.sh test` runs each
  package under a limit (ten times its last passing run, at least ten minutes;
  `VX_TEST_TIMEOUT_SECONDS` overrides it), kills the run with its children when it is over and
  reports `test <package> FAILED: still running`. `test_panic_in_a_server_thread_fails_fast`
  (tests/, with the `tests/panic_fixture` package, not in TEST_PACKAGES) panics on
  purpose in a worker with a server running and expects a failure well inside the limit;
  `test_run_limited_kills_the_tree` covers the kill.

### Saves
Region files (e.g. 32×32 chunk columns per file), palette + RLE per chunk, versioned, written
only by the server.

## Audio engine

### Decisions (locked; change them only by editing this list)

| Area | Decision |
|---|---|
| Not used | FMOD, Wwise and OpenAL Soft: proprietary or binaries beside the exe, and a game of this shape does not need a black box. miniaudio stays the device layer only, until the next tier's *Audio devices in Odin* removes it |
| Music codec | Ogg Vorbis, decoded at run time by our own Odin decoder (`common/ogg`, M53c; until then by miniaudio's own decoder, since M32c found `vendor:stb/vorbis` not built on source-built Odin and colliding with miniaudio's copy on macOS). Encoded only by the dev tool, with an external `oggenc` or `ffmpeg` found on the PATH; the encoded files are committed, so nobody else needs either |
| Music sources | Both a text score (`assets/music/*.score`, diff-friendly, what we write) and standard MIDI files (`.mid`, what a score editor exports) become one note list; `build music` renders either. Scores export to `.mid` so MuseScore can open them |
| Renderer | Our own SF2 reader and sample renderer in Odin (`tools/music`, no FluidSynth): presets, instruments, key and velocity zones, loops, volume envelope, pan, tuning, a low-pass filter; our own reverb (the engine's, see M32) on the render. The soundfont is not committed: downloaded and checked against a SHA-256 like glslang (`build/tools/`) |
| Piano | First: Upright Piano KW (FreePats; listed CC0 by the pages found, ~6 MB small build). Audition Salamander Grand (CC BY 3.0, a credit line) in M43; the tool takes any SF2. Before anything is committed, read the license on the download page itself (the research was second-hand) and write the sound's credit in `assets/music/CREDITS.txt`, shown by the game's credits screen |
| Style | Everything is clean: effects synthesized at 48 kHz in float (from M57; today's 16 kHz, 8-bit effects are replaced, not imitated), music and ambience clean 44.1/48 kHz stereo. The aim is sound that is good to hear again and again; the pixel look is the world's, not the sound's (owner, 2026-10-26) |
| Size | The release executable carries everything (`#load`): music budget 24 MB of Ogg (q5, ~0.8 MB a minute stereo). The packages stay one file |
| Output | Stereo. The mixer's internals take a channel layout so 5.1 can follow; the spatializer has a Speakers / Headphones setting |
| Latency and cost | Callback of about 10 ms (480 frames at 48 kHz); the mix of 64 real voices, 4 buses and the reverb stays under 5% of one core (a benchmark scenario holds it); the audio thread never allocates, locks or logs |
| Loudness | Everything is mastered to a target (music -20 LUFS integrated, effects measured per class); the master has a look-ahead limiter at -1 dBFS; a K-weighted meter (BS.1770) is in the engine for tests and the debug overlay |

### What the engine has (the feature list the milestones build)

- **Buses.** A tree: Master <- Music, Ambience, Effects (<- World, Player, UI). Per bus
  gain, mute, solo (debug), low-pass, send to the reverb, and **ducking**: a bus lowers
  others while it plays (side-chain), with attack and release. Snapshots: named sets of bus
  settings crossfaded in (Underwater, Paused menu, Death, Loading) the way FMOD does.
- **Voices.** 128 virtual voices, 64 real. A voice is a generational handle (ground rule 2)
  the game keeps to stop it, move it, change its parameters or fade it. Priority and
  audibility decide who is kept; a virtual voice keeps its place in time and resumes when
  it becomes audible again. Sample-accurate start times, loops with a loop point and a
  crossfade, fade in and out, per-voice low-pass, gains smoothed per block (no zipper
  noise), pitch with cubic resampling.
- **Sources.** Memory sounds (effects, mono or stereo, any rate) and **streams** (music,
  long ambience): a decoder thread fills ring buffers from the Ogg in memory; an underrun
  is counted, never silent.
- **DSP.** Biquad filters, delay lines, a feedback-delay-network reverb (8 lines, damping,
  early reflections, RT60 set live), a compressor and the limiter, all on buses or sends.
- **Events, not files.** The game says `event(.Block_Break, {material = .Stone})`; a
  table of event definitions says what plays: variations with no-repeat, pitch and gain
  ranges, the bus, priority, attenuation curve, cooldown and instance limit, and
  parameters (speed, material, intensity, depth) driving gain, pitch and filter by curves
  (FMOD's parameters). Dev builds reload the table while the game runs.
- **Spatial.** A listener with velocity and head; emitters as voices with positions;
  attenuation curves per class, Doppler, air absorption (distance dulls high
  frequencies); a head model for stereo (inter-aural delay, head shadow, an elevation
  cue), no third-party HRTF data.
- **Acoustics from the blocks** (what only this game can do): occlusion from a voxel ray
  from emitter to listener through the client's chunks (each block's material absorbs
  its own amount: wool a lot, glass little), an open path around corners found among a few
  extra rays; the reverb from rays cast around the listener (room size, how much of the
  sky is open, what the walls are), smoothed; underwater and in lava muffled by snapshots.
- **Music.** A director (states, silences, crossfades, stingers, tracks chosen by place,
  time and world) over the stream voices, plus music made of layers for later use.
- **Tools (M32, M32b).** Capture files and `build audiodump`, baselines and cost scenarios in CI, the freeze-and-solo inspector (see M32b); `build audio` renders a scenario to a WAV to listen to; `build music`
  renders scores; an in-game audio overlay (voices with their buses and priorities, bus
  meters and LUFS, the reverb's room, occlusion rays drawn as debug lines); a benchmark
  scenario for the mixer's cost.

## Scripting, packs and agents

### First principles

The engine is a replicated, deterministic simulation of a voxel field and its entities,
driven by data and scripts, in which every change has a cause and a history. It protects
five freedoms: **rules** (any mechanic is data and script, not an engine change), **world**
(scale, physics and generation are properties of a world), **content** (added without
code), **society** (one server process to many players, trust and an economy built in)
and **truth** (every change journaled: replay, rollback, audit, test).

### Threat model (what the script and agent surface must survive)

Untrusted: (1) generated scripts, buggy or hostile (a jailbroken or prompt-injected
agent); (2) player input, which reaches the agent as chat and behaviour ("give me
infinite diamonds" is an attack); (3) generated text and names (offensive or illegal
content); (4) the pack's transport (a forged pack). Defences, in layers, each built by
a milestone below:

- **A world is the unit of isolation.** A pack's content belongs to its universe (fixed while
  it runs) and its behaviour is enabled per world (M17's address); its scripts can touch only
  the worlds it is enabled in. The worst a script can do is ruin the worlds it is enabled in,
  which are reverted from the journal (M45).
- **Decoders that meet network data are Odin.** A pack's PNGs are read by `core:image/png`
  after a header check (M47b) and its Oggs by `common/ogg` (M53c): bounds-checked, with every
  size a constant, one allocation, an `Error` for anything malformed, fuzzed in the suite and
  from the command line. No C parses a hostile file.
- **Capabilities, not permissions.** A script has no ambient authority: its pack declares a
  manifest and the server grants it per world (edit blocks in a region, spawn N
  entities, give items from a budgeted faucet, show UI, send chat, read these events).
  Nothing else exists to call (M52).
- **Hard metering.** Per script, per tick and per second: instructions, memory, block
  edits, spawns, messages, events. Over budget suspends that script and logs it; the tick
  never stalls (M51, M52).
- **Economy containment.** Script-made items go through M31's ledger under their own reason
  with per-world caps and the script as their cause (M52); tagging the items themselves with
  their origin, and rules on where they may travel, wait for the economy's content wave (it
  changes stacks, merging and the inventory protocol).
- **Validation before anything runs:** static checks (capabilities used = declared,
  bounded loops, schemas), a headless dry run with bots measuring crashes, budgets, ledger
  balance and softlocks, moderation of generated text and of the images and sounds in packs,
  then a staged rollout (M54).
- **Signed packs.** The agent runs off-server; a server accepts only packs signed by
  a key it trusts (M54).
- **Journal and replay.** Every script effect carries its cause (M45); a bad script's
  changes are undone, and a bug replays deterministically (M38).
- **Telemetry is the agent's eyes** (M26-M27): it reads aggregate behaviour, not raw chat.
  The consent question (M27) is off by default: `telemetry.ask` (0) turns it back
  on, all its code is kept, and while it is off nothing is sent (unanswered = no). It stays
  off until it is redesigned.
- **Fuzzing from the first VM:** the VM, the packs' parsers and the protocol are fuzzed in
  CI from M51 on, not at the end: Q1-Q2's harness comes before M51a, and M51c's
  fuzzers register in it. Q5 moves this section into `docs/threat_model.md`, each threat
  mapped to its covers, and leaves a summary here.

### Decisions (locked)

| Area | Decision |
|---|---|
| Script language | Our own Lua-like language and VM in Odin (parser, bytecode compiler, register VM, incremental GC), close enough to Lua 5.4 that models write it well (tables, closures, metatables-lite, no `goto`, integer and float numbers, optional type annotations as in Luau). No C in the sandbox: memory-safe by construction, deterministic (no ambient clock, random, hash-order or I/O), metering built in, state serializable. `vendor:lua` is not used (its vendored builds lack macOS, and its C surface is what we avoid) |
| Live adaptation | No live director: agents author content (packs, quests, dialogue) between or beside play and never change the simulations' numbers (owner's decision, 2026-10-28). Kept possible, not built: script state is serializable (snapshot and restore) and packs are versioned and hot-swappable at a tick boundary, so a revision can arrive between visits or, later, during one |
| Scale | Minecraft's architecture: one server process per universe, worlds on their own threads, empty worlds asleep; the target is about 100 players per universe spread over worlds, benchmarked; scaling beyond is a later problem. No distributed universe now (the handoff protocol is not designed here) |
| Authoring surface | Mostly declarative data interpreted by the engine (quests, objectives, spawners, triggers, dialogue, loot: M53); scripts only for logic data cannot say. The engine API is small, typed, versioned, with machine-readable schemas and errors written for a model to act on |
| Content vs foundation | No gameplay decisions (survival, crafting, combat, economy numbers) are made in the foundation arc (M38-M39, M45-M55b). Anything that needs one waits for the content waves. No new gameplay mechanics, and no polish of existing ones (health and death, M28, stay as they are), before the foundation arc is done: gameplay is rewritten on the script VM and the declarative layer, so polishing it now is done twice Fixes from playtests to menus, comfort and defaults (M40) are not gameplay and are fine. |
| Hosting, payments | Out of the engine's scope: any service around agents or a future custom-experience platform (billing, credits if it has them, age gates, legal review) is separate. The engine provides pack signing, metering and the ledger hooks |
| Numbers (M38) | Three tiers, written in `docs/determinism.md`: **state** (server simulation, prediction, worldgen, light, rules, RNG) is bit-identical on every OS and optimization level; **replayable** (the audio mixer and its capture, client visuals) is bit-identical on one OS and optimization level, which is why the audio baselines keep a checksum per OS; **free** (rendering, UI, timing). State uses `base.sin`, `base.cos`, `base.exp` (ours), never `core:math`'s sin, cos, tan, pow, exp or fmuladd (LLVM intrinsics: each OS's libm, folded differently by `-o:speed`), and `base.Rng` (ours, xoshiro256**), never `core:math/rand` (ChaCha8, 1 KiB of state, its stream the toolchain's to change) |
| What determinism means (M38) | The simulation is a function of what reaches it at each tick boundary. A live server is not lockstep: inputs and chunk jobs arrive when they arrive. A stepped server (no thread, inline chunk jobs, inputs given per tick) is the reproducible form, used by tests and the cross-OS job now, and by replay and the journal later (M45). No map iteration order and no thread completion order reaches state or the wire |
| State model (M39) | Server-to-client state is **records** of typed **state kinds** (a value type, a key, a lane) and one-off **events**, encoded by one codec derived by reflection from the value types (field tags give string limits and the `acked` field), with a schema hash checked on joining. Two lanes: reliable records are deltas against the last value sent; snapshot records (motion) are deltas against the client's last acknowledged snapshot (a ring of 32). Values travel exactly (quantization waits for M50). The handshake, answers to one client's requests and the bulk chunk streams stay messages; client-to-server messages are not state |
| Authorship (owner's decision, 2026-10-27; clarified 2026-10-28) | Optionally, one agent authors a universe's shared experience (a universe without one is a complete game). New worlds behind gates are purely procedural (an address's parameters, and later worldgen graphs), not authored per world or per player |
| Packs per universe (2026-10-27) | A universe's packs are fixed while it runs. Its registry never grows at runtime, and packs aren't sent in the middle of a session. Joining sends every pack in the universe, cached by hash, whether or not the player visits the worlds that use it. Content is per universe, as M47 already says; a pack's *behaviour* is enabled per world |
| Pack sides (2026-10-27) | A pack has three folders. `assets/` is client-only: textures, sounds, music, later UI text. `data/` is for both sides: block and item definitions, tags, recipes, data rules. `server/` is server-only: scripts, quests, loot, worldgen graphs. The server sends `assets/` and `data/` only. Client scripts (M52c, 2026-10-30) live in `assets/scripts/`: client-only code, sent and hashed with the archive; server scripts in `server/scripts/`. The content check covers what both sides build from `data/`. A custom item's definition lives in `data/` (the client must show it); its scripted behaviour may live in `server/`. The base pack's files are laid out this way already |
| Prediction (2026-10-27; client scripts 2026-10-30) | Behaviour written as data rules is deterministic, runs on both sides, and is predicted. Prefer it. Server scripts can't be predicted, so use them only where a round trip's delay is acceptable (custom quests, item behaviour, AI, events). Client scripts (M52c) present (HUD, camera, input mapping, local effects) and never decide state: nothing a client script does is predicted state or reaches the simulation except as a message its server script validates |
| Neighbour rules are pack JSON (2026-10-30) | A neighbour rule (M49b) is a `sim_rule` entry in a pack's `data/sim/*.json`, beside M49's flow rules: the envelope (blocks, trigger, delay, wakes, the statement tree with `if` and `repeat` objects) is JSON, and each statement, condition and expression is a short string in a bounded statement language lexed by `common/game/sim_lexer.odin`, its errors `Pack_Error`s at the exact token. Rules reuse the registry, the pack hash, hot reload, packs over the wire and the pack fuzzing; no file format of their own. Ordered block lists are `sim_rule` entries too (`"list"`), and a flow rule is a list of its blocks, so no fact is written twice |
| Gameplay data is pack JSON (2026-10-30) | M53's declarative layer (regions, triggers, loot tables, pack rules, death causes; M53b's quests and dialogue; M53d's spawners and encounters) is registry kinds of pack JSON, one object of named definitions per file, as every other kind: triggers, regions, quests, loot, dialogue, spawners, encounters and pack rules in `server/<kind>/` (the server's alone), death causes in `data/death_causes/` (the client tells a death from them). Conditions and actions are short strings in M49b's statement language (`sim_lexer.odin`, plus a decimal literal and `~` for relative positions); those that carry text or a nested list are objects with one fixed key (`{"message": ...}`, `{"if": [...], "do": [...]}`). Why: the decision taken for neighbour rules (one format, the registry's ids, load order, overrides and errors, the pack hash, hot reload, Q1's pack fuzzing; no file format of its own) holds for the same reasons, and M54's validator and schemas then cover one format. Gameplay data is part of the stable API (M52e): the vocabulary is versioned with `api` |
| Worldgen as data (2026-10-27) | Worldgen in packs is graphs of native building blocks (density functions, noise, splines, carvers, placement). A pack only wires them together. Scripts never run per voxel |
| Scripts stay in the VM (2026-10-27) | Scripts are never transpiled or compiled to native code. When a script pattern is hot, the engine gains a reviewed native building block or function for it instead |
| Accounts and remotes (2026-10-27) | Identity and ownership (skins, owned things) come from a central source of truth: an auth service reached through *remotes* in `settings.cfg`. The default remote is `voxiverse.net`, with services at `auth.voxiverse.net` and `api.voxiverse.net` (the remote format allows other hosts). The website and service are closed source; the game sees only the API. As with Minecraft: singleplayer and LAN work offline with a local key. A server is either **online** (it requires a token signed by its remote's auth service) or **offline** (local keys, as today). Online becomes the default once it's built; until then servers are offline. The keypair of the glossary's Account stays as a device key an account vouches for when online. Built in "Auth client and online servers" (the next tier) |
| Third-party code in the game (owner's decision, 2026-10-28) | The game ships no third-party C or C++ except MoltenVK on macOS (Vulkan on Metal; revisit only if it causes trouble). Build-time tools (glslang, the music pipeline's `ffmpeg`, `7z` or `bsdtar`, the SoundFont) are fine, because their output is checked or committed and they are never shipped. Untrusted data (anything from packs or the network) is parsed only by Odin code: pack PNGs by `core:image/png` (M47b), pack Oggs by `common/ogg` (M53c). Why: it is the sandbox principle applied to decoders (C parsing a hostile file is the memory-unsafe surface the script VM already refuses), and it removes a C library to build, our reliance on Odin's `vendor/` folder for miniaudio (and the cross-check's placeholder library) and our lack of control over default-device and hot-plug behaviour. miniaudio is replaced in two steps: its decoder by M53c, its device layer by *Audio devices in Odin* (the next tier), which also removes `ensure_miniaudio` and `ensure_foreign_miniaudio` |
| Modes and death in M53 (owner's decision) | The hard-stop list is a hard stop in specs too. M53 builds the mechanism (death causes as data ids, the `player_died` trigger and its actions, the mode conditions and `mode_set`) and chooses no rules. Superseded in part by the owner's decision of 2026-10-28: the LAN party's survival rules, death messages and the death screen with its cause were decided then and built by M48f-M48g (modes per player as profiles of abilities with kits; the base modes are `voxiverse:creative` and `voxiverse:survival`, the base pack's namespace being `voxiverse`, not `base`). M53 keeps them exactly (every base death line byte for byte) and adds no rule, message or penalty; the death screen is M48g's and M53b builds none. Why: what you keep, where you wake and any penalty are the owner's design; a spec that fixes them lets a session build them |
| Pack media moderation (2026-10-27) | Images and sounds in packs go through a moderation hook before players see them, like generated text. M54h owns the hook; the service does the moderation |
| Before 1.0, no compatibility (2026-10-27) | Saves and the protocol carry no migrations and no compatibility. A new build may require a fresh world, and older clients must update. Specs drop their migration and compatibility work (a world of an older format is refused with a message). Existing migration code can stay until it is in the way |
| macOS port, one pass (2026-10-27) | The port is M47d (window, input, MoltenVK, renderer) and M47e (gamepads, audio, keep-awake, icon, `.app`), first in the order, each written once. Their exit check is `build check`, build and link on the macOS CI runner with the existing unit tests, and the `.app` as a CI artifact. No macOS-specific tests, offscreen game checks, screenshots or benchmarks; what only hardware shows is under "Check by hand" for occasional testers, and what they find becomes an issue then, with no sessions spent chasing behaviour nobody here can see. Unchanged: the loop's checks before a push, the weakened-test guard, CI on every push |
| The bedrock for players' experiences (owner's decisions, 2026-10-30) | Players make and share their own experiences; the engine builds the bedrock for it, in the order of the 2026-10-30 note. **Client scripts** (M52c): a pack may run scripts on the client for its own HUD, camera, input and local effects, in a VM per pack with capabilities and quotas like the server's; the server stays authoritative: a client script changes nothing the server owns, and reaches the server only through **script messaging** (M52d: typed channels between a pack's client and server scripts, rate-limited and validated at the edge like any other client message). The client-script design is part of M52's sandbox, written before M52 runs. **A UI toolkit creators can script** (M52f, M52g: HUD elements, menus, their own inventory views) on the client scripts, reusing the engine's own UI (`client/ui`), never a second UI system. **Moving block structures** (M50c, M50d): groups of blocks that move and collide as one body (doors, lifts, vehicles), scriptable, server-authoritative and replicated like entities; this is the motion bedrock, and there is no general rigid-body physics. **Creator tools** (M54c-M54f): a build/edit mode, test-play, scripts edited in the game, and a world packaged with its packs and scripts as one experience. **Engineering:** a versioned, stable script API with deprecation rules and compatibility tests that keep old experiences running (M52e; the one exception to *Before 1.0, no compatibility*: a script written for an API version keeps working while that version is supported), and hooks for later online services (M55c: an identity abstraction, starting and stopping servers headless; no online service is built). Sharing experiences beyond one server waits for online services |
| Everyone who plays may fire the launcher (2026-10-31) | `world.fire` is in the default role like `world.edit`: a joined player has the launcher as the host does (the start kit gives it by the same node). Open to LAN gives the node to an older world's default role when its permissions.cfg says nothing about it; a world that says `-world.fire` keeps its word. Why: the host's `*` hid that the default role lacked it, so guests on a LAN were refused with "You may not do that here (world.fire)". Other nodes the default role lacks (`world.summon`, `teleport.tp`, commands) are deliberate: those are the host's or the mod role's |
| The proof layer (owner's decisions, 2026-10-30) | Every claim about the engine is backed by evidence anyone can rerun (Q1-Q7). **Fuzzing:** one harness of our own in Odin (`base/fuzz`, `build fuzz`) for every parser of untrusted input, guided by outcome signatures, not edge coverage: Odin's compiler has no coverage instrumentation, and libFuzzer through LLVM IR would add C++ and clang to the build on Linux only; when Odin gains coverage instrumentation the harness adds it. A fixed seed on every push (a push never fails on a seed nobody has seen), the run number's seed for longer under AddressSanitizer every night (`nightly.yml`), every crash found a committed regression file the suite replays on the three OSes. **Crash reports:** a local bundle only (stacks of every thread, log tail, build, OS and GPU, last actions; no chat, names, keys, addresses or minidump), offered on the next start; uploading is the owner's open question. **Benchmarks:** our own numbers only, with the command that reproduces them; no comparisons with other engines (owner's answer); reports are written to `build/`, attached to each named release by CI from its runner, and no hardware of ours enters the repository or the docs. **Threat model and quality bar:** `docs/threat_model.md` and `docs/quality.md`, each line naming the test, fuzz target, lint or CI step that covers it, checked by a `check` lint; a threat whose milestone is done but still `planned` fails it. **Showcases:** experiences built only from packs and scripts, after the creator tools; the owner names each one and the plan invents none (Q6 holds the place) |
| Platforms (2026-10-27) | Follow [platforms.md](platforms.md): Tier 1 (blocks a release: CI builds it, runs the full tests and the game, packages ship) is Windows x86_64, Linux x86_64 and macOS arm64 (a target: it builds and packages in CI and is not tested on hardware by the project; port: M47d-M47e); Tier 2 (CI builds and runs the unit tests) is Linux arm64 and macOS x86_64 (its CI jobs are "Tier 2 CI" in the next tier); Tier 3 is best effort. The Tier 1 list is one constant in `tools/build` (`TIER1_TARGETS`), checked against that document by a test |
