# Design

How Voxiverse is built and why: the foundations, the rules every change follows, and the core
designs. A cheat sheet: it says what is true of the code. Terms are in
[glossary.md](glossary.md); the folders and their files in [layout.md](layout.md). The audio
engine is in [audio.md](audio.md); packs, the pack sandbox and the threat surface in
[packs.md](packs.md); the script language in [script.md](script.md); the save format in
[saves.md](saves.md); bit-identical state in [determinism.md](determinism.md); switches,
profilers and crash reading in [debugging.md](debugging.md).

## Foundations

| Area | Rule |
|---|---|
| Language and toolchain | Odin, pinned with odinup (`odinup.toml`). |
| Platform layer | One interface (`client/platform`) with native backends: Win32 (`core:sys/windows`), AppKit (`core:sys/darwin/Foundation`), Xlib (`vendor:x11/xlib`, which also serves Wayland sessions through XWayland). Gamepads on all three through our own backends (XInput, evdev, the GameController framework). No SDL, no GLFW. |
| GPU | Raw Vulkan 1.3 (dynamic rendering, synchronization2, bindless descriptors). The loader is opened at run time; nothing ships beside the executable. macOS runs on MoltenVK inside the `.app`. |
| Audio | Mixing, voices, buses, effects and the Ogg Vorbis decoder (`common/ogg`) are our Odin. miniaudio opens the output device and does nothing else (a lint keeps `vendor:miniaudio` to `client/audio/device.odin`). |
| Multiplayer | Authoritative server; the client/server boundary is the wire protocol even in singleplayer (in-process transport) and over UDP. |
| Third-party code | Odin `core:` first. The game ships no third-party C or C++ except MoltenVK on macOS and miniaudio's device layer. The UDP layer and the font rasterizer are our own. No `thirdparty/` directory. Build-time tools (glslang, `ffmpeg` or `oggenc`, `7z` or `bsdtar`, the SoundFont) are fine: their output is checked or committed and they never ship. Untrusted data (anything from packs or the network) is parsed only by Odin code, because a C parser on a hostile file is the memory-unsafe surface the script VM already refuses. |
| Assets | Generated by code: block textures, box models, sound effects, the window icon. Committed third-party files: JetBrains Mono (OFL, one weight) and Noto Sans Old Turkic (OFL, the symbol fallback font). Music is rendered offline from scores through a SoundFont that is downloaded, not committed; the rendered Ogg files and their credits are. The home world's relief (NOAA ETOPO, public domain), imported by `tools/planet`, is committed (`assets/planet`). |
| Tick rate | 30 Hz (`game.TICK_RATE`), one constant, announced by the server in Welcome. Smaller prediction corrections and smoother remote motion than 20 Hz, at negligible cost for a voxel game. |
| World height | Bounded: y -256..+256 (32 chunk layers), streamed as 16³ chunks. Sky light comes from a per-column top block; saves and build limits stay simple. |
| Light | 4-bit block light and 4-bit sky light per block, smooth lighting with ambient occlusion. |
| Movement | Minecraft-like baseline: a 0.6 x 1.8 block player, walk 4.317 blocks/s, jump height 1.25 blocks; every number is a field of `game.Rules`, so a console variable. |
| Shaders | GLSL compiled to SPIR-V by a pinned `glslangValidator`, provisioned by the build driver (see Tooling). |
| License | MIT. |
| Platforms | [platforms.md](platforms.md) defines the tiers. The Tier 1 list is `TIER1_TARGETS` in `tools/build/platforms.odin`, kept equal to that document by a test. |
| Imports | Code imports through collections, never a relative path: `client:gpu`, `server:core`, `common:game`, `common:base`, `common:limited`. A collection's root is its directory and no package sits at a root. The list is `COLLECTIONS` (in `common/limited`, shared with `tests/`); the driver passes it to every `odin` it runs, and `build.sh`, `build.bat` (the driver's own build) and `ols.json` (the editor) repeat it. `check` rejects any relative import, and a test keeps those three files in step with the list. `base` lives in `common/base` because Odin's own `base:` collection is `base:runtime`. |
| File layout | Feature packages under `client/` and `server/`; tests beside the code as `<file>_test.odin`, multi-package tests and fixtures in `tests/`; one folder per tool, shared code in `common/`; the folder is the noun (singular snake_case, no prefix repeating it, platform suffixes stay). [layout.md](layout.md) lists every folder and its file-name patterns, and `check` fails on a file that matches none, a folder not listed, a package over the file cap and an untracked file outside `build/` (all scratch lives in `build/`). A `package_lists` lint keeps `PACKAGES`, `TEST_PACKAGES` and `SOURCE_DIRS` (`tools/build/main.odin`) complete. The server's root package is `server/core` (the server state is one dependency cycle); the client's lowest package is `client/engine` (it holds `App` and the feature state), with the features in packages above it and the executable in `client/main`. |
| Arenas | `base` has no arena type: every lifetime's arena is `core:mem/virtual`'s `virtual.Arena`, and frame, tick and job scratch is `context.temp_allocator`, freed where ground rule 1 says. |
| Serial type checks | `build check` passes `-no-threaded-checker` to its host type checks and cross object builds (`CHECK_FLAGS` in `tools/build/main.odin`): the pinned compiler's threaded global checker sometimes ends a run with `Assertion Failure: g->groups[gi].done.load()` (`checker_global.cpp`), a race in the compiler, and a check that fails by chance is no check. Nothing is checked less and the jobs still run in parallel. |
| Line endings | Native (`* text=auto`: CRLF in a Windows checkout, which is what odinfmt writes there). Files a test or generator compares byte for byte are pinned to LF in `.gitattributes` (the Wireshark dissector, the audio baselines and the music director's `.decisions` file, the Ogg test digests); add any new one there rather than normalizing in code. |
| Low-fidelity science | Science is simplified and always behind "it must stay fun": planet classes, climate, ecology as population dynamics, genetics (`game/genetics.odin`) simulate the gist, never the detail; when realism and fun conflict, fun wins. |
| Permissions | A joined player has the `default` role: `world.edit`, `world.fire` (the launcher, like the host's), chat, travel and info nodes. `world.summon`, `teleport.tp` and commands belong to the host and the `mod` role. Opening a world to the LAN adds `world.fire` to an older world's `default` role when its `permissions.cfg` says nothing about it; a world that says `-world.fire` keeps its word. |

## Ground rules

1. **Lifetimes are structure.** Three tiers, each owning its memory and torn down in one place:
   - `App` (process): settings, platform, GPU device, UI, audio device.
   - `Session` (one world, client or server side): arena-backed; leaving a world frees the arena.
   - `Frame`/`Tick`: scratch arena reset every frame/tick, on every thread that uses one.

   Lower tiers may point into higher ones, never the reverse.
2. **Handles, not pointers or map values, for game objects.** Generational `u32` handles into
   pools (entities, chunks, GPU resources, audio voices). Maps only map keys to handles.
   UUIDs exist only in save files.
3. **Allocating procedures take `allocator := context.allocator, loc := #caller_location`.**
   Enforced in review; no implicit `context.allocator` in long-lived data.
4. **No mutable globals.** Constant tables only; no lazy-initialised globals (they race once
   the server runs on its own thread).
5. **Packages depend downward only** (see layout). A UI or renderer package never imports game
   code; game code never imports platform or GPU code.
6. **Untrusted input is validated at the edge.** Every decoded enum is range-checked, every
   length capped; handlers receive validated types only. Every parser of untrusted input has a
   fuzz target in `build fuzz` ([fuzzing.md](fuzzing.md)).
7. **Nothing fails silently.** No silent truncation or dropped work; Vulkan validation on in
   debug and routed to the real logger; asserts on invariants.
8. **One source of truth per fact.** Physics, block rules and RNG live once in shared code;
   the server decides, the client predicts and reconciles.

## Core designs

### Main loop
`App` owns platform, GPU, UI, audio. A `Session` exists only inside a world. Each frame:
poll events, map them to actions, run fixed ticks, build the UI, let each pass record its draws
from the session and the UI, render. The tick accumulator is added to once per frame and capped
at four ticks: a long hitch is not caught up on. The tick rate is announced by the server in the
handshake and checked by the client.

### World data
- Chunks are 16³ with `u16` block ids. In memory a chunk is one block (all air, all stone: most
  chunks) or a flat array taken from a region reserved for the session's maximum, so memory has
  a hard ceiling; on the wire and on disk a chunk is palette + runs. Light is not stored.
- One chunk pool plus a coordinate-to-handle map. The server's chunks are `Generating` or
  `Ready`; the client marks a chunk dirty when its mesh no longer matches its blocks.
- Generation, lighting and meshing run as jobs on worker threads, on immutable padded
  snapshots (18³ for meshing), never on live data.
- Lighting is a pure function in `game/`: a chunk's sky and block light, computed whole from
  its 3x3x3 neighbourhood and the column heights (light travels at most 15 blocks, so that is
  all it depends on), inside the mesh job. With no stored light there is no removal pass and
  nothing to go stale: an edit re-meshes the chunks within 15 blocks. The server sends column
  heights (`Column`), because the client cannot see above what it has loaded.
- Interest is a cylinder around each player's chunk (radius and height announced in Welcome),
  sent nearest column first. The client drops chunks one past it and the server frees them two
  past it (`CLIENT_DROP_MARGIN`, `SERVER_UNLOAD_MARGIN`), so crossing a chunk border back and
  forth sends nothing again. Both sides size their storage from it once, at join.
- Every block change goes through the edit journal ([journal.md](journal.md)).

### Authority and netcode
- The client sends tick-stamped input commands; the server simulates every player with the
  shared physics and sends state; the client predicts its own player and reconciles. The server
  queues inputs per player with a bounded depth and a per-tick budget (`INPUT_QUEUE_MAX`,
  `INPUT_BUDGET_MAX` in `game/prediction.odin`), so a client cannot run faster than the server
  ticks.
- Block edits and attacks are requests: predicted locally, confirmed or rolled back by the
  server. Each names the input it follows, and the server applies it right after that input, so
  reach is judged from the same position however late it arrives.
- The transport is an interface with two implementations. In process, the server runs on its own
  thread and talks to the client through queues (`game.Pipe`); singleplayer keeps a separate
  client replica on purpose, so authority stays honest. Over the network, `common/netcode` is
  our reliability layer on UDP: acknowledgement bits, reliable ordered messages with
  fragmentation, unreliable latest-wins messages, a byte-rate limit.
- The protocol has a version handshake (`Hello` carries the protocol and the schema hash;
  `Welcome` carries the protocol, tick rate, rules, interest area, registry hash and pack list),
  validated decoding (with Steam, `Hello` also carries the SteamID and an auth ticket, which a
  server with Steam checks and links to the account: [server.md](server.md)), and palette + RLE chunk encoding. A client joining a server fetches the
  packs it lacks ([packs.md](packs.md)).
- Players join with an account (a keypair the client makes; the server issues a `Challenge`
  and the client answers with a `Proof`) and choose a character.

### State replication
Server-to-client state is **records** of typed **state kinds** (a value type, a key, a lane;
`game/state_kinds.odin`) and one-off **events**, encoded by one codec derived by reflection
from the value types (field tags give string limits and the `acked` field). Adding a replicated
value is a struct, an entry in the table and the code that puts it; the codec, the Wireshark
dissector's table (`build schema`) and the wire tests follow from the types.
- Two lanes: reliable records are deltas against the last value sent; snapshot records (motion)
  are deltas against the newest snapshot the client acknowledged (`SNAPSHOT_RING` = 32 kept
  baselines, sent as at most 8 unreliable packets).
- Keyed kinds are rebuilt every tick: what the server does not put is removed. Values travel
  exactly (no quantization).
- The schema hash is checked when a client joins. The handshake, answers to one client's
  requests and the bulk chunk streams stay plain messages; client-to-server messages are not
  state.
- Remote entities and players are drawn `INTERPOLATION_TICKS` (3) behind the newest update,
  interpolated, not predicted.

### Renderer
- Chunk meshes are sub-allocated in one device-local buffer and uploaded per chunk through
  per-frame staging (no whole-world rebuild); textures and meshes are used by handle.
  Positions are relative to the camera's chunk; the projection is reverse-Z and infinite.
  Meshing merges quads greedily when all four corners are alike (ambient occlusion, light,
  texture), so the result is pixel-identical to one quad per face; water is not merged.
- Per frame: a scene buffer (camera, sun, sky, fog, clouds; read by address in the shaders,
  laid out as `assets/shaders/scene.glsl`) and each pass's own per-frame-in-flight buffers
  (entity boxes and particles, debug lines, UI vertices).
- Swapchain recreation touches only the swapchain and size-dependent images.

### UI
- Immediate mode, one hashed id system with an id stack.
- Hover, keyboard focus and active are separate states; clicks fire on release over the same
  widget.
- Layers (`Base`, `Popup`, `Modal`, `Keyboard`, `Tooltip`) decide input priority and draw
  order; while anything is drawn on `Modal`, lower layers are inert.
- Per-command scissor clipping; a layout cursor (rows/columns) instead of hand-placed rects.
- Input is a generic event stream (keys, text, pointer, and navigation events from a pad or the
  keyboard: up, down, left, right, confirm, back, secondary, tertiary, start), not game
  actions.
- Output is vertices + texture ids; the renderer draws them.
- One look (the `Theme`), no player-chosen themes; a call site overrides it for the widgets it
  draws with a scoped `theme_scope` (colours, metrics, an `opacity` for everything inside).
  A lint rejects `ui.Color{` literals and English string literals in widget calls in the
  feature layers (colours come from the theme, text from `tr(key)`).

### Input
Platform events (keyboard, mouse, gamepads) go through the action map (rebindable, per context:
in the world, in a menu) to a per-tick input command. Analog values (sticks, triggers) are
actions too. Text input is a separate event stream for UI and console.

### Console and variables
Not a global registry (Quake's cvars, Call of Duty's dvars): every tunable value is a field
of a typed struct with one owner, described once in a table (`base.Var_Table`: name, type,
range, default, help) that the console, the tuning panel and save files all use. Code reads
plain fields.

| Kind | Examples | Owner | Saved | Changed by |
|---|---|---|---|---|
| Client settings | sensitivity, FOV, UI scale, view distance, volume | App | settings file | the user; never sent |
| Game rules (`game.Rules`) | gravity, speeds, jump, reach, flying | server session | world save | the server only; sent in Welcome and as the `Rules` state kind so prediction uses them |
| Debug switches | chunk borders, net trace, simulated latency | the side they affect | no | console, dev builds |

Singleplayer changes rules by sending a command message to its own server, never by writing
server memory. A value becomes a variable only when someone tunes it; design decisions
(tick rate, chunk size, protocol limits) stay constants. Dev-only commands exist only in dev
builds (`base.DEV`); cheats are gated by the server's permissions.

### From Quake 3: kept and dropped
Kept: authoritative server, client prediction of its own movement from tick-numbered input
commands, one movement code path for both sides, a local server for singleplayer, fixed
server tick, interpolated (not predicted) remote entities, console + config scripts.
Dropped: global string cvars (see above); everything-on-unreliable-snapshots (chunks and
edits need a reliable ordered stream; entities get snapshots); client-reported frame times
in commands (speed hacks; inputs are tied to server ticks and capped); sending every entity
to everyone (interest management); QVM; lag compensation.

### Assets
Generated by code at startup, deterministic on every machine: block textures (procedural, one
generator per texture, `client/mesh/textures.odin`), sound effects (synthesized, `client/sfx`;
`build sfx` writes them out to listen to), the font atlas (JetBrains Mono, rasterized by our
own `font/` as glyphs are needed). Shaders are the one build-time asset (SPIR-V, hot reloaded
in dev builds). Music is committed as Ogg ([audio.md](audio.md)).

### Tooling
Setting up a fresh machine is: install odinup, then run `build`. Nothing else.

- The build driver is an Odin program (`tools/build`); `build.sh` / `build.bat` only hand off
  to it. `./build.sh help` lists the commands.
- **Shader compiler, zero setup.** On first use the driver downloads the pinned official
  glslang release for the host OS (Khronos GitHub release, Windows x64 / Linux x86_64 / macOS
  universal) with the `curl` and `tar` every supported OS ships, verifies its SHA-256 against
  hashes committed in the repo, and unpacks it into `build/tools/`. Everyone compiles with
  the same version; bumping it is a version constant plus three hashes. For unusual hosts
  (e.g. Linux arm64) `GLSLANG=/path/to/glslangValidator` overrides it. Compile errors
  point at the GLSL file and line.
- **The inner loop is parallel and clean.** `check` runs the host's type checks and the other
  targets' object builds in one pool, one job per core (`VX_JOBS=n` overrides); `test` runs the
  packages the same way, the slowest last time first, each printing its output whole when it ends;
  `test <package>...` runs only those. Builds and tests execute directly in parallel without
  intermediate compiler cache state: builds stay fast, reproducible, and deterministic, eliminating
  state invalidation and stale cache artifacts. A test that loops over independent cases that each take
  seconds (the music, the audio scenarios, seeking in each file) is one test per case, so the runner's
  threads share them; an `#assert` on the count says when a case lacks its test.
- **CI uses exactly the same path.** Its Linux checks are three parallel
  jobs, "Test · Linux x64" (check, tests, determinism, the system test suite, the fuzz regression run),
  "Game · Linux x64" (the scenario checks: benchmarks, fuzz, flight, culling, audio,
  multiplayer, crash handler, printers) and "Game · Linux x64, images" (AddressSanitizer,
  profiling, screens, sky and held items); macOS and Windows run one job each. CI sets
  `VX_CI=1`, which makes `check` skip its cross-target object builds (every Tier 1
  target compiles natively in its own job); locally they run. A tool's executable (`bench`) is
  built once per job. Every check runs on every push. The tests run once, with
  `ODIN_TEST_RANDOM_SEED` set to the run number (a re-run repeats it). `./build.sh test` turns
  `ODIN_TEST_RANDOM_SEED`, `ODIN_TEST_THREADS` and `ODIN_TEST_NAMES` from the environment into
  `-define:` flags (Odin reads them only as defines), so `ODIN_TEST_RANDOM_SEED=n ./build.sh
  test` reproduces a CI failure; `-test-name:<name>` sets `ODIN_TEST_NAMES` for the named
  packages (see [debugging.md](debugging.md#switches)). Ubuntu packages come from a cache of their `.deb` files
  (`.github/actions/apt`).
- **Test memory.** A test's big values go on the heap (`new`, `defer free`): the runner's
  threads have the platform's default stack, 512 KB on macOS against Linux's 8 MB, and a test
  that overflows it dies with a silent exit and no message. On Linux `./build.sh test` runs each
  test executable with its stack limit at 512 KiB (set after the build, for the run only), so an
  overflow fails here as it does on macOS. Code under test follows the same
  rule: `s^ = {...}` builds the whole literal on the stack before copying, so a large struct
  (`Session`, 214 KB) is assigned `s^ = {}` and then its fields, and `for &p in h.peers` loops
  by reference rather than copying a 64 KB `Peer` per step. `ulimit -s 160 ./build.sh test
  client/main` reproduces a stack too small on Linux. Every `odin test` also gets
  `-define:ODIN_TEST_FAIL_ON_BAD_MEMORY=true` (tracking stays on): a test that leaks or frees
  badly fails, naming the allocation's line. Ownership is the caller's where a procedure returns
  text or errors (`registry_build`'s errors: `pack_errors_destroy`; `registry_id_changes`'
  text: `delete`); a thread started with `thread.create_and_start_with_poly_data` is given
  `context`, so what it allocates is freed by the owner under the same allocator.
- **Test files.** A test package's binary, log and timing file are named by its whole path
  (`build/test/client-music`, `tools-music`; the cross objects of `check` too): by the last
  element alone `client/music` and `tools/music` would share a file, so one starts the binary
  while the other still writes it (`Text file busy`). `test_test_packages_keep_their_own_files`
  keeps names unique.
- **No test asserts a time.** A performance budget is a scenario of `build bench` (`chunks`,
  `telemetry`, `budgets`, `script`, and the game's `viewmodel` and `audio`) with its limits
  beside it in code, gated by CI's "Benchmark check" steps in a release-like build; a test calls
  the same scene for what it does (`server/core/budgets.odin`: a save that commits, 10 000
  blocks flowing, an audit with no lines). A budget is read from `base.thread_cpu_us` (the
  thread's CPU time), not a wall clock: a core taken from the measured thread is not the work's
  cost. On Windows it is the thread's cycle count over a rate calibrated against the wall
  clock, because `GetThreadTimes` advances once per 15.6 ms scheduler tick. Where the work is
  big and the runner's speed is the unknown, the budget is a multiple of a reference the scene
  measures on the same thread in the same run (`Counters_Ratio`: save and load at most 6 times
  what building the counters cost, which measures at 2 to 3), because a fixed limit fails on a
  slow runner.
- **A panic must fail a test, never hang it.** The Odin test runner's signal handler
  (`stop_test_callback`) returns without doing anything on a thread the runner did not start;
  the trap then runs again, for ever, at full CPU. A thread a test starts (the server, job
  workers, the telemetry writer, the collector, audio threads) that copied the test's context
  would inherit the runner's `assertion_failure_proc` and spin. Every thread we start gets
  `base.thread_context()` instead: under `odin test` its failed assert or panic prints and ends
  the process (exit 2), so the run fails in seconds. A new thread-starting site must use it.
  Second layer: `./build.sh test` runs each package under a limit (ten times its last passing
  run, at least ten minutes; `VX_TEST_TIMEOUT_SECONDS` overrides it), kills the run with its
  children when it is over and reports `test <package> FAILED: still running`.
  `test_panic_in_a_server_thread_fails_fast` (`tests/`, with the `tests/panic_fixture` package,
  not in `TEST_PACKAGES`) panics on purpose in a worker with a server running and expects a
  failure well inside the limit; `test_run_limited_kills_the_tree` covers the kill.

### Saves
Region files of chunk columns, palette + RLE per chunk, versioned, written only by the server.
[saves.md](saves.md) has the layout, the transaction and the formats.
