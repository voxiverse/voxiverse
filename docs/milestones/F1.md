# F1: client/main fails on macOS CI with no cause shown (issues #104, #105)

Owner's priority: first among the open rows, because it keeps main red.

## What happened

`Test - macOS arm64` failed `client/main` twice running (runs 41388516407 and
41390538806), passing on a re-run, with no error line in the report. `build.sh` printed the
head of `build/test/main.log`, which is only start-up lines (runner start, input pad
connect/disconnect); the suite runs about a minute, so any `[ERROR]` line came later and was
not shown. The test binary's name no longer collides with another package's (#101: every
package's binary and log are named by its whole path, `build/test/client-main.log`).

## Part one (done)

- `failure_excerpt` (tools/build/main.odin): a failed package's report leads with `first
  error line:`, then every cause line (`[ERROR]`, panics, assertions, signals; up to 40),
  then the log's last 15 lines. A log with no cause line says `NO ERROR LINE`, with the exit
  status (on POSIX a kill is its signal number: 6, 9, 11) or that it was killed at its limit.
- `limited.Job.status` carries the exit status out of `run_parallel`.
- CI uploads `build/test/*.log` as the `test-logs-<os>` artifact when a Test step fails.

Not reproduced on Linux: `ODIN_TEST_RANDOM_SEED=20995611411 ODIN_TEST_THREADS=3
./build.sh test client/main` passed under six busy loops, and six further plain runs of the
binary passed.

## Part two (open)

1. Take the cause from the next macOS failure's report (or its `test-logs-macOS` artifact).
   Decision: no fix is guessed from a log that has no cause in it; the failure is shown first.
2. Fix it at the root: no retry, no skip, no loosened bound.
3. A test pins the cause (it fails without the fix).

## Exit check

The cause is named in the commit; `./build.sh check` and `./build.sh test` pass.

## Notes from the first part-two attempt (no macOS log with the report exists yet)

The runs since the report was added (b1fed88 and later) were cancelled by newer pushes, and
the two failed runs predate the report, so no cause line has been seen. What was learned on
Linux: both failed macOS runs died about three seconds after `client/main` started, with only
start-up lines in the log and nothing after, which fits a crash with no message (a stack
overflow, as in the earlier fixes fc51fdc and 893d26f for macOS's 512 KB test-thread stack).
Test: `ulimit -s N` sets the test threads' stack on Linux. The 109 tests pass at N=320 with
3 threads and fail with SIGSEGV at 256, so Linux has little headroom over macOS's 512 KB
(arm64 frames and the debug build differ). If the next report shows a signal 10 or 11, look
for large locals in the `client/main` tests first and put them on the heap; a test that runs
the package's binary under `ulimit -s 400` would pin the fix. Still open: take the cause from
the first report.
