# M47e: macOS: MoltenVK, the Vulkan surface and the renderer

**Read first:** M1b in plan.md (the spike this replaces), `client/gpu/gpu.odin` (instance,
device choice, the features it asks for), `client/gpu/swapchain.odin`,
`client/platform/platform_darwin.odin` (`VULKAN_LOADER`, the three `native_vulkan_*` stubs),
`tools/build/glslang.odin` (the pattern for a pinned download with checksums), M47d (the
window and its `CAMetalLayer` view) and docs/platforms.md.

**Why.** The renderer is raw Vulkan 1.3 style (dynamic rendering, synchronization2,
bindless descriptors, buffers read by address). On a Mac that runs through MoltenVK, a
translation layer onto Metal. M1b was to find out whether MoltenVK covers what we use;
nobody has a Mac to run it, so this milestone finds out in CI and writes the answer down.

**Design.**

- **MoltenVK is a pinned download.** `tools/build/moltenvk.odin`, like `glslang.odin`: the
  release's URL, its SHA-256 (committed), unpacked into `build/tools/moltenvk/` with the
  `curl` and `tar` macOS ships; `build` and `package` call it on macOS only; CI caches it by
  the file's hash. The release must report Vulkan 1.3; if the newest release does not, the
  pin is the newest and step 2 below says what that costs. One universal `libMoltenVK.dylib`
  serves arm64 and x86_64.
- **No Vulkan loader.** `VULKAN_LOADER` becomes the path of `libMoltenVK.dylib` found, in
  order, at `<exe dir>/../Frameworks/` (inside the `.app`, M47g), `<exe dir>/` and
  `build/tools/moltenvk/` (development); the runtime opens it with `dynlib` and takes
  `vkGetInstanceProcAddr` from it, as the Windows and Linux paths take it from their loader.
  Nothing is installed on the player's Mac; nothing needs an ICD file or an environment
  variable. A missing library is `the Vulkan driver (MoltenVK) was not found next to the
  game; reinstall`.
- **Surface.** Instance extensions `VK_KHR_surface`, `VK_EXT_metal_surface`,
  `VK_KHR_get_physical_device_properties2`; `native_vulkan_create_surface` calls
  `vkCreateMetalSurfaceEXT` with the view's `CAMetalLayer` (M47d). The layer's drawable size
  follows `Resize_Event` pixels; `displaySyncEnabled` follows the vsync setting, with the
  present modes MoltenVK offers mapped as the other platforms' are.
- **Portability.** The device extension `VK_KHR_portability_subset` is enabled when the
  device lists it (Vulkan requires it); the features it removes are read from
  `VkPhysicalDevicePortabilitySubsetFeaturesKHR` and checked against what the renderer
  needs, so a gap is named, not a crash.
- **Feature probe.** `gpu.probe(g) -> []Missing` lists every feature and limit the renderer
  uses (dynamic rendering, synchronization2, descriptor indexing: runtime arrays,
  non-uniform indexing, update-after-bind, partially bound, enough sampled-image descriptors
  for the bindless table; buffer device address; shader draw parameters; `fillModeNonSolid`
  for debug lines; the texture formats and the 2D array size the block atlas uses) with the
  device's answer. `voxiverse --probe-gpu` prints it as JSON lines on every OS and exits 0
  when nothing is missing, 1 otherwise. The renderer's own init uses the same list, so the
  two cannot disagree.
- **If something is missing.** The first step ends with the probe's output from the CI
  runner, committed in the milestone's report. A missing feature has one of three
  outcomes, in this order: (a) MoltenVK has it behind a setting (for example Metal argument
  buffers: `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS`, set through the environment variable of
  the same name by the platform layer before the first Vulkan call); (b) the renderer has
  an equivalent for one path: if buffer device address is the gap, scene and pass buffers
  are read as bindless storage buffers on macOS (a `when`-free capability flag in `gpu/`,
  `g.caps.buffer_address`, and one GLSL variant chosen at pipeline creation; no second
  renderer); (c) a gap with neither is the milestone's finding: it is written in plan.md
  as an open row (what is missing, what MoltenVK release adds it) and the exit check below
  is met with the probe reporting it by name. The decision is the session's, in that order.
- **Shaders and quirks.** The SPIR-V the build makes is what MoltenVK translates (SPIRV-Cross
  to MSL). Known to need care, to check in the first run: reverse-Z with an infinite
  projection (depth range 0..1: Metal's), `gl_VertexIndex` base, the push-constant size
  limit, and point/line sizes of the debug lines.

**The order of the steps:** (1) the pinned download, the loader path and the probe command,
and CI's probe step with its output saved; (2) read the probe and settle the gaps as above;
(3) the surface, the swapchain, a clear and the M1 triangle through `--check triangle` (an
exit check that renders one frame offscreen and compares pixels, written here for every OS if
it does not exist); (4) the renderer's own pipelines created on MoltenVK (a pipeline-creation
pass over every shader, which needs a device and no window); (5) the game to a world and a
screenshot (the `Game` steps of M47h).

**CI and what the runner can do.** A hosted macOS runner may have no Metal device (the arm64
images are virtual machines; whether they expose one is not known and is found out here).
The macOS job therefore starts with `voxiverse --probe-gpu --json`; its answer sets a job
output `gpu`, and every step that needs a device is `if: steps.probe.outputs.gpu == 'yes'`.
A runner with no device makes the skipped steps loud: a `::warning::` annotation names them and
the job summary lists them, so a green job is never read as "the game ran". Everything
below that needs no device runs either way.

**Left out:** other present-time features (HDR, ProMotion tuning), Metal-specific
optimizations, the macOS timing queries (GPU timestamps are used if the device has them and
skipped otherwise), a native Metal renderer (never; MoltenVK is the decision), MoltenVK
configuration screens.

**Tests:**

- `tools/build`: the MoltenVK pin's checksum is a 64-hex string and the URL names the
  version; the unpack finds `libMoltenVK.dylib` (a fake archive, built by the test).
- `client/platform`: `test_vulkan_loader_search` (a temp directory with and without the
  library, in each of the three places, picks the first and reports the missing message);
  `test_vulkan_extensions_mac` (the list is the five names above).
- `client/gpu`: `test_probe_lists_what_the_renderer_uses` (the probe's list and the
  features `init_device` enables are one table: a feature added to one and not the other
  fails); `test_probe_report_json` (a fake device answer with two missing features prints
  both and exits 1; none prints nothing and exits 0). These run on every OS.
- With a device (every OS that has one, so the Linux "Game" job on lavapipe too): `--check
  triangle` passes, and the pipeline-creation pass creates every pipeline with no
  validation message. On macOS the validation layer is not present on the runner; the
  check relies on `VK_LAYER` being absent and logs it.

**Exit check:** the tests above pass; on the CI runner `--probe-gpu` either reports nothing
missing and `--check triangle` passes, or reports exactly the gaps the report lists and the
plan.md row for them exists; the other jobs are unaffected; the suite and the `build check`
cross-compile pass locally.

**Check by hand** (a tester with a Mac): run `voxiverse --probe-gpu` and send the output;
start the game from a CI build and get to the title screen, then a singleplayer world: the
picture is the same as on the other OSes (the block textures are crunchy, not blurred; the
sky and clouds draw; no flicker at the chunk borders); resizing the window and entering full
screen keep the picture; the log has no `vulkan:` error lines (`grep -i vulkan voxiverse.log`).
