# M47h: macOS: the game's checks in CI, and Tier 1

**Read first:** `.github/workflows/ci.yml` (the "Game · Linux x64" job: every step that runs
the game), M47e's "CI and what the runner can do" (the probe and the `gpu` output),
docs/platforms.md (the Tier 1 promise and the macOS rows).

**Why.** Tier 1 means "CI runs the game". Linux does it under xvfb on a software Vulkan
driver. macOS arm64 gets the same steps, offscreen where the runner allows it, so that a
change that breaks the Mac build is found by CI and not by a tester. The runners are
what they are: this milestone writes the job so that it runs everything a device allows,
says loudly what it could not, and then updates the documents to say what is now true.

**Design.**

- **A job "Game · macOS arm64"** on `macos-latest`, next to "Test · macOS arm64" (which stays:
  check, tests, determinism, build, benchmarks). It builds the game (`build build`), then
  `voxiverse --probe-gpu --json` (M47e) as step `probe`, whose output sets `gpu` to `yes` or
  `no`. The two outcomes:
  - `gpu == yes`: the steps of the Linux "Game" job that need only the game, with the
    macOS differences below: `--check` flights and the tour, the gamepad flight (the `pad`
    console command's virtual pad, no hardware), the blast test, the biome tour, the
    benchmark scenarios (smoke), the audio smoke run (`--check audio`, the file device, no
    speakers needed), the screens, the sky, the multiplayer step (the Wireshark/tshark parts
    are Linux's and are skipped), the screenshots uploaded as an artifact. Each step is the
    same command line as Linux's with `xvfb-run -a` removed (the runner has a window
    server) and the Linux-only checks left out (AddressSanitizer on macOS arm64 is
    attempted once with `-sanitize:address`: if Odin's ASan does not work on darwin the
    step is dropped with a comment saying why, not left failing; the crash handler check
    uses the macOS crash path, `base/crash_posix.odin`; the lldb printers are
    `tools/debugger`'s macOS side (`use_lldb` in `tools/build/main.odin`) and run if lldb is
    on the runner).
  - `gpu == no`: those steps are skipped with a `::warning::` per step and a list in the
    job summary ("no Metal device on this runner: these checks were not run"), and the job
    still runs what needs no device: the game's `--help` and `--version`, `voxiverse-server
    --smoke`, `build audio`, the server benchmark smoke, the pipeline/SPIR-V checks that
    only parse, and M47d/M47f's tests (already in the Test job). The result is green with the
    warning, never green without it.
- **No device means no game run.** The game has no mode that starts without a GPU (no
  `--no-gpu` exists on any OS, and none is added here: it would test a path players never
  take). If the runner has no device, the report says so and the by-hand list carries the
  game run; the window, input, audio and server paths are still covered by M47d and M47f's
  tests and the server steps above.
- **The runner's answer is recorded.** The first green run's `probe` output is pasted in the
  commit message and in docs/platforms.md ("CI's macOS runner has/has no Metal device"), so
  the document says what CI can and cannot do on the Mac.
- **Tier 1 audit.** A test in `tools/build` (`test_platforms_ci_claims`) reads
  `.github/workflows/ci.yml` and `docs/platforms.md` and checks that every job name the
  document lists under "What CI does today" for a Tier 1 target exists in the workflow
  (`Test · macOS arm64`, `Game · macOS arm64`, `Package · macOS arm64`, ...), so the
  document cannot claim a job that was deleted.
- **The documents.** `docs/platforms.md`: the macOS arm64 row moves from "port in progress" to
  "supported" (or "supported; the game run in CI is limited because the runner has no GPU",
  whichever the probe said), the "What is missing" cell is rewritten to what is true, the
  Tier 1 note about the port is removed once the package job and the game job are both
  green; `README.md`'s status line and Download section say Windows, Linux and macOS;
  plan.md's "Platform" and "GPU" decision rows lose "(verify feature coverage early)" and
  M1b's row gets "(done by M47d-M47h)"; the release notes' "macOS: not yet" line was
  changed by M47g.

**The order of the steps:** the job with the probe and the gated steps (copying the Linux
steps); run it, read what the Mac does differently from Linux (the screenshots, the
flights' budgets: the frame-time budgets of the checks are per-OS values today? if a check
has one threshold for Linux's CPU Vulkan, the macOS thresholds are set from the first
runs, with the same margin policy as the others); the Tier 1 audit test; the documents.

**Left out:** a self-hosted Mac runner (no Mac), cross-OS screenshot comparison (rendering
is "free" in determinism.md's tiers: pictures differ by driver), notarization (M47g),
Metal GPU captures, performance work on MoltenVK.

**Tests:** the CI job is the integration test; `test_platforms_ci_claims` (above) and
`test_platforms_doc_matches` pass locally.

**Exit check:** the "Game · macOS arm64" job is green on the commit's push with either every
step run or each skipped step warned and listed; `test_platforms_ci_claims` passes; the
documents say what the probe found; the suite and `build check` pass locally.

**Check by hand:** this is where the Mac checks of M47d to M47g are collected for one tester
session (about thirty minutes): run the CI build's game on a Mac; get to a world; walk, build,
look at the sky and the clouds; try the Options screens and a gamepad; join a LAN game from
the Linux or Windows build and back; quit; send `voxiverse.log` and the output of
`voxiverse --probe-gpu`. The tester's report becomes issues in the loop repository.
