# M48b: doors, fences and block entities

**Why.** M48's blocks are static. Two more kinds complete "block states and shapes":
blocks whose state follows their neighbours or spans two cells (fences, doors), and
blocks with data of their own beyond a state (M30's chest, kept today as a per-world
`containers.cfg` map by position, made on first open and found gone by a sweep).

**Design.**

*Neighbour updates.* A type with `"connect": {"to": "<block tag>"}` (fences) has four bool
properties `north`, `east`, `south`, `west` (checked at load), set from its neighbours: a
side is `true` when the neighbour on that side is in the tag or has a full render cover
on the face toward it. `shape_update(reg, b, pos, q) -> Block` (shared, `common/game/placement.odin`)
gives the state the neighbours call for; `placement` uses it for the placed state, and
`set_block` (M45's pipeline) re-evaluates the four horizontal neighbours of every changed
cell, writing any that change with the same cause. Bulk edits run it over the box grown
by one. The client applies the same to its predicted edits; the server's `Block` records
correct anything else.

*Fences.* Base pack: `voxiverse:planks_fence` in `blocks/fences.json`, tag
`voxiverse:fences`; shape `fence` in `shapes/fences.json`: post `[6, 0, 6, 10, 16, 10]`,
`cases` per side adding the two rails (north: `[7, 12, 0, 9, 15, 6]` and `[7, 6, 0, 9, 9,
6]`, the other sides by the same boxes turned); collision `fence_collision`: post `[6, 0,
6, 10, 24, 10]` and per side `[6, 0, 0, 10, 24, 6]` turned (a player cannot jump a
fence: 1.5 blocks); selection as the render shape; `"place": "connect"` (the default
state with `shape_update` applied).

*Doors.* Base pack: `voxiverse:planks_door` (`blocks/doors.json`; states `facing` four,
`half` `["lower", "upper"]`, `open` bool: 16 states; generated textures `door_lower`,
`door_upper`: planks with a frame and, on the upper half, a window).

- Shape `door`: closed, a plate along the north edge `[0, 0, 0, 16, 16, 3]`; `cases`
  `{"open": "true"}` replace it (a new `"replace": true` on a case: its boxes instead of
  the base boxes) with the plate along the west edge `[0, 0, 0, 3, 16, 16]` (the hinge in
  the north-west corner); rotated by facing. Collision, selection and render alike.
- `"place": "door"`: facing as stairs'; `pos = target + normal` must be replaceable and so
  must the cell above it, and the cell below must give a full top face. The rule returns
  the lower half at `pos` and the upper half at `pos + up` (`placement` returns up to two
  cells: `Placed {cells: [2]{pos, b}, count}`). An `Edit` names the lower half; the
  server checks and writes both through the pipeline as one change with one cause.
- **Companions.** Breaking either half breaks both (`companion(reg, b, pos) -> (Block_Pos,
  bool)`: the other half of a door), on both sides of the edit; one item drops.
- **Opening.** A type with `"use": "toggle_open"` is used (right button) by an `Edit`
  whose state is the current one with `open` flipped (a new edit kind beside break and
  place: `edit_kind(t, current, requested)` gives `Break`, `Place` or `Toggle`), applied
  to both halves. It is predicted like any edit, so the door opens at once and closes
  again if refused. Doors no longer go through `Use_Block`, which stays for chests.
- `Edit_Result` gains `companion: Maybe(Block_Record)` (the server's value at the other
  cell), so a refused two-cell edit puts both cells back.
- A player standing in a door's cell when it closes is not pushed: the sweep ignores
  boxes the player already overlaps (they are not "ahead"), so they walk out.

*Block entities* (`common/game/block_entity.odin`, `server/block_entities.odin`):

- A type with `"entity": {"kind": "container", "slots": 25}` has a block entity. Kinds are
  the engine's (`Block_Entity_Kind :: enum u8 {Container}`); a container's slots are 25,
  the size the chest overlay draws (other sizes are an error: `containers hold 25 slots
  (the chest screen); got 27`). The base chest says so; the chest code finds its block by
  `entity.kind`, not by `.Chest`.
- **Storage:** per server chunk, `Chunk.block_entities: [dynamic]Block_Entity {local:
  u16, kind, slots: [CHEST_SLOTS]Stack}` sorted by `local` (the index in the chunk),
  looked up by binary search. `w.containers` and `containers.cfg` go.
- **Lifecycle,** at one point: `set_block` compares the old state's entity kind with the
  new one's. A new kind makes an empty entity (when the block is placed, not on first
  open). The kind gone removes it: a container's stacks spill as today's `chest_gone`
  spills them, players looking in are closed. A state change within the type (a facing)
  keeps it. Bulk edits and explosions go through the same point, so `containers_tick`'s
  sweep for records without their block goes (what it still does for lookers walking off
  stays).
- **Journal** (M45): the entry for a change that makes or removes a block entity carries
  the entity's encoded value (the bytes of the region encoding below), so undo and
  rollback restore a broken chest with its contents. The stacks spilled by the removal are
  entities made under the same cause; rollback treats them as M45 treats any entity its
  cause made (if M45 does not remove entities made by a rolled-back cause, the rollback
  test below shows the duplication and that becomes M45's fix, written down here).
- **Saves:** region format 3 adds after each chunk's blocks `varint n`, then per entity
  `u16 local`, `u8 kind`, and for a container `varint` count of non-empty slots, each
  `u8 slot`, `varint item` (an index into a second name table, of items, after the
  blocks' one) and `varint count`. A loaded entity whose block's type has no entity, or
  another kind, is dropped and logged as M30 logs it. No migration (before 1.0 nothing is
  compatible): `containers.cfg` is no longer read and its code goes; a world that still has one
  is refused as an older build's world (M47a's message).
- **Replication:** none new. A container's slots reach the players looking in through
  `Inventory` as in M30; no block entity kind has a client-visible part yet. The first that
  does (a sign's text) adds a `Block_Entity` state kind keyed by `Block_Pos`.
- **State hash:** the `Containers` section hashes the chunks' entities sorted by position,
  position then slots, as it hashed `w.containers`.

*Order of the steps:* neighbour updates and fences; doors (two cells, companions, toggle,
the edit and result fields); block entities (storage, lifecycle, journal, region format 3),
chests moved onto them.

**Left out:** double chests, signs, hoppers, locks; door hinges on the other side and
double doors; fence gates; walls and panes (data on the same mechanism, later); doors
opened by redstone-like signals; entities pushed by closing doors.

**Tests:**

- `common/game/placement_test.odin`: fence states for each neighbour pattern; a fence beside a
  stone block connects, beside a stair's partial side does not; a door's two cells, and
  refused without room above or a floor; companions; `edit_kind`.
- `common/game/physics_test.odin`: a fence cannot be jumped (1.5 blocks); a closed door stops,
  an open one lets through; a player in a closing door walks out.
- `server/shapes_test.odin`, `test_doors_and_fences_agree`: stepped server and mirror;
  build a fence line, break its middle (both neighbours disconnect on both sides),
  place a door, open it, walk through, close it, bump it; zero corrections, chunks equal.
- `server/latency_test.odin`: open and close a door at 200 ms; a refused toggle (a second
  player standing in the way is not a refusal: a door with no room above is) restores
  both halves.
- `server/containers_test.odin`, moved onto block entities: M30's checks unchanged (filled,
  saved, quit and loaded holds the same; unloaded and reloaded with its chunk; broken, it
  drops every stack; two players over UDP agree); an explosion removes the entity at the
  pipeline, not by a sweep.
- `server` journal test: break a filled chest, roll back by cause: the chest and its 25
  slots are back and `/audit` balances.

**Exit check:** `test_doors_and_fences_agree` and the door latency test pass; M30's
chest tests pass on block entities; the rollback test
restores the chest with its contents and the audit balances; the suite and the CI run of
the commit are green.

**Check by hand:** a fenced field with a door: open it, walk in, close it behind; a chest
inside, filled, the universe saved, quit and reopened.
