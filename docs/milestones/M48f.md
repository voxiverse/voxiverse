**No code tests a mode by name.** Systems ask for abilities. A new mode is a data file.

## Names and files

- `common/game/abilities.odin`: `Ability :: enum u8 {Fly, Invulnerable, Instant_Break,
  Infinite_Items, Catalog, Health, Regenerate, Drop_On_Death}`, `Abilities :: bit_set[Ability;
  u32]`, `ability_parse`, `ability_name`. (A new ability is a new enum value plus the system
  that asks for it; a new mode is data.)
- A new registry kind `Game_Mode` (M47): `data/game_modes/<name>.json`, id `<pack>:<name>`:

  ```json
  { "abilities": ["fly", "invulnerable", "instant_break", "infinite_items", "catalog"],
    "kit": [],
    "rules": {} }
  ```

  `abilities`: a list of ability names (an unknown one is a load error with the file and
  the name). `kit`: `[{"item": "base:pistol", "count": 1}]`, given at respawn and when the
  mode is set (M48g reads it; this milestone only loads it, and the kit's items are
  resolved). `rules`: world rules the mode implies for the players in it (none today;
  reserved: an empty object is the only accepted value for now). `Registry.game_modes:
  []Mode_Def {id, abilities, kit}`, hashed with the registry, sent with the packs.
- The base pack gets `data/game_modes/creative.json` (`fly invulnerable instant_break
  infinite_items catalog`) and `survival.json` (`health regenerate`). Their ids are
  `base:creative` and `base:survival`. `game.Game_Mode` (the enum M48e made) is replaced by
  a mode id (a registry index): `universe.cfg` and the creation screen keep the words
  `creative` and `survival` for the base ones and accept any registered mode's id.
- `common/game/abilities.odin`: `derive_abilities(reg, mode, inv) -> Abilities`: the
  mode's profile + the equipment's modifiers (`Modifier_Kind.Grant_Ability` and
  `Revoke_Ability`, an `amount` that is the ability's number; none shipped, one test).
  Beside `derive_mods`; the server and the client's prediction both call it
  (`game.player_step` takes `abilities` and flying needs `.Fly` in it as well as the
  `allow_flying` rule: the rule is the world switching flight off for everyone, the ability
  is what this player can do).
- `server/modes.odin`: `set_game_mode(s, player, mode, cause) -> Mode_Result` is the one
  place a player's mode changes (the `Mode_Result` is `.Ok`, `.Unknown_Mode` or `.Same`).
  It sets `Client.mode` (a registry index; saved with the character in `player_data` under
  a versioned field, M46 migration: an old character takes the world's default), puts the
  `Game_Mode` state record (M39, reliable, per-client singleton: `mode: string
  net:"max=64"`), appends a `Mode_Change` to the edit journal's provenance records with the
  actor and the cause (who changed it: `Cause` text such as `command:Sam`, `join`,
  `script:<pack>`), emits the telemetry event `Mode_Changed` (player, from, to, cause) and
  the `mode_changed` script event (M26's event stream; the VM's name for it, see
  `docs/script_api_notes.md`). Flight is stopped when `fly` is lost (`flying = false`, the
  next prediction frame agrees because both sides run `derive_abilities`).
- `default_game_mode` is a rule (below): a joining character with no saved mode takes the
  world's, else the universe's. The universe's is chosen at creation (the creation screen's
  Mode choice, unchanged) and kept in `universe.cfg`.
- The existing permission nodes `items.catalog` and `items.infinite` are **abilities now**
  (`catalog`, `infinite_items`); the code that asked `allowed(s, c, "items.catalog")` asks
  `has_ability(c, .Catalog)` (server) or `session_ability(s, .Catalog)` (client). The node
  names stay valid in old `permissions.cfg` files and grant nothing (logged once). The
  owner's "every node" no longer implies abilities: a survival-mode owner has no catalog.
- *Permissions guard the commands.* `/gamemode <mode> [player]`: the node
  `voxiverse.command.gamemode.self` for oneself, `voxiverse.command.gamemode.others` for
  another player; `default` has neither, `admin` has both (the operator role: `grant *`),
  `mod` has neither. No argument: prints the mode (no permission). A refusal says
  `You may not change your own game mode.` / `You may not change another player's game
  mode.` (string keys). The existing `world.rules` node no longer guards `/gamemode`.
  Permissions say what you may *ask for*; abilities say what your character *can do*.
- *One rules table.* `common/game/rules.odin`'s `Rules` gains: `pvp: bool` (default true),
  `keep_inventory: bool` (default true: replaces `death_drops`, its inverse; the old name
  is read from saves and `/rule` as an alias, inverted), `natural_regeneration: bool`
  (true), `regen_delay: f32` (5 s), `regen_rate: f32` (1 point a second), and
  `default_game_mode: string` (a `Var` of string kind: if `base.Var` has no string kind
  yet, it is added here with a max length of 64 and the registry check that the mode
  exists). `/rule` is permission-guarded (`voxiverse.command.rule`; admin has it) and
  every change is journalled (`Rule_Change` with actor). The universe's rules and a
  world's override use the table that already exists (a world's `rules.cfg`); nothing new
  is built beside it.
- Wiring the abilities (the only places that ask): `fly` -> physics; `invulnerable` ->
  `damage_player` (M48g makes it the pipeline); `instant_break` -> the break time
  (breaking is instant everywhere today; the ability is read and has no effect until
  break times exist, with a test that the query answers); `infinite_items`, `catalog`
  -> the places above; `health` -> `health_tick`, the HUD's bar (`rules.damage` is
  removed as a rule: the ability replaces it; creative has no bar, survival has one);
  `regenerate` -> M48g; `drop_on_death` -> `die` (and `keep_inventory`).
- Script API shape: the procedures and events are declared in `server/script_api.odin` as
  typed procedures with a `Capability` constant each (comments only for the VM; no VM
  exists yet) and `docs/script_api_notes.md` lists them.

## Order

1. `abilities.odin`, the registry kind, the base pack's two modes, `derive_abilities`,
   the physics parameter; the equivalence tests (`test_base_matches_legacy`-style: with
   `base:creative` the physics and edits are byte-identical to before).
2. `Client.mode`, `set_game_mode`, the state record, the character's save field, the
   journal record, the event; the consumers switched to abilities.
3. The rules table's new fields and `/rule`; `/gamemode` with its nodes.
4. `docs/script_api_notes.md`, `server/script_api.odin`.

## Tests

- An operator's `/gamemode creative` lets them fly while another player stays in survival
  (`server/gamemode_test.odin`, two clients on the stepped server).
- A player without the node is refused with the clear message; with only `.self` they may
  change themselves and not another.
- `fly` is predicted with no rubber-banding: the latency test's desync check over a mode
  change (`server/latency_test.odin`): the client flies the same tick the server does.
- A mode defined only in a test pack (`server/testdata/packs/modes/`: `data/game_modes/
  spectator.json` with `fly` and `invulnerable`) works: no code names it.
- A scan test: no `.odin` file under `server/`, `client/` and `common/` compares a mode
  to `"creative"`, `"survival"`, `base:creative` or `base:survival` outside tests, the
  creation screen's labels and the base-pack loader (a grep over `git ls-files`).
- The mode is saved and loaded with the character; an old save's character takes the
  default; the journal holds the change with the actor; the `Mode_Changed` event is
  emitted once per change and not for `.Same`.
- Rules: `pvp`, `keep_inventory`, `natural_regeneration`, `default_game_mode` read and
  set by `/rule` with the permission, refused without it; a world's override beats the
  universe's; the rule change is in the journal.
- The suite, `build check`, `build determinism` (the state hash includes the mode).
