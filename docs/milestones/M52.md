# M52: the sandbox, part one (capabilities, the host, scheduling, world and entity bindings, the journal; the client-script design)

What a script may do in a world is a list of capabilities: its pack declares them, the
world grants them, and every call into the engine checks one and charges a budget. Nothing
else is reachable from a script. Every world mutation a script makes goes through M45's
journal with the script as its cause. **Split (2026-10-30, #83):** this row builds steps 1-4
and hostile rows 1-20 and 27; [M52b](M52b.md) builds steps 5-8 (players' health and modes,
items, chat, notices and prompts, rules, store, commands, custom events, persistence, the
commands, the hostile rest and the 100-script benchmark). The section *Client scripts and
messaging (the design)* at the end is decided here and built by [M52c](M52c.md) and
[M52d](M52d.md); M52 builds none of it, but nothing M52 builds may contradict it.

**What this builds on (assumed as their paragraphs say; names used below):**

- M51's VM, package `common/script/` (depends on `base` only), with the host API exactly as
  M51's section defines it (`vm_create(Config{limits, seed, libs, natives})`, `compile`,
  `call`, `resume`, `abort`, `Run_Result{status: .Done/.Suspended/.Yielded/.Error}`,
  natives as `Native_Spec{name, fn, cost}` with `check_*`, `push_*`, `raise`, `charge`,
  `host_yield`; pins and handles from M51b; snapshots and the verifier from M51c).
  Decided with M51 (planner, 2026-10-26):
  - **One VM per pack per world**, not per script: a pack's scripts share an author and its
    modules, so isolating them from each other buys nothing. Events for the pack queue on
    its VM and run one at a time; a run may take several slices across ticks. Budgets are
    still kept **per script** (the script whose handler the run is, recorded when the run
    starts) and per pack, and every effect's cause names both.
  - **A throttled call is parked, then done by the host:** the native records the pending
    call (its binding and checked arguments) and returns `host_yield`; the run ends
    `Yielded`; when the bucket holds the cost, the host performs the call itself and
    `resume`s the run with the results (M51: the values become the yielding native's
    results). Nothing is executed twice.
  - Running out of a slice is `.Suspended` (resumed next tick with no values); a limit
    fault (instructions per run, memory, call depth) is `.Error` and cannot be caught by
    the script's `pcall` (M51); what a fault does to the script is decided here.
  - Values: nil, bool, int (i64), float (f64), string, table, function, handle; the host
    builds and reads tables with M51's table helpers (deterministic `pairs` order) and keeps
    functions across runs with M51b's pins (roots, part of a snapshot).
  - `Config.libs` holds all of M51's libraries (base, string, math, table, utf8, coroutine;
    the names of M51's `Lib` enum),
    none of which does I/O (M51's base library has no `load`, `require`, `dofile`, `io`,
    `os`, `package`; `debug` holds only `traceback`).
  - M51c's snapshot and validated restore (fails as a value), pins included; snapshots are
    valid within one engine version only (M51), so a script's lasting state is `store`
    (M52b) and M53's variables, and a snapshot is for a running world, not for upgrades.
- M45 as built: actions (`action_begin(w, Actor{kind, name, bypass}, system)`), `Act
  {action, how}`, the cause-taking `set_block(w, p, block, act, by)` and `bulk_edit(w, e,
  act) -> (changed, result, protected)`, and `admit(w, act, p) -> Admit`, the one
  enforcement point. Here: scripts act as `Actor_Kind.Script` with the name
  `<pack>:<script>`; `Edit_System` gains `Script` (appended: values are on disk); `admit`
  gains `No_Capability` and `Over_Budget` and nothing else checks them; and the journal,
  which holds block entries and block-entity values today, gains entry kinds for what
  scripts can also do: entity spawn and removal (M50's `Origin` and the removal's act) in
  this row, item gains and losses, rule and time changes in M52b, each with its rollback, so
  a pack's effects can be undone by cause (`/rollback script demo:main 10m`) and M54b's
  revert restores the world hash.
- M46: atomic writes (`base/disk*.odin`); a world's extra state files are written through
  it (no migrations before 1.0).
- M47: packs installed per universe (`universe.cfg` `packs`, `<universe>/packs/<namespace>/`,
  `server/universe_packs.odin`), their content universe-wide and fixed while the server

  `pack_archive_sent` never sends `server/`). A pack's *behaviour* is enabled per world,
  here: `worlds/<address>/world.cfg` gains `packs`, the ordered list of installed packs whose

- M50: entity kinds by id, `entity_spawn(w, kind, pos, cause)` with `Origin`, `Tags` (up to 4

  death with the killer, and the spatial query service (`spatial_sphere`, `spatial_box`,

**Script, pack, world.** A script is one source file of a pack, named `<pack>:<name>`
(`demo:main`), run in one world. A pack enabled in two worlds runs two copies that share
nothing. Each pack in a world has one VM (its heap and snapshot), shared by its scripts,
which run one at a time; budgets are per script. Packs never share a heap.

**The API version.** `pack.json` gains `"api": <int>`, required for a pack with scripts:
the script API version the pack was written against. M52 defines version 1 (everything in
M52 and M52b). The server refuses to enable a pack whose `api` it does not support, with
`demo/pack.json:3:10: api 7 is not supported by this server (supported: 1)`. How later
versions are added, deprecated and kept running is [M52e](M52e.md); M52 only reads and
checks the number, and records `Pack_Behaviour.api` so every binding call can be dispatched
by version later without a format change.

The full binding list (name, capability, argument types, cost, the API version it appeared
in) is the `BINDINGS` table in `common/game/capabilities.odin` (signatures) and
`server/sandbox_bindings.odin` (the run procedures, an enumerated array
`[Binding_Id]Binding_Run`, so a signature without an implementation does not compile).
Argument types: `Int`, `Number` (int or float, finite), `String` (max length per binding),
`Bool`, `Table`, `Function`, `Block_Name`, `Item_Name`, `Kind_Name`, `Mode_Name` (checked
against M47's registry), `Player` and `Entity` (handles, below), `Box` (six integers, min
not above max), and `Optional(T)`. Coordinates are integers for blocks, finite floats under
`game.WORLD_LIMIT` for positions.

*Handles.* Players and entities reach scripts as M51b handles (`register_handle_kind`:
`player` and `entity`; `type(h)` is `"handle"`, `tostring` `player: 0x...`): an entity as
its M50 handle (`index | generation << 32`), a player as `player_id | join_serial << 16`
(`join_serial` a new per-`Client` counter that changes on every join and every arrival in a
world). A script cannot make a handle from a number (M51b: handles are made only by the
host). A binding resolves a handle **only in its own world's pools** and checks the
generation (entities) or that the client with that id is in this world with that serial
(players). A stale or other-world handle is refused as `not found`.

*The manifest* (members `api`, `capabilities`, `scripts` and `limits` of the pack's
`pack.json`):

```json
{
  "namespace": "demo", "title": "Demo Quests", "version": "1.0.0",
  "api": 1,
  "capabilities": {
    "world.edit": {"region": [[-64, 0, -64, 64, 128, 64]], "per_tick": 32},
    "entity.spawn": {"kinds": ["base:sheep"], "alive": 8, "per_second": 1},
    "item.give": {"items": ["base:wheat", "base:seeds"], "per_hour": 64},
    "chat.send": {},
    "ui.prompt": {"optional": true}
  },
  "scripts": {"main": "server/scripts/main.vxs", "waves": "server/scripts/waves.vxs"},
  "limits": {"instructions_per_tick": 20000, "memory": 4194304}
}
```

- Server scripts live in the pack's `server/` folder (never sent to clients). Parameter
  names are the budget names in the table (`per_tick`, `burst`, `per_second`,
  `per_minute`, `per_hour`, `per_player_per_hour`, `alive`, `radius`, `bytes`) plus
  `region` (up to 8 boxes, each six integers, inclusive, or `"world"`), `kinds`, `items`,
  `blocks`, `names`, `modes` (lists of ids; `"*"` any), `any` (bool), `optional` (bool).
- `optional` marks a capability the pack works without; the rest are required.
- Validated at load with M47's errors: unknown capability (with the nearest name), unknown
  parameter, a number above its ceiling (`world.edit per_tick 9000 is above the ceiling
  4096`), a box with min above max, the item entity kind in `entity.spawn kinds`, a
  missing or unparsable script file (with M51's diagnostics, file:line:column), a script
  path outside `server/scripts/` or with `..`, a missing or unsupported `api`.

*The grants* (`worlds/<address>/grants.cfg`, the line format of `permissions.cfg`; written
by the server, edited by `/pack grant` (M52b); M52 reads the file, tests write it):

```
# What each pack's scripts and data may do in this world (see docs/debugging.md)
pack demo
grant world.edit region=-64,0,-64,64,128,64 per_tick=32
grant item.give items=base:wheat per_hour=32
grant chat.send
pack arena
grant all
```

- `grant <capability> [param=value ...]`; lists comma-separated; `grant all` grants every
  capability the manifest declares at the manifest's parameters.
- **Effective** capability = declared and granted. Its parameters: regions intersected
  (box by box; an empty intersection removes the capability), lists intersected, numbers
  the least of manifest, grant and ceiling. A parameter the grant leaves out takes the
  manifest's.
- A required capability with no effective grant: the pack's scripts do not start, logged
  once at `warn` with every missing one and the command that would grant it (`pack demo
  needs world.edit, item.give in world <address>: /pack grant demo all`). Its data (M53)
  does not run either. An optional one missing: the scripts start without it.
- Universe ceilings and world pools in `universe.cfg` (new keys, defaults shown):
  `scripts = on` (off: no pack runs scripts or data anywhere), `scripts.max = 128` (per
  world), `scripts.instructions = 1000000` (all scripts of a world, a tick),
  `scripts.blocks = 2048` (a tick), `scripts.spawned_alive = 1024`, `scripts.chat = 10`
  (lines a second), `scripts.items_per_hour = 4096` (of each item, a world, all packs).
- A grant change applies at the next tick boundary. A revocation takes effect at once
  (call-time check); an added capability takes effect when the script restarts, because
  what is registered in a VM is fixed at start.

*The binding layer* (`server/sandbox.odin`, `server/sandbox_bindings.odin`).

- At start, a pack's VM gets `Config.libs` and exactly the bindings of its implicit and
  effective capabilities, each registered as one trampoline with its `Binding_Id` as
  `data`, inside one global table per namespace (`world`, `entity`, ...). **Nothing else is
  registered**: what was not granted does not exist in the script's globals (calling it is
  the VM's "attempt to call a nil value (field 'give')").
- Every call goes through `sandbox_call(script, id, call)`, in this order:
  1. the script is `Running` (not halted or stopping);
  2. arguments against the signature (count, types, ranges, string lengths, handles
     resolved in this world);
  3. the capability is still effective (not revoked), and its parameters cover the call
     (`grant_covers(effective, binding, args)`: region contains every block, kind and item
     in the lists, own entity unless `any`);
  4. the cost (`Binding_Info.cost`: a fixed amount, or a procedure of the arguments: a
     fill's volume, a query's limit) against the script's bucket and the world pool;
  5. run: world mutations through `set_block(w, p, b, act)` and `bulk_edit` with the
     script's action; everything else directly.
- The journal gate: `admit` calls `sandbox_admit(w, act, p)` for an action whose actor is a
  `Script`; it returns `No_Capability` when `grant_covers` does not cover the block and
  `Over_Budget` when the script's block bucket is short. It is the same procedure as step 3,
  called once more at the one enforcement point M45 provides; a mutation it refuses after
  step 3 passed is a bug, logged at `error` and counted (`sandbox.gate_refusals`, which the
  hostile suite asserts is 0).
- Outcomes (`Call_Outcome :: enum {Done, Refused, Denied, Throttled, Halt}`):
  - **Refused** (bad arguments, not granted, revoked, outside the region, not found, not
    own): the native raises a script error (`raise`) with the reason, written for a
    model to act on (`world.set_block: (100, 64, 3) is outside this script's world.edit
    region -64 0 -64 .. 64 128 64`). The handler ends; the script stays. Logged at `warn`
    (`server script refused world=... script=demo:main call=world.set_block reason=...`),
    a `Script_Refused` telemetry event (appended kind), a line in the script's log.
  - **Denied** (a hard cap: alive entities, the hourly faucet, pending timers,
    subscriptions, a cost larger than the bucket's capacity): the call returns `nil,
    message` (two results, Lua's idiom); nothing else happens. Logged at `debug`, counted
    per script.
  - **Throttled** (the bucket or the world pool is short now, but the cost fits its
    capacity): the native parks the call and returns `host_yield`; the run is parked until
    the tick its bucket holds the cost (computed exactly from the rate), when the host
    performs the call (from step 1) and resumes the run with its results. The tick never
    waits.
  - **Halt** (below): the script stops.
- Buckets are integers in thousandths of a unit (`Bucket {level, rate, capacity, last}`),
  refilled lazily from the world's script tick: `level = min(capacity, level + rate *
  (tick - last))`. Per-player budgets are buckets keyed by player id in a sorted array,
  made on first use and dropped when the player departs. Deterministic: no clock, no map
  order.
- **Halting.** A script is halted (state `Halted`, its VM kept for `/script log`, its
  entities left as they are) when: its memory budget is exceeded (M51's `.Memory` fault);
  one handler has run 300 ticks' worth of its instruction budget without finishing (an
  infinite loop: it suspends every tick at its budget and is stopped after 10 s); it was
  refused 32 times within 900 ticks; a handler errors 32 times within 900 ticks. Logged at
  `error` with the reason, a `Script_Halted` telemetry event (appended kind), a notice to
  players holding `admin.scripts` in that world. A halted script stays halted until its
  world restarts it (M52b's `/script restart`; in M52, tests call `sandbox_restart`).

*Scheduling and the fixed points of the tick* (`server/sandbox.odin`).

- Each world has `scripts: [dynamic]Sandbox_Script` in a fixed order (pack order of
  `world.cfg` `packs`, then the order of the manifest's `scripts` member) and `script_tick:
  u64`, which counts the world's unfrozen ticks (timers and buckets use it, so a paused
  singleplayer world's scripts stand still with its entities).
- Two points in `tick` (`server/server.odin`), per world, both skipped while frozen
  (re-check the line numbers when building: the client loop around `simulate_player` and
  the world loop around `entities_tick`, `gates_tick`, `changes_flush`):
  - **Point A, after the players** (after the `for &c in s.clients` loop of
    `simulate_player`/`health_tick`/`stats_tick`): region membership is updated
    (`regions.watch`), then the events raised since the last point (messages received this
    tick: chat, commands, edits, uses, answers; players' movement, damage and deaths) are
    delivered.
  - **Point B, after the world** (in the world loop, after `entities_tick` and
    `containers_tick`, before `gates_tick` and `changes_flush`): due timers, `tick`
    events, then the events raised since point A (entities died and hurt, block changes
    by the simulation and by point A's scripts). Effects made here reach clients in the
    same tick's `changes_flush` and `replica_flush`.
- Delivery: data (M53's triggers) first, then scripts. Scripts run round-robin starting
  at index `script_tick % len(scripts)`; each script handles its queued events and
  resumes a parked call while its tick budget lasts, then the next; when the world pool
  is spent, the rest wait for the next point, in order. A script whose events wait more
  than 30 ticks is reported as `starved` (a counter, and in `/script list`, M52b).
- **Events raised by a script's own effects are queued for the next point**, never
  delivered within the run that caused them, and a script never receives events it
  caused (`cause.id` is its own). No recursion inside a tick.
- A script's queue holds at most 1 024 events; filtered at enqueue (region, kind,
  name). On overflow the newest are dropped and counted; the script gets an
  `events_lost {count}` event first at its next delivery, and a `warn` line is logged once
  a minute per script.

*The events* (`Script_Event :: enum` in `common/game/capabilities.odin`; the M39 event kinds
are client-facing and stay as they are; these are the scripts' vocabulary). A handler is
`on(name, fn, filter)`; `fn` gets one table with `name` and the fields. Built in M52: all
but `prompt_answer`, `rule_changed`, `command`, `custom` and `mode_changed` (M52b).

*Isolation (why each escape is impossible).*

- **Other worlds.** A script holds a `^World` it cannot name or change; no binding takes a
  world, an address or a path; coordinates are always its own world's. Handles resolve
  only in its world's pools (a player who travelled away has a new `join_serial` and is
  not in this world: refused). Chat and events reach only this world. Script state,
  buckets and stores are per world. Test: the same pack in two loaded worlds.
- **The file system, network and clock.** The VM has no I/O (M51), `Config.libs` adds no
  I/O, and the sandbox registers no binding that touches them. Time is `world.tick` and
  `world.time`, both simulation state. Snapshots and stores (M52b) are written by the
  server to paths it builds from ids it validated (`worlds/<address>/scripts/<pack>/...`),
  never from script strings. A test lists every global of a script with every capability
  and compares it with the expected set (`server/testdata/scripts/globals_v1.txt`), so a
  new binding cannot appear unnoticed.
- **Other scripts.** One heap each; the only channels are `events.emit` (copied data,
  M52b) and the world itself (blocks, entities). No binding returns another script's
  values or functions.
- **The engine's memory.** The VM is memory-safe and metered (M51); bindings validate
  every argument before use (ground rule 6) and return copies, never views into server
  memory. A script's heap is its own region, capped by its memory budget.
- **Forged effects.** The cause is set by `sandbox_call` from the script's id; no binding
  takes a cause. Chat from a script is a system line (`chat_system`) prefixed with the
  pack's title in brackets (`[Demo Quests] ...`), run through `chat_clean`, so it cannot
  pass for a player or the server. Items enter only through `item.give` (ledger reason
  `Script_Give`) and leave through `item.take` (`Script_Take`); `entity.spawn` of the
  item kind is refused, so there is no second faucet.
- **The tick.** Budgets are in instructions and units, never time; a script cannot hold
  the tick past its budget, and the world pool caps all of them together.

*The ledger.* `game.Reason` gains `Script_Give` and `Script_Take` (appended). `item.give`
charges three buckets: the script's per-item hourly one, the per-player hourly one and the
world's `scripts.items_per_hour` pool for that item (one per world, all packs). `Ledger`
entries keep the universe-wide counts as today; the world's per-pack totals for `/pack
info` are counters in the world's stats (`scripts.items.<pack>.<item>`). Stack origin tags
(an item remembering it was made by a script) are not built: they wait for the economy's
content wave (plan, threat model).

*Observability.* Every script has a 256-line log (ring, `log.*` lines and the sandbox's own
refusal and halt lines), counters (`instructions`, `refused`, `denied`, `throttled_ticks`,
`queued`, `lost`, `starved`), and the world a `base.metric_scope(.Server_Scripts)` (a new
`Metric`, appended) around both points, so the profiler and `build trace` show the
scripts' share of the tick. Errors carry M51's traceback, written to the log with
`file:line`.

## Client scripts and messaging (the design; owner's decision 2026-10-30, #83; built by M52c and M52d)

**Why.** Creators want their own HUD, camera, input and local effects, which a round trip to
the server cannot give. A pack may therefore run scripts on the client. The server stays
authoritative: a client script presents and asks; it never decides.

**The rule.** A client script may change only what the client alone owns and shows: its own
UI elements, the camera's presentation, its declared input actions, and local effects
(sounds and particles at positions, nothing that collides). It reaches the server only by
sending messages on its pack's declared channels, which the pack's server script receives
as validated data and may act on through its own capabilities. Nothing a client script does
is state (the *Numbers* decision's "free" tier); nothing it does is predicted.

**Where client scripts live.** In the pack's `assets/scripts/` folder (`assets/` is the
client-only side, already sent by `pack_archive_sent` and covered by the archive hash; no
fourth folder). The manifest's `client_scripts` member names them, beside `scripts`; its
`client_capabilities` member declares their capabilities. The server validates the client
manifest at load like its own (it holds every folder), so a pack with a malformed client
side is refused before any client sees it.

**The client VM.** One VM per pack per session on the client (`Client_Script`, package
`client`, files `client/sandbox*.odin`), created after the pack phase when the player
arrives in a world that enables the pack, destroyed on departure, travel or leaving. Same
`common/script` VM, same `Config.libs`, its own heap region, its own seed (from the world
address and pack hash, so a recorded session replays). It runs at the client's fixed tick
(30 Hz) for events and logic, never per frame: what is drawn every frame is a retained
element tree the script updates (M52f), and the camera is a rig the script sets and the
engine interpolates (below), so a script's cost does not grow with the frame rate.

**Client capabilities** (`side = .Client` rows of `CAPABILITIES`; built by M52c unless
noted; budgets are engine ceilings sized from the frame budget, see M52c):

| Capability | Allows |
|---|---|
| (implicit) `cpu`, `timer`, `events`, `random`, `log`, `clock` | as on the server, on the client tick; `log` goes to the client's log and the dev console |
| `hud` | the element tree (M52f): create, update and remove elements in the pack's HUD layer |
| `menu` | the pack's own screens and inventory views (M52g) |
| `camera` | `camera.rig{...}`: offsets, a target, a field-of-view change and a blend time, inside the engine's limits; `camera.reset()` |
| `input` | the pack's declared actions (`client_actions` in the manifest: a name and a suggested binding) and their `action` events; players rebind them in Options under the pack's title |
| `effects` | `effects.sound(name, pos)`, `effects.particles(kind, pos, count)` from the pack's own assets, local only |
| `view.read` | what this client already knows: its own player's position, look, health and held item; the blocks and entities loaded around it (`world.block`, `entity.query` over the client's replica); the pack's own replicated values (M52d) |
| `channel` | `channel.send(name, data)` on the pack's declared channels and the `message` event (M52d) |

**What a client script may never do** (each a row of M52c's hostile suite): change a block,
an entity, an inventory, health, a mode, a rule or any replicated value; send anything to
the server but its channel messages; read raw keys, text or the pointer outside its own
focused element (no keylogging); read chat, the player list beyond names in its world, other
players' accounts or addresses, the clipboard, files, the network, settings (except UI
scale, language and Reduce motion, read-only); cover or disable the engine's own UI (the
game menu, chat input, the death screen, prompts, toasts, the Escape key, the F1 toggle, the
pack's attribution); capture or warp the pointer; change volumes; take screenshots; run
while its world is not the one shown; outlive its world.

**Messaging** (M52d). A pack declares channels in `pack.json`:
`"channels": {"vote": {"to": "server", "schema": {...}, "per_second": 4}, "score": {"to":
"client", "schema": {...}}}`. A message is plain data matching its schema (nil, bool, int,
float, string, lists and records of those; depth, entries and bytes capped), encoded by one
codec, carried in a new protocol message `Script_Message {pack, channel, data}` on the
reliable ordered lane. Client to server: decoded and validated at the edge (ground rule 6),
rate-limited per player and channel with the sandbox's `Bucket`, delivered at point A as a
`message` event `{player, channel, data}` to the pack's server scripts in that world, never
to another pack. Server to client: `channel.send(player, name, data)` with the
`channel` capability, charged like `chat.tell`. A flood is dropped and counted; a client
over ten times its rate for five seconds is disconnected with a reason (M55 later folds this
into its general rate limits).
