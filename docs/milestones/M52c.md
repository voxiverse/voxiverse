# M52c: client scripts (a VM per pack on the client, its capabilities and quotas, what a client script may never do)

**Why.** The owner's decision of 2026-10-30 (#83): creators make their own HUD, camera, input
and local effects, which a round trip to the server cannot give. M52's section *Client
scripts and messaging (the design)* decided the shape; this row builds the client VM and its
capabilities except drawing (M52f, M52g) and messaging (M52d). The server stays
authoritative: nothing here can change what the server owns.

**What this builds on:** M51 (`common/script`), M52 and M52b as built (the capability table,
`Bucket`, `sandbox_call`'s steps, the manifest parser and its errors, grants, the hostile
harness); M47b's pack phase (`pack_archive_sent` sends `pack.json`, `assets/`, `data/`; the
client keeps archives by hash, `pack_fetch.odin`) and, for singleplayer, the client's
registry built from the save's packs (`registry_for_dir`); the client session
(`client/session.odin`: `session_start`, arrival, travel, `session_end`); the action layer
(`client/actions.odin`: `Action_Context {World, Menu}`, `ACTION_INFO`, `actions_update`,
`action_pressed`); the camera (`client/view_camera.odin`: `camera_update` builds `s.view`
from `s.camera`, `camera_third_person` pulls the camera in against blocks;
`client/camera.odin`: `View`, `camera_render`); local effects (`client/entities.odin`'s
`Puff` particles, `client/sounds.odin` and the mixer's World bus); Options' controls tab
(`client/screen_options.odin`).

**Names.** The client's sandbox type is `Client_Script` in package `client`, files
`client/sandbox.odin` (host, scheduler), `client/sandbox_bindings.odin` (run procedures,
`[Client_Binding_Id]Client_Binding_Run`). The `--exec` runner (`client/script.odin`,
`Script`) is unrelated and keeps its name.

**The manifest, client side** (`pack.json`; parsed by the same code as M52's manifest, so the
server validates it at load and refuses a pack whose client side is malformed before any
client sees it):

```json
{
  "api": 1,
  "client_scripts": {"hud": "assets/scripts/hud.vxs", "cam": "assets/scripts/cam.vxs"},
  "client_capabilities": {"camera": {}, "input": {}, "effects": {"optional": true}, "view.read": {}},
  "client_actions": {"boost": {"key": "LShift", "pad": "Right_Bumper"}, "horn": {"key": "H"}},
  "client_limits": {"instructions_per_tick": 50000, "memory": 8388608}
}
```

- Client scripts live under `assets/scripts/` (sent, hashed by the archive; never under
  `server/`); a path outside it or with `..` is a load error. At most 64 files, 256 KiB a
  file, 1 MiB together (compile time bounded on the client).
- `client_actions`: up to 16 per pack, names `[a-z][a-z0-9_]{0,23}`, suggested bindings by
  the names `actions.odin` already parses for keys and pad buttons. A suggested binding the
  engine already uses in the World context (movement, jump, sneak, inventory, chat, F-keys,
  Escape) is not applied: the action starts unbound and the load logs one `info` line. A
  pack action never suppresses an engine action.
- Grants: `grants.cfg` lines name client capabilities like server ones (`grant camera`);
  `grant all` covers both sides. The effective client capabilities are computed on the
  server (M52's intersection) and sent; the client registers exactly those.

**Telling the client which packs run here.** A new reliable state kind `World_Packs` (M39's
mechanism, keyed by world): the packs enabled in the world the player is in, each with its
namespace, archive hash, API version and effective client capabilities with their numbers.
Sent on arrival and when a grant changes. The client starts a pack's client VM when the
record names it and the archive with that hash is in its cache (singleplayer: the save's
pack directory, checked against the same hash). `PROTOCOL_VERSION` goes up; the bandwidth
baseline is re-accepted with the record's bytes listed in the report.

**The client VM** (`Client_Script`):

- One per pack per session, created on arrival in a world that enables the pack, destroyed
  on departure, travel, leaving, or a `World_Packs` record without it; its timers, handlers
  and heap go with it (no persistence on the client: a client script's lasting state is its
  server script's, M52d).
- `Config.libs` as on the server; natives exactly the client capabilities' bindings; seed
  from the world's address and the pack hash, so a recorded session replays the same.
- Run at the client's fixed tick (`game.TICK_RATE`, the same accumulator as prediction), in
  `session_update` after `receive` and before `camera_update`, never from the frame or the
  UI. Round-robin over packs like the server's, with a client pool.
- Events (`Client_Event`, in `common/game/capabilities.odin`): `load`, `tick` (`every`),
  `action` (`name`, `pressed`/`released`, `value` for analog), `arrive` (the world's
  address), `depart`, `held_changed`, `health_changed` (own player), `block_changed`
  (loaded chunks, region filter), `entity_seen`/`entity_gone` (entities entering or leaving
  the client's replica), `events_lost`. M52d adds `message`, M52f `ui_*`.
- Halting as on the server (memory, 300 ticks of budget without finishing, 32 errors or
  refusals in 900 ticks): the VM is kept for the log, the pack's camera rig is reset, its
  effects stop, its actions go quiet. Logged on the client; a `Client_Script_Halted`
  telemetry kind (appended).

**Client capabilities built here** (the `side = .Client` rows of `CAPABILITIES`; budgets
are engine ceilings sized from the frame budget, see *Budgets*):

| Capability | Bindings | Budget (ceiling) |
|---|---|---|
| (implicit) `cpu` | running at all | 50 000 instruction units a client tick, 8 MiB heap, call depth 200; all packs together 100 000 a tick and 32 MiB |
| (implicit) `timer`, `events`, `random`, `log`, `clock` | as on the server (`clock` is the client's view of the world tick and time) | as on the server |
| `view.read` | `me.position()`, `me.look()`, `me.health()`, `me.held()`, `me.mode()`; `world.block(x, y, z)` and `world.top(x, z)` over loaded chunks (nil when not loaded); `entity.query(center, radius, filter)` over the replica (kind, position, tags; never account, address or chat) | 4 096 reads a tick, 32 queries a tick of 64 results |
| `input` | `input.action(name) -> bool, value`; the `action` event | none beyond `cpu` |
| `camera` | `camera.rig{offset, target, look_at, fov_add, blend}`, `camera.reset()` | 4 rig changes a second |
| `effects` | `effects.sound(name, pos, {gain, pitch})` (the pack's own sounds, World bus), `effects.particles(block_or_colour_index, pos, count)` (the `Puff` path) | 8 voices playing per pack, 16 sounds a second; 256 puffs a second, 64 alive per pack |

**The camera rig.** Applied at the end of `camera_update` to `s.view` only (never
`s.camera`, which feeds the player's input yaw and pitch, so a rig cannot steer the player).
`offset` (in the view's frame or the world's), `target` (a position or an entity handle from
`entity.query`, whose interpolated position is followed), `look_at`, `fov_add` and `blend`
(ticks, interpolated per frame). Limits, all engineering: the camera is pulled in against
blocks by `camera_third_person`'s collision, so it never sees through walls; its distance
from the player's eye is at most the interest radius; the resulting field of view stays
inside Options' own range; with `reduce_motion` on, blends are cuts. F5 still cycles the
engine's modes; a rig applies in first person only when the pack sets `offset` to zero and
changes only `fov_add` (so held-item drawing, M48k, stays right). `camera.reset()`, a halt or
departure returns to the engine camera within one frame.

**What a client script may never do** (each a hostile row): change a block, an entity, an
inventory, health, a mode, a rule or any replicated value (no such binding exists); send
anything to the server (until M52d's channels); read raw keys, text or the pointer (only its
declared actions; M52f adds focus-scoped text for its own fields); read chat, the player
list, accounts, addresses, the clipboard, files, the network or settings (except
`settings.ui_scale()`, `settings.language()`, `settings.reduce_motion()`, read-only, in
`view.read`); bind Escape, F1-F12, the chat key or the game-menu pad button; capture or warp
the pointer; change volumes; take screenshots; draw over the engine's UI (M52f keeps its
layer below the engine's overlays); run while its world is not the one shown.

**Budgets.** The ceilings above are engine protection, not creator-facing product numbers:
M51 measured 100 000 units at about a millisecond, and the client's whole-tick pool of
100 000 units keeps every client script together near 1 ms a client tick, a sixteenth of a
60 Hz frame. A new benchmark scenario `client-scripts` (`client/benchmark.odin`, version 1,
3 repetitions): 8 packs, each running `client/testdata/scripts/busy.vxs` at its ceiling
(reads, queries, a rig change a second, sounds and puffs at their rates) in the `views`
scene; its limit, beside the others gated in CI's Profiling step, is the script phase's p99
under 1.2 ms of the main thread's CPU per client tick and the frame's p99 within 10% of
`views` without scripts.

**Order of the steps:**

1. The client side of the manifest (`client_scripts`, `client_capabilities`,
   `client_actions`, `client_limits`) parsed and validated with M52's errors; the client rows
   of `CAPABILITIES` and `Client_Event`; the server refusing a malformed client side.
2. `World_Packs` (server sends, client receives); `Client_Script` lifecycle (arrival,
   travel, departure, record change); the scheduler at the client tick; implicit bindings,
   `load` and `tick`.
3. `view.read` and `input` (pack actions in `ACTION_INFO`'s dynamic part, Options' controls
   tab listing them under the pack's title, rebinding saved per pack namespace in
   `settings.cfg`); `action` events.
4. `camera` (the rig, its limits) and `effects`.
5. The hostile suite; the benchmark scenario.

**The client hostile suite** (`client/sandbox_hostile_test.odin`, scripts in
`client/testdata/scripts/hostile/`, on a stepped server with the client's session as in
`test_weapons_over_a_stepped_server`). Every row asserts its outcome, a log line, the
server's state hash unchanged by the client script, and nothing sent to the server beyond the
honest client's own messages (the pipe's message count by kind).

| # | Script | Does | Expected |
|---|---|---|---|

| 5 | `escape_grab` | declares actions bound to Escape, F1, the chat key, the pad's Start | each starts unbound with an `info` line; Escape still opens the game menu |

**Other tests:** manifest client-side errors (exact text and line); `World_Packs` round trip
and schema; VM lifecycle over join, travel, leave and a revoked grant; pack actions in
Options (listed, rebound, saved, conflicts left unbound); the rig's interpolation and
`reduce_motion` cut; determinism: a client session replayed from its recording gives the
same client script logs.

**Open questions for the owner** (none blocks this row; each is built only when answered):

1. May a player turn off a pack's client scripts (an Options switch per pack), and what does
   the experience show then?
2. Are the engine ceilings above also the limits a creator meets, or should creators get
   lower defaults (and if so, which)?

**Left out:** drawing (M52f, M52g); messaging (M52d); persistence on the client; client
scripts in menus outside a world (the title screen and universes screen never run pack
code); hot reload of client scripts beyond the pack reload that already restarts them.

**Exit check:** the client hostile suite (rows 1-16) contained as listed; the other tests;
`client-scripts` within its limit in CI's Profiling step; the whole suite, `build check`,
`build determinism`; CI green.

**Check by hand:** in a singleplayer world with `client/testdata/packs/camera_demo`
installed and granted (`/pack grant camera_demo all`), press the pack's `orbit` action: the
camera swings to the side over about a second and back on release, never inside a wall
(stand against one to try); with Reduce motion on it cuts instead.
