# M52d: script messaging (typed channels between a pack's client and server scripts, rate limits, validation)

**Why.** A client script (M52c) presents and asks; the server script decides. The only way a
client script reaches the server is a message on a channel its pack declared, which the
server decodes, validates, rate-limits and hands to the same pack's server scripts in that
world. The other direction lets a server script feed its client scripts (a score, a timer, a
target). Designed in M52's section *Client scripts and messaging*; built here.

**What this builds on:** M52/M52b (server scripts, `Bucket`, the event queue and point A,
`events.emit`'s plain-data copy and limits), M52c (`Client_Script`, `World_Packs`, the
client capability rows), M39's protocol (`common/game/protocol.odin`: messages with a
validated decoder; `PROTOCOL_VERSION`), the M7 netcode lanes (reliable ordered), the
dissector's generated schema block (`./build.sh schema`, `tools/wireshark`), `netdump
-summary`.

**Channels** (`pack.json` member `channels`; validated at load with M52's errors):

```json
"channels": {
  "vote":  {"to": "server", "per_second": 4, "burst": 8,
            "schema": {"choice": "int 0..8", "note": "string 64?"}},
  "score": {"to": "client", "per_second": 10,
            "schema": {"team": "string 16", "points": "int", "left": "list 8 of int"}}
}
```

- At most 16 channels a pack, names `[a-z][a-z0-9_]{0,23}`.
- `to` is `server` (client scripts send, server scripts receive) or `client`.
- Schema field types: `bool`, `int` (optional range `a..b`), `number` (finite float,
  optional range), `string N` (bytes, at most 1 024, UTF-8 checked), `list N of T`, `record
  {...}` (nested, depth at most 4), `handle` (an entity or player handle; resolved on the
  receiving side in that world, refused if stale), a trailing `?` for optional. A message is
  at most 4 KiB encoded; a schema whose largest message could exceed it is a load error with
  the computed size.
- `per_second` and `burst` per player per channel, with engine ceilings (client to server:
  20 a second, burst 40; server to client: 60 a second per player, burst 120). The ceilings
  are engine protection sized from the per-client bandwidth baseline (M39's `session`
  scene), not creator-facing product numbers (see the open question).
- A channel is part of the API version (M52e): its schema is in `api.json`'s pack-facing
  description, so a later engine reads an older pack's channels the same way.

**The wire.** One new client-to-server message `Script_Send {pack: u16 (index in this
world's `World_Packs`), channel: u8, data: bytes}` and one server-to-client message
`Script_Deliver {pack, channel, data}`, both on the reliable ordered lane, `data` encoded by
one schema-driven codec (`common/game/script_message.odin`: `message_encode(schema, value)`,
`message_decode(schema, bytes) -> (Value_Tree, Message_Error)`, the same code on both
sides, no allocation past the message's limits). `PROTOCOL_VERSION` goes up; the dissector
and `netdump -summary` learn both messages (summary by pack and channel); the bandwidth
baseline is re-accepted, its change listed.

**Client to server** (`server/script_messages.odin`):

1. Decode the envelope (pack index in range for the player's world, channel exists and its
   `to` is `server`) or count `script.msg_refused{malformed}` and drop.
2. The player's bucket for that pack and channel (M52's `Bucket`, per player, dropped on
   departure); empty: count `throttled`, drop. A client that sends more than ten times the
   channel's rate for five seconds in a row is disconnected with the reason `too many script
   messages` (logged, a `Script_Message_Flood` telemetry kind, appended).
3. `message_decode` against the schema: wrong type, out of range, too long, bad UTF-8,
   depth, a stale or other-world handle: count `refused`, drop, log at `debug` once a second
   per player with the first error (`vote.choice: 12 is above 8`).
4. Queue a `message` event `{player, channel, data}` on the pack's server scripts in the
   player's world (M52's queue: filtered by channel subscription, `events_lost` on
   overflow), delivered at point A. A pack with no running server script drops it (counted).
   The event's `data` is built in the receiving VM's heap from the decoded tree; the server
   never hands one VM's values to another.

**Server to client.** `channel.send(player, name, data)` and `channel.broadcast(name,
data)` (every player of this world), capability `channel` on the server side (new row, API
version 1: M52e records it), charged per player against the channel's rate; over the rate
the call is `Throttled` (parked, M52) for `send` and `Denied` for `broadcast`. The data is
encoded from the script's value by the schema (refused with the field named if it does not
match). The client decodes with the same codec, refuses and counts what does not match
(only a broken server would send it), and delivers a `message` event to the pack's client
script. The client never resends.

**Client scripts.** `channel.send(name, data)` (capability `channel` on the client side),
checked against the schema before sending (a script error naming the field), charged
against a client-side bucket at the channel's rate so an honest script is never
disconnected; over the rate the call returns `nil, "throttled"`.

**Order, delivery and loss.** Reliable ordered per client; messages to one script arrive in
the order sent, at point A of the tick after they were received. A player departing or
travelling drops their queued messages (counted). The server never trusts a message to mean
anything beyond its schema: what it allows is the server script's decision, through its own
capabilities.

**Observability.** Counters per pack and channel (sent, delivered, throttled, refused,
dropped) in `/pack info` and the stats; `netdump -summary` totals; a `Script_Messages`
metric scope around step 1-4.

**Order of the steps:**

1. Channel declarations, schema parsing and the size computation; `message_encode` and
   `message_decode` with unit tests and the codec fuzz.
2. The two protocol messages, the dissector and netdump; the server's four steps; the
   `message` event on the server.
3. `channel.send`/`broadcast` on the server; the client's decode and `message` event; the
   client's `channel.send`.
4. The hostile suite; the bench scene.

**The messaging hostile suite** (`server/script_messages_test.odin`, raw messages written by
a `Fake_Client` of the harness, and over `Simnet` with loss):

| # | Sends | Expected |
|---|---|---|
| 1 | a pack index past the world's packs; a channel index past the pack's | dropped, `malformed` counted, nothing delivered |
| 2 | on a `to: client` channel from the client | dropped, `malformed` |
| 3 | data that does not match: wrong type per field, an int out of range, a 2 KiB string on `string 64`, invalid UTF-8, depth 9, 10 000 list entries, a truncated buffer | each refused with its error; the server's allocator unchanged after |
| 4 | 1 000 valid messages in one tick | `burst` delivered, the rest throttled; after five seconds over ten times the rate the client is disconnected with the reason |
| 5 | a handle of another world's entity, a stale player handle | refused |
| 6 | a valid message for pack B while the player's world enables only pack A | dropped (`malformed`: B is not in this world's index) |
| 7 | a valid message while the pack's server script is halted | dropped, counted; the client is not disconnected |
| 8 | the same valid message from two players | delivered twice with each sender's handle; neither can claim the other's handle |
| 9 | a server script sending to a player in another world; broadcasting past the rate | refused (`not in this world`); denied |
| 10 | 1 000 random byte strings as `Script_Send` payloads (fixed seed) | none crashes or allocates past the limit; every one refused or delivered as a schema-valid value |

**Other tests:** codec round trips for every schema type and limit (exact bytes for a few
golden messages, so the format is pinned); the size computation; a round trip client script
→ server script → client script over UDP with 10% loss and duplication
(`test_script_messages_over_loss`: every message once, in order); determinism: the
harness's recorded messages replay to the same server state hash; the server's
`message_decode` added to the protocol fuzz corpus (`common/game` protocol fuzz, M55 widens
it); `channel.send` refusals on both sides name the field.

**Benchmark.** A scene in `server/budgets.odin`, `budget_script_messages`: 100 players'
`Fake_Client`s each sending at a 20-a-second channel's rate to one server script that
answers with a broadcast every tick, 300 ticks; judged by `build bench budgets -check`: the
messages' share of the tick (decode, validate, deliver) p99 at most 1 ms, and the server's
outgoing bytes a tick within 1.25 times the encoded payload (envelope overhead).

**Open question for the owner** (does not block this row): are the per-channel engine
ceilings (20 a second up, 60 down per player) also what creators meet, or should creators
get lower defaults?

**Left out:** unreliable channels (a later row if a moving structure's driver input needs
lower latency than reliable delivery gives, measured in M50d); messages between packs (packs
talk through `events.emit` on the server only); messages across worlds or servers; M55's
general rate limiter (it absorbs step 2's bucket later).

**Exit check:** the messaging hostile suite (rows 1-10) as listed; the other tests; the
bench scene within its limits; the whole suite, `build check`, `build determinism`; CI green.

**Check by hand:** none.
