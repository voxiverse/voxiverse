# M52f: the creator UI toolkit, part one (HUD elements from client scripts, on the engine's UI)

**Blocked until the owner answers the open questions below.** The engineering is decided;
what a creator's HUD may look like and where it may sit are the owner's.

**Why.** The owner's decision of 2026-10-30 (#83): creators script their own HUD, menus and
inventories, on the client scripts (M52c) and **reusing the engine's own UI system**
(`client/ui`), never a second one. This row is the HUD: elements a client script creates and
updates, drawn by the engine every frame, never interactive. Menus, focus and inventories are
[M52g](M52g.md).

**What this builds on:** M52c (`Client_Script`, the client capability rows, the client tick,
halting), the engine UI as built (`client/ui`: `begin_frame`/`end_frame`, `Layer {Base,
Popup, Modal, Keyboard, Tooltip}`, ids with `push_id`/`pop_id`, `layout_begin`/`next`, the
`cut_*` helpers, `label`, `title`, `panel`, `draw_text`, `measure_text`, `wrap_words`,
`draw_image`, `add_icon`/`draw_icon`, `push_clip_rect`, `Theme`, `theme_scope`, `opacity`),
the HUD as built (`client/hud_game.odin`: `game_screen` → `hud_draw`, returning when
`app.hud_hidden` (F1); `client/hud_hotbar.odin`'s `stack_slot` path for item icons;
`client/menu_inventory.odin`'s `stack_slot`), pack assets (`common/game/pack_assets.odin`:
`png_texture`'s header check before `core:image/png`), R1's visual baselines (`--scene`,
`build images`).

**The design (engineering, decided):**

- **Retained, not immediate.** A script holds an element tree (`Hud_Tree` per pack:
  `[dynamic]Hud_Element` in a pool with generational handles, ground rule 2); it creates,
  updates and removes elements on its client tick; the engine draws the tree every frame
  inside `hud_draw`, after the engine's own HUD elements and before `draw_overlays`, on
  `Layer.Base`, under `push_id("pack:<namespace>")`. A script never runs per frame, and the
  frame's cost is the tree's size, not the script's.
- **The engine's widgets only.** Element kinds map one to one onto existing `client/ui`
  procedures and the engine's look (`Theme`): `text` (`label`/`draw_text`, wrapped by
  `wrap_words`), `title`, `panel`, `image` (a pack PNG from `assets/ui/`, through
  `png_texture`'s checks and `add_icon`), `item` (an item icon and count through
  `stack_slot`), `row` and `column` (containers laid out by `layout_begin`/`next`). Any
  further kind (a bar, a timer face) is the owner's question 3 below, not added here.
- **Anchoring and units.** A root element is anchored to one of nine screen points with an
  offset in UI units (scaled by the player's UI scale like every engine element); children
  lay out inside their container. Every element is clipped to the screen and to its
  container (`push_clip_rect`). The screen region a pack may use is the owner's question 2;
  until answered the row does not run.
- **Hidden with the HUD.** F1 (`app.hud_hidden`) hides pack elements with the engine's;
  overlays that take the world (`overlays_take`) dim or hide them as they dim the engine's
  HUD; the death screen and the game menu draw over them (they are on higher layers).
- **Text.** Strings from the script are cleaned like chat (`chat_clean`: no control
  characters, valid UTF-8), capped at 256 bytes an element and 4 KiB a pack's tree, and
  drawn with the engine's font; a glyph the font lacks shows the font's fallback. A pack's
  texts are data, not the engine's string table (`Text`, `TEXT_EN` stay the engine's own);
  the `lint_ui_literals` rule is for engine Odin files and is unchanged.
- **Budgets** (engine ceilings): 256 elements a pack, 1 024 for all packs; 64 element
  changes a pack a client tick; images: 16 a pack, at most 256x256 pixels each, in the UI
  atlas's space (an atlas that cannot fit one refuses it with `nil, "atlas full"`, never
  silently). Over a ceiling: `Denied` (`nil, message`).

**Bindings** (capability `hud`, client side, API version recorded by M52e's description):
`hud.add(kind, props) -> element`, `hud.set(element, props)`, `hud.remove(element)`,
`hud.clear()`; props: `anchor`, `offset`, `parent`, `text`, `item`, `count`, `image`,
`visible`, `order` (within the pack's tree), and, depending on question 1, `colour`. A prop
the kind does not take, or a wrong type, is refused naming it.

**Order of the steps:**

1. `Hud_Tree`, its pool and handles, the bindings with validation and budgets.
2. Drawing inside `hud_draw` through the engine's widgets; anchoring, layout, clipping; F1 and
   overlays.
3. Pack images from `assets/ui/` (validated at load like other pack PNGs, M47i).
4. Tests, visual baselines, the benchmark.

**Tests:** every kind drawn (vertex and command counts, clip rectangles) in UI tests without
a GPU (`client/ui`'s `Output`); anchors at the nine points at three UI scales and two window
sizes; F1 hides; an overlay over the HUD; budgets (257th element denied; 65 changes in a
tick: the 65th denied); text cleaning (control characters, broken UTF-8, 1 KiB); a refused
image (wrong size, not in `assets/ui/`, broken PNG: load error with the file); a halted
script's tree is removed; the tree is gone after travel. Visual baselines: two new R1 scenes
`hud_pack` (each kind at each anchor) and `hud_pack_scaled` (UI scale 2), accepted by `build
images`. Hostile rows (in M52c's suite): an element tree of 10 000 adds (denied at 256),
`hud.set` on another pack's element handle (refused), an image path `../../` (load error), a
text of 1 MiB (refused).

**Benchmark.** `client-scripts` (M52c) gains version 2: each of its 8 packs keeps 128
elements and changes 32 a tick; limit: the HUD's share of the frame (`ui` metric scope) p99
under 0.5 ms of CPU, and `frame` p99 within 10% of `views`.

**Open questions for the owner** (this row waits for 1 and 2; 3 and 4 do not block):

1. May creators colour their elements (any colour, or only the Theme's named colours, or a
   palette)? Today every engine element takes its colours from the `Theme`.
2. Where may a pack's HUD sit: anywhere on screen, or only in zones that never cover the
   engine's own HUD (crosshair, hotbar, health, chat feed)? May an experience hide engine HUD
   elements (the hotbar, health) for itself?
3. Which element kinds beyond the engine's existing widgets (a bar or meter, a timer, a
   minimap-like image is excluded by the plan's no-minimap rule) should creators have?
4. May packs ship their own fonts, or is the engine's font the only one?

**Left out:** interaction, focus and menus (M52g); animation of elements beyond what the
script sets each tick; 3D elements in the world (name tags over entities, waypoints).

**Exit check:** (once unblocked) the tests and the two visual baselines pass; `client-scripts`
version 2 within its limits in CI's Profiling step; the suite, `build check`; CI green.

**Check by hand:** in a world with `client/testdata/packs/hud_demo` installed and granted,
the demo's elements sit at their anchors at UI scales 1 and 2 and disappear with F1.
