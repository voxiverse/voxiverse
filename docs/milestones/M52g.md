# M52g: the creator UI toolkit, part two (menus, lists and the creator's own inventory views)

**Blocked until the owner answers the open questions below.**

**Why.** The owner's decision of 2026-10-30 (#83): creators make their own menus and their
own inventories, on client scripts and the engine's own UI. A menu is interactive (mouse,
keyboard and pad, as every engine screen since M42); an inventory view shows slots whose
contents the **server** owns, so moving items stays a server-checked request that the
ledger balances.

**What this builds on:** M52f (`Hud_Tree`, the element kinds, anchors, budgets, images),
M52c and M52d (client scripts, channels: a menu's choice reaches the server as a channel
message), M52b (server scripts, `item.give`/`item.take`), the engine UI's interaction
(`interact`, `button`, `checkbox`, `slider`, `choice`, `list_nav`, `text_input`,
`tooltip`, `keep_focus_visible`, `nav_pick`, `consume_nav`, `default_focus`, the on-screen
keyboard: M42), overlays (`client/overlay.odin`: `Overlay`, `OVERLAY_INFO` with `takes`,
`overlay_open`/`close`, `escape`, `draw_overlays`), the prompt bar (`client/prompts.odin`),
containers and their requests (`client/menu_inventory.odin`: `stack_slot`, `Inventory_View`,
`inventory_mouse`, `inventory_pad`, every move through `session_inventory_do(s,
game.Inventory_Action)`; the server's `Inventory_Action` handling, block-entity containers
from M48b, M31's ledger and audit).

**The design (engineering, decided):**

- **A pack menu is an engine overlay.** One new `Overlay.Pack_Menu` (with `OVERLAY_INFO`
  taking keyboard and mouse like the inventory) draws the open pack's menu tree on
  `Layer.Modal` with the engine's backdrop. One pack menu open at a time; opening one closes
  another pack's. Escape and the pad's Back always close it (the engine's `escape`, never the
  script's), and the script gets `ui_closed`. Focus, navigation, the prompt bar and the
  on-screen keyboard are the engine's: a pack menu works with a pad the day it is written.
- **Interactive kinds** (added to M52f's): `button`, `checkbox`, `slider`, `choice`,
  `list` (`list_nav`), `text_field` (`text_input`, single line; its text reaches the script
  only on submit, as `ui_submit`), `tooltip` on any element. Each maps to the existing
  procedure; events `ui_click`, `ui_change`, `ui_submit`, `ui_closed` carry the element and
  its value, on the client tick after the frame they happened in.
- **A menu is a request, not an authority.** What a menu does on the server it does through
  the pack's channel (M52d) and the server script's own capabilities. No new server path.
- **Inventory views.** A pack declares containers in data (`data/containers/<name>.json`:
  slot count and the pack's layout as rows of slots; registry kind `Container_Def`, M47's
  rules), owned by the server per character or per block entity (M48b's lifecycle). The
  client shows one with the `slots` element (`stack_slot` for each, the engine's drag and
  drop, shift-click, pad cursor, tooltips and details panel, i.e. `inventory_mouse` and
  `inventory_pad` reused by passing a layout instead of `inventory_layout`'s fixed one).
  Every move is the existing `Inventory_Action` with the container named; the server checks
  it exactly as a chest's (M30, M48b) and the ledger sees moves, never creation. A server
  script opens one for a player with `container.open(player, name [, block])` (capability
  `container`, server side) and reads and writes its contents through `item.give`/`item.take`
  (already budgeted). A client script can only show the view the server opened.
- **Budgets** (engine ceilings): one open pack menu; 256 elements in it (M52f's count);
  containers: the slot count is the owner's question 2; 8 container kinds a pack.

**Order of the steps:**

1. `Overlay.Pack_Menu`, the interactive kinds, events, Escape and Back, pad navigation.
2. `Container_Def` in the registry; per-character and block-entity containers on the server;
   `container.open`; the inventory view with a data layout.
3. Tests; visual baselines.

**Tests:** UI tests drive a pack menu with mouse, keyboard and pad events only
(`test_pack_menu_by_pad`, the way `test_menus_with_a_pad` drives the engine's): every kind
reached, changed and submitted; Escape and Back close it and the script sees `ui_closed`; a
script cannot keep it open (a re-open in the same tick as `ui_closed` is denied until the
next client tick, so Escape always wins one frame); the on-screen keyboard on a
`text_field`. Server: a pack container's moves over UDP with loss between two players agree
with the server; refused moves roll back on the client; the ledger audit balances after a
fuzz of 4 000 random container actions (M31's fuzz pattern); a container of a removed block
spills like a chest. Visual baselines: `pack_menu` and `pack_container` scenes. Hostile rows
(M52c's suite): opening a menu every tick (one open; throttled), a 10 000-element menu
(denied), a forged `Inventory_Action` naming a container the server never opened for that
player (refused at the edge), `container.open` of another pack's container (refused).

**Open questions for the owner** (this row waits for 1 and 2):

1. Where do pack menus live: only as their own overlays opened by the experience, or also as
   sections of the player menu (`SECTIONS`: Inventory, Statistics, and the hidden Map,
   Journal, Character, Atlas)? May a pack replace the engine's inventory screen in its
   experience?
2. How many slots may a creator's container have, and may containers hold the engine's
   equipment slots (head, chest, legs, feet, offhand)?
3. (Does not block.) Should a pack menu pause a singleplayer world like the game menu does?
   Until answered it does not (the inventory does not).

**Left out:** multi-line text and a script editor (M54e); drag and drop between pack menus and
the world; crafting grids (recipes are data, M47; a crafting view is content).

**Exit check:** (once unblocked) the tests and visual baselines pass; the ledger balances after
the fuzz; the suite, `build check`, `build determinism`; CI green.

**Check by hand:** with `client/testdata/packs/menu_demo` installed, open its menu with the
pack's action and walk it with a controller only: every control reachable, Back closes it.
