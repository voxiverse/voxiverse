# M53b: dialogue and prompts, the placeholder death screen, spawners and encounters, the UDP exit

The second part of M53: its design, names and files are in [M53.md](M53.md); read it first.
Its *Mechanism only* paragraph binds this part too: death and respawn are the owner's to
design, so the death screen stays the agreed placeholder.

*Dialogue* (`data/dialogue/*.txt`):

```
dialogue elder {
  speaker = "Elder Ama"
  node start {
    text = "Travellers again. Will you help an old woman?"
    choice "I will." { if { quest_state demo:village = unknown } do { quest_start demo:village } goto = bye }
    choice "I found the well." { if { quest_stage demo:village = 1 } goto = well }
    choice "The den is quiet now." { if { quest_stage demo:village = 3 } goto = done }
    choice "Goodbye." { goto = end }
  }
  node well { text = "Then the den is next." choice "On my way." { goto = end } }
  node done { text = "Thank you. Take this." do { quest_advance demo:village } choice "Farewell." { goto = end } }
  node bye { text = "Find the old well first." choice "Goodbye." { goto = end } }
}
```

- A node: `title` (optional), `text`, up to 6 choices; `do { }` runs when the node is
  reached. A choice: a label (at most 96 bytes), optional `if { conditions }` (hidden
  when false, evaluated when the node is sent), `do { }`, `goto = <node>` or `end`
  (closes), and `leave = true` (client side: the client leaves the world after
  answering). Dialogue options: `style = dialogue`
  (default) or `screen`; `closable = true` (default; Escape or Back answers -1 and
  closes) or false; `range = 8` (blocks from the entity that opened it, when one did:
  further away closes it).
- A prompt is a one-node dialogue made by a script (`ui.prompt(player, {speaker, title,
  text, choices = {...}, style, closable})` returns a prompt id; the answer comes as
  M52's `prompt_answer`) or by data (`prompt "Open the gate?" { choice "Yes" { do { ... }
  } choice "No" { goto = end } }` as an action).
- The server keeps one open prompt per player (`Client.prompt`: `seq: u32` (a new one for
  every node sent), the source (dialogue id and node, or the script), the visible choices'
  indices, the entity and its position). A new prompt replaces an open one (the replaced
  one answers -1 to its source). It closes on travel, leave, death (the placeholder death
  screen replaces it) and range.
- New state kind `Prompt` (reliable, singleton, M39; fields `seq: u32, style: u8,
  closable: bool, speaker: string net:"max=64", title: string net:"max=64", text: string
  net:"max=1024", choices: string net:"max=768"`: one line per visible choice, `-` or `L`
  (leave) then a space then the label; an empty `text` with `seq` 0 means closed). Text
  fields are formatted on the server.
- New client message `Answer {seq: u32, choice: i8}` (appended to `Client_Kind`;
  `PROTOCOL_VERSION` +1). The server accepts it only for the open prompt's `seq` and a
  choice in range or -1 when closable; anything else is refused (logged at `debug`, not a
  disconnect: an answer can cross a replaced prompt). An answer runs the choice's `do`,
  then `goto`; reaching a node raises the `dialogue` trigger and `talk` objectives.
- `deliver <quest> <objective>` (a choice action): takes the objective's items and marks
  it done; with `else { }` when the player holds too few.
- Client (`client/prompt_ui.odin`): `Overlay.Prompt` (`takes = {.Keyboard, .Mouse}`,
  `in_game = true`; the world goes on; not over the game menu). `dialogue` style: a panel
  at the bottom centre, 640 px wide at UI scale 1, the speaker in the theme's accent
  colour, the text wrapped, the choices as a column of buttons numbered 1-6 (keys 1-6 pick
  them). `screen` style: the backdrop dims the whole screen, the title large in the centre,
  the text under it, the buttons centred below. Focus starts on the first choice; M42's
  navigation moves it (up and down), confirm answers, Back and Escape answer -1 when
  closable and do nothing otherwise (Escape still opens the game menu over a screen-style
  prompt, so Leave stays reachable). Prompt glyphs follow the last device (M42). Opening
  and closing follow the record; the client sends `Answer` once and greys the buttons
  until the next record.

*The death screen: the agreed placeholder, as data.*

- It is a Respawn button and nothing else: no death message, no time, day or place, no
  Title-screen choice, no penalty, no timer, no new art. The words are the minimum the
  button needs. `die` does what it does today (the inventory dropped by `death_drops`, the
  `Player_Died` event) and then, instead of waking at once, sets `Client.dead` and opens
  the base pack's dialogue `base:death` for the player:

  ```
  dialogue death {
    style = screen
    closable = false
    node start {
      title = "You died"
      choice "Respawn" { do { respawn } goto = end }
    }
  }
  ```

  (A pack's override of `base:death` is M47's general override and is not a feature here;
  no test or spec makes death text a thing to customise.)
- While dead: the server simulates the player with an empty input so prediction still
  matches; edits, attacks, uses, fire and inventory requests are refused; no damage;
  `game.Health` gains `dead: bool` (a field only: M39 sends it). The HUD is not
  redesigned: the screen covers it.
- `respawn` (the action, valid only while dead): exactly what `die` did at its end before
  this milestone: full health, `dead` cleared, `land_at_spawn(remember = false)`, the
  prompt closed, `player_respawn` raised. Leaving while dead respawns the character
  before it is saved, so it joins alive at the spawn. Tests that relied on the instant
  respawn (`server/health_test.odin`) answer the prompt.

*Spawners* (`data/spawner/*.txt`):

```
spawner den {
  kind = base:sheep
  region = demo:den
  tag = den
  max_alive = 3
  every = 100                # ticks between spawns while fewer are alive
  total = 0                  # 0: unlimited
  active = manual            # always | manual | near <blocks>
  min_distance = 6           # from any player
  on_empty { say "The den is quiet." }
}
```

- Each attempt picks a column in the region with the gameplay RNG, takes the region's
  ground there with `game.landing_spot`, requires the chunk loaded and `min_distance` from
  every player; 8 tries, then the next `every`. Spawns through `entity.spawn` of the pack
  (its kinds, alive and per-second budgets) with `Tags {tag}`; the spawner keeps its
  handles. `near N`: active while a player is within N blocks of the region. `on_empty`
  runs (and `spawner_empty` fires) when its last entity dies after at least one spawned.
  State in `Gameplay_State` (active, spawned total, next tick, handles); entities persist
  with M50's.

*Encounters* (`data/encounter/*.txt`): `encounter ambush { region = demo:den  waves {
wave { spawn base:sheep 3 tag ambush } wave { delay 60  spawn base:sheep 5 tag ambush } }
timeout = 3600  on_cleared { loot demo:reward }  on_failed { message "They got away." }
reset_after = 6000 }`. Started by `encounter_start` (or `start = enter` on a region
entry); participants are the players in the region at the start; a wave starts when the
previous one is all dead (after its `delay`); the last wave dead is cleared (`on_cleared`
for each participant, `encounter_cleared` trigger); past `timeout` or with no
participant in the region for 600 ticks it fails (its entities removed, `on_failed`).
States `Idle, Running(wave, handles, started), Cleared, Failed`, back to `Idle` after
`reset_after`. Saved in `Gameplay_State`.

*The quest tracker.* The HUD (`game_screen`) draws the `Quests` record at the top right:
up to three quests, the title in the accent colour, the stage text, the progress in a
dim colour; nothing when empty; hidden with the rest of the HUD while dead or paused.
Through the theme (M40), so `theme_scope` reaches it.

*The two-player UDP scenario* (`server/gameplay_net_test.odin`,
`test_quest_chain_two_players`, on M39's `Net_Client` helpers, a listening server with
cheats for alice only, the demo pack granted `all`; `Net_Client` learns the `Prompt` and
`Quests` records and sends `Answer`):

1. Both join; the elder is there within 30 ticks (an `Entity` record of kind
   `demo:elder`).
2. alice uses the elder: a `Prompt` arrives with four choices filtered to "I will." and
   "Goodbye."; she answers 0; her `Quests` record shows "Find the old well"; bob's shows
   nothing (quests are per character).
3. alice teleports into `demo:well` (`/tp`): the stage becomes "Drive off the sheep of
   the den 0/3"; the den spawns three sheep tagged `den`.
4. bob kills two den sheep (`Attack` until `Entity_Died`): alice's progress stays 0/3.
   alice kills three (the spawner refills to three): 3/3, the stage becomes "Return to
   the elder".
5. alice uses the elder, answers "The den is quiet now.", then "Farewell.": the quest is
   completed, her inventory holds the reward's rolls (the exact items for the test's
   seed), the world chat shows "[Demo Quests] alice helped the elder." to both.
6. bob runs `/bonus` five times: four loot rolls arrive, the fifth gives the notice "The
   ruin is empty for now."
7. alice leaves and joins again: her quest reads as completed (the elder offers only
   "Goodbye."); bob is unaffected.
8. alice runs `/gamemode survival`: the base mode lists no rules, so both clients'
   `Rules` records do not change; both see the announcement. (`/gamemode demo:adventure`
   changes exactly that test mode's rules.)
9. alice runs `/damage alice 100 base:fall`: her `Prompt` is the placeholder death
   screen with one choice; she answers "Respawn" and is at the spawn with full health
   within 30 ticks; bob's chat shows nothing new. A test pack's `death` trigger on
   `demo:zap` ran its action for a `/damage` with that cause.
10. The ledger audit balances, with `Loot` and `Script_Give` entries equal to what the
    clients' inventories gained.

Each step waits with `net_wait` (10 s at most); the test runs under 60 s.

**Order of the steps (M53b):**

1. The `Prompt` record, `Answer`, `Client.prompt`, dialogue data and runtime, `deliver`,
   `talk` objectives, M52's `ui.prompt` sending the record instead of a notice.
2. `client/prompt_ui.odin` with both styles, keys 1-6 and pad navigation; its UI test.
3. The dead state, `respawn`, the placeholder `base:death`, `Health.dead`; `health_test` updated.
4. Spawners, then encounters, their state in `Gameplay_State`.
5. The quest tracker.
6. The demo pack completed and the UDP scenario.

**Tests (M53b):**

- Dialogue: hidden choices by condition; `goto`, `end`, `do`; a stale `seq`, an
  out-of-range choice and -1 on a non-closable prompt refused; replaced prompt answers -1
  to its source; range closes; `deliver` with too few runs `else`.
- `client/menus_test.odin` (M42's UI test): the prompt overlay driven by pad events only
  (move, confirm, back) in both styles; keys 1-6; the death screen ignores Back and has one button.
- Death screen: dying opens the placeholder screen with one Respawn button; respawn
  restores health and position exactly as the pre-M53b instant respawn did (the same
  asserts as before); while dead edits and attacks are refused and prediction stays exact
  (`server/latency_test.odin`'s desync check over a death); leaving while dead rejoins
  alive at the spawn; the screen holds no message, time or place, asserted.
- Spawners: max alive, every, total, `near`, `min_distance`, `on_empty`; state through
  save and load; encounters: waves in order, cleared, timeout, failure by absence, reset.
- `test_quest_chain_two_players` above.

**Exit check (M53b, the milestone's):** `test_quest_chain_two_players` passes over UDP
(a quest chain, a spawner, a loot table and a dialogue in data only); dying from each
base cause (`/damage` per cause) opens the placeholder screen and Respawn does what the instant respawn did; the
section's tests; the whole suite, `build determinism`, `build check`; CI green.

**Check by hand (M53b):** in singleplayer, install the demo pack in a new
world (`/pack grant demo all`), talk to the elder with the mouse and then with a pad, do
the chain, die with `/damage @s 100 base:fall` and press Respawn; the dialogue panel and the
placeholder death screen read well at UI scales 1 and 2, the quest tracker does not cover the chat.

**Left out (M53 and M53b):** AI beyond today's (spawned sheep behave as sheep; the AI
framework is the next tier); hunger, break times, drowning, lava and void damage (no causes exist for them; the
mechanics are content, and with survival's rules, death penalties, death messages and the
respawn point they are the owner's to design); parties and shared quests; a quest log
screen beyond the tracker (UI v2); localization of pack text; entity drops by loot table;
moderation of pack text (M54); item origin tags.
