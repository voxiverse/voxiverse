# M54b: bots, the dry run and staged rollout

**Why.** Static checks cannot see whether a quest can be finished by playing, whether an
item faucet runs away once triggers interact, or whether a script's cost under real events
fits the budget. M38 left "several deterministic players" to a bot harness. M55b needs 200
bots for load, and M55's hostile client is a bot too. So the harness is built once here: headless
clients on M38's stepped server, a dry run that plays a candidate pack and reports as JSON,
and staged installation and revert on M45's journal.

**Layout.** Added to PLAN.md's Layout:

```
bot/        headless clients: a link (pipe or UDP), the replica, behaviours (tests, dry runs, load)
```

`bot/` imports `base`, `game` and `netcode` (never `server`), so bots can run in a process
of their own (M55b).

**Design.**

*The bot* (`bot/bot.odin`): M38's mirror client (`server/determinism_test.odin`'s `Mirror`)
grown into a package. It has:

- `Bot_Link :: union {game.Endpoint, ^netcode.Link}`;
- `name`, `key` (`bot_key(name)`: an `Account_Key` from the seed `SHA-256("voxiverse bot
  v1" || name)`, the same on every run);
- `state` (`Connecting`, `Proving`, `Playing`, `Rejected`, with the server's reason);
- `schema`, `rx: game.Receiver` (M39's records: its own player, other players, entities,
  inventory, rules, clock, and M53's quest, objective and dialogue records);
- `chunks` (kept only with `keep_chunks`: a map from chunk position to block array, as the
  mirror's);
- `prediction: Maybe(game.Prediction)` (with `predict`: M38's reconciling client);
- `seq`, `server_tick`;
- `notices` (the last 32);
- `rng: base.Rng` (seeded from the name);
- `behaviour: Behaviour`;
- `stats: Bot_Stats` (`inputs`, `bytes_in`, `bytes_out`, `edits_refused`, `rejected`).

The procs:

- `bot_init(b, name, link, keep_chunks, predict, allocator)`;
- `bot_pump(b, now)` (what arrived, applied);
- `bot_step(b)` (one input: the behaviour decides it and any actions, which are sent);
- `bot_destroy(b)`.

The verbs behaviours use: `bot_move`, `bot_look_at`, `bot_break`, `bot_place`, `bot_attack`,
`bot_use_entity`, `bot_use_block`, `bot_command`, `bot_chat`, `bot_choose` (a dialogue
option), `bot_inventory`. Each builds the message the client would send, its `after` set to
the last input sent.

`Behaviour :: struct {name: string, data: rawptr, step: proc(b: ^Bot, data: rawptr)}`.
Shipped behaviours:

- `script`: M38's pure function of the tick. The determinism session's script moves here
  unchanged, as `bot.determinism_script`.
- `idle`.
- `explorer`, for dry runs (below).
- `wander`, M55b's load behaviour, written there.
- `hostile`, written in M55.

*Several in-process players.*

- `server.Config.bots: []game.Endpoint` adds in-process seats after the local one. `Local`
  becomes `Local :: struct {index: int}`.
- `receive_messages` reads the pipes in index order, so a stepped server stays a function
  of what was sent before each `step`.
- `send_bytes` and `send_message` pick the pipe by index.
- `determinism_test.odin` and `bandwidth_test.odin` move onto `bot.Bot`. Their hashes and
  `assets/baselines/net/bandwidth.txt` must not change: that is the proof the move is
  faithful.

*The explorer* (`dedicated/explorer.odin`): it needs the pack's data, so it lives beside the
dry run, not in `bot/`.

- Each step it lists **affordances**: things it could do now, each a key (`dialogue:<node>:<option>`,
  `reach:<region>`, `hunt:<entity kind>`, `use_entity:<kind>`, `use_block:<kind>`,
  `collect:<item>`, `command:<trigger>`, `wait`). They come from:
  - an open dialogue prompt: each option;
  - the bot's active objectives (M53's records), joined with their definitions in the pack;
  - entities with a use, in view;
  - blocks with a use within 32 blocks, from the chunks it keeps;
  - region and command triggers in the pack that it has not fired yet.
- It picks the first of, in this order:
  1. dialogue options it has not chosen yet;
  2. affordances serving an active objective, fewest attempts first;
  3. untried trigger affordances;
  4. a random wander.
- It acts with the bot verbs. To get somewhere it uses `/tp @s x y z` (the `bot` role in a
  dry run has `teleport.tp`, `chat.send` and `world.edit`, nothing on items or rules), lands
  next to the target, then walks the last blocks: there is no navigation yet.
- `collect:<item>` breaks a block, or kills or uses an entity, that the registry and loot
  tables say drop it. It never `/give`s, so the ledger sees only the pack's faucets and the
  world's.
- An attempt ends at success or after 600 ticks. Attempts are counted per key.

*The dry run* (`dedicated/dryrun.odin`).

- The world: a stepped server (no threads, `workers = 0`), view radius 4, height 2. It is a
  scratch world from `--address` and `--seed` (defaults: the base pack's default world,
  seed 54), or a copy of a real world: `--world <universe> <address>` copies its directory
  to a temporary one through M46's export.
- Rules: `game.rules_still()` except what the pack's mode sets, `no_sheep` unless the pack
  relies on natural spawns. The pack is installed into that world as M54b's install does,
  with its own grants (the manifest's requests, capped at M52's ceilings).
- Bots: `--bots` (default 4), each `explorer`, each with its own name, each joining 60
  ticks after the previous one.
- Length: `--ticks` (default 18 000, ten minutes of game time).
- The same pack, seed and options give the same report, timings aside.
- Process model: `voxiverse-server pack dryrun <dir> ...` is a supervisor.
  - It verifies (M54) and validates first. A failed validation ends there, with the
    validation findings in the report.
  - It then runs itself as a child, `voxiverse-server pack dryrun-child <args>`, through
    `os.process_start`.
  - Every 600 ticks the child writes its report so far to `<tmp>/progress.json` (replaced by
    rename, never torn) and its log to `<tmp>/child.log`.
  - A child that exits with a non-zero code, dies of a signal, or runs past
    `max(120 s, 50 ms × ticks)` of wall time (killed) gives `engine.crash` or
    `engine.timeout`. Those findings carry the exit code or signal, the last tick reached
    and the last 50 log lines. The report is otherwise the last progress.
  - A crash is an engine bug, never a pack's right, so it fails the verdict and the report
    says so ("an engine bug: report it").
  - DEV builds take `--crash-at <tick>` (a deliberate panic) for the test of this path.
- Measured, from the server side (in process, the child reads the server's state directly;
  bots are not trusted to report progress):
  - Crashes and timeouts (above). `script.error`: M51 runtime errors per script, the first
    three messages with their lines.
  - Budgets: per script, from M52's usage counters: instructions per tick (p99, max),
    memory (max), edits, spawns and messages per tick (max), and suspensions. Per world:
    tick time p50, p99 and max (CPU time on the stepped server), edits and spawns per tick.
    Findings:
    - `budget.suspended`: any suspension is an error;
    - `budget.near`: p99 over 80% of a budget, a warning;
    - `tick.over_budget`: tick p99 over `game.TICK_DURATION`, an error.
  - The ledger: M31's audit every 600 ticks and at the end. Any difference is
    `economy.imbalance`, with item, held and ledger. Items created, by item, reason and
    origin, give a rate per game hour. `economy.faucet` is an item created by the pack's
    origin over its declared `faucets` cap (per character, or per hour scaled to the run's
    length), or over the world's cap. `economy.faucet_capped` is a warning: M52's cap held,
    but the pack tried to exceed it.
  - Progress: per bot, the tick of its last progress. Progress is: an objective advanced or
    completed, a quest started or completed, a dialogue node reached the first time, a
    first item of a kind obtained, a region first entered. Findings:
    - `progress.softlock`: a bot has an active, unfinished quest, no progress for 6 000
      ticks (200 s), and has tried every affordance it has at least twice. The finding
      gives the bot, the quest, the objective, the last progress tick and the affordances
      with their attempt counts.
    - `progress.loop`: one bot completed one quest more than `repeat.max` times, or more
      than 6 times per game hour if the quest does not say. Also any trigger that M52
      suspended for firing over budget.
    - `progress.unreached`: a quest no bot started, a warning.
  - Text: strings checked at run time and refused (`text.refused_runtime`, with origin and
    category).
- The report (`dryrun-report.schema.json`): the validation report's fields, and

```json
{"report": "dryrun", "report_version": 1,
 "config": {"seed": 54, "address": "...", "ticks": 18000, "bots": 4, "world": "scratch" | "copy"},
 "verdict": "pass" | "fail",
 "findings": [{"code": "progress.softlock", "severity": "error", "tick": 9120, "bot": "bot2",
   "quest": "lighthouse:wool", "objective": "bring_wool", "message": "...", "fix": "...", "docs": "..."}],
 "crash": null | {"exit_code": 0, "signal": "", "tick": 0, "log_tail": ["..."]},
 "budgets": {"tick_ms": {"p50": 0, "p99": 0, "max": 0, "budget": 33.3},
   "scripts": [{"id": "lighthouse:lamp", "instructions": {"p99": 0, "max": 0, "budget": 0},
     "memory": {"max": 0, "budget": 0}, "suspensions": 0, "errors": 0}],
   "world": {"edits_per_tick_max": 0, "spawns_per_tick_max": 0}},
 "ledger": {"balanced": true, "audits": 30,
   "faucets": [{"item": "lighthouse:lantern", "origin": "lighthouse", "count": 4, "per_hour": 24, "cap": "1 per character"}]},
 "progress": {"quests": [{"id": "...", "started": 4, "completed": 4, "completions_max": 1}],
   "bots": [{"name": "bot1", "last_progress_tick": 0, "stuck": false,
     "tried": [{"affordance": "dialogue:keeper:0:1", "attempts": 2}]}]},
 "text": {"checked": 0, "refused": [{"origin": "lighthouse:lamp", "use": "notice", "category": "word"}]}}
```

  - `--out <file>` writes it. `--json` prints it, otherwise a summary in the human format.
  - Exit codes: 0 pass, 1 fail, 2 usage or I/O, 3 the child crashed or timed out.
  - `docs/agent/dryrun.md` explains each section and each finding.

*Staged rollout* (`server/pack_install.odin`). A pack is installed for one world at a time.

- `/pack install <dir under incoming/> <world address>`, and offline
  `voxiverse-server pack install <dir> --universe <dir> --world <address>`. Both need
  `server.packs`. The steps:
  1. Verify against `trust.cfg`.
  2. Validate with that world's grants.
  3. If `universe.cfg` has `packs.require_dryrun 1`, refuse unless
     `<dir>/dryrun.json` exists, has verdict `pass`, the same pack hash and this engine's
     version. The default is 0, and 1 is recommended for servers that take agent packs.
  4. Copy the pack to `<universe>/packs/<namespace>@<version>/`, read-only afterwards
     (re-verified at every start, M54).
  5. At the next tick boundary: write a journal marker `Pack_Install {pack, version,
     hash}` (M45's journal gains this entry kind) and record the world's state hash. Add the
     pack to the world's `packs` list in `worlds/<id>/world.cfg` and activate its behaviour
     (scripts and gameplay data, M52-M53, grants as validated). Rollout is of behaviour, per
     world and live; a pack that also carries content (blocks, items, kinds: universe-wide,
     M47) is first installed in the universe (`universe.cfg`, a restart), and the dry run
     says so in its report (`needs_universe_install`).
- Every effect of the pack is journaled with a cause naming the pack. M45 and M52 give every
  script effect a cause. M54b uses the action's actor (`Script`, named `<pack>:<script>`, M45 and M52) to find a pack's effects
  and that M53's data actions use it too. Items the pack creates carry its origin (M52's
  ledger origin).
- `worlds/<id>/packs.jsonl` records each step, one line each: `{"t": <unix ms>, "tick": n,
  "action": "install" | "revert", "pack": "lighthouse", "version": "1.0.0", "hash": "...",
  "key": "...", "by": "<character or console>", "world_hash": "...", "journal": <marker
  sequence>}`. A revert's line also has `"undone": {"blocks": n, "entities": n, "items": n,
  "quests": n, "conflicts": n}`. `/pack history <world>` prints them. `/pack list [world]`
  lists installed packs, their keys and revoked-key warnings.
- `/pack revert <namespace> <world address>` (`server.packs`), at a tick boundary:
  1. Deactivate the pack: scripts stopped, triggers and spawners off, no new effects.
  2. M45's rollback by cause (`pack = <namespace>`) since the install marker. This undoes
     block edits, entity spawns and removals, and container changes. A block that a
     non-pack cause changed after the pack did is left as it is and counted in `conflicts`,
     with its position logged.
  3. Items with the pack's origin are removed from the world's characters' inventories,
     containers and dropped stacks, through the ledger with the reason `Revert`.
  4. The pack's per-character quest state for characters in this world is deleted.
  5. It comes off the world's `packs` list. Blocks of the pack's own kinds left in the world
     (placed by players) become M47's missing-content placeholder, and are counted.
  6. The journal gets a `Pack_Revert` marker, and `packs.jsonl` the line above.
- If no non-pack cause changed the world in between, the world's state hash after a revert
  equals the hash recorded at install. That is the exit check. In general the guarantee is
  that every journaled effect of the pack is undone, and every player's own effect stays.
- An update is a revert and then an install. Keeping script state across versions is left
  out.

*The example pack, finished* (`docs/agent/examples/lighthouse/`): agent-style, small, and
touching every part of the pipeline.

- A keeper entity (M50 kind, M53 dialogue) by a lighthouse region near the world spawn.
- A quest chain: talk to the keeper, shear three wool (M23 sheep, a spawner of four near the
  lighthouse), bring them to the lighthouse region, talk again.
- The reward: one `lighthouse:lantern` item (a pack block, M48 shape), with the faucet
  `per_character: 1`.
- A script `scripts/lamp.vxs` (capability `blocks.edit` in the lighthouse's region, a small
  budget) that lights the lamp blocks when the quest completes, and sends a notice built at
  run time (moderated).
- A `death` trigger (M53's mechanism) on a cause of the pack's own, saying one line of the pack's own: the base pack has no death messages.

Its `pack.json` declares exactly what that uses. The tests sign it with a key made in the
test. The repository commits no private key and no `pack.sig`.

**The order of the steps:**

1. `bot/` from the mirror, `Config.bots`, multi-pipe receive. The determinism and bandwidth
   tests on `bot.Bot` with unchanged hashes and baseline.
2. The explorer.
3. The dry-run child: measurements, findings, progress file, report.
4. The supervisor, its crash and timeout paths, `pack dryrun`, `dryrun-report.schema.json`
   (through `build agent-docs`), `docs/agent/dryrun.md`.
5. Install, journal markers, `packs.jsonl`, `/pack list|history`.
6. Revert.
7. The lighthouse pack finished, the testdata packs, the end-to-end test.

If the session must split, the remainder is M54c: steps 5 to 7, with the revert test and the
end-to-end test as its exit check.

**Left out:**

- Navigation (bots teleport). Bots that fight well. Bots that use M53 scripts as players
  would through a UI.
- Running dry runs in parallel, and dry runs over many seeds (one seed per run; the agent
  service may run several).
- Updating a pack in place while keeping script state. Removing a pack's content kinds from
  a world.
- Rolling back players' own effects with a pack.
- Network upload of packs.

**Tests:**

- `bot/bot_test.odin`: a bot joins a stepped server over a pipe and is `Playing`. `bot_key`
  is stable. A bot with `predict` sees no corrections over 600 quiet ticks.
- `server/determinism_test.odin` and `bandwidth_test.odin`, on bots: unchanged roots and
  baseline. New, `test_four_bots_deterministic`: two side-by-side stepped servers with four
  `script` bots each (different scripts) agree every tick for 2 000 ticks.
- `dedicated/dryrun_test.odin`, each a stepped dry run of a pack under
  `agent/testdata/dryrun/` (3 000 to 6 000 ticks, 2 bots, signed in the test):
  - `lighthouse` (the example): verdict `pass`, every quest completed by every bot,
    ledger balanced, no suspension, its lantern faucet exactly 1 per bot.
  - `loop`: a repeatable quest without cooldown whose completion restarts it and gives an
    emerald. It passes static validation because it declares `repeat.max: 1000` and a faucet
    `per_hour: 100000`. It is caught by `progress.loop` and `economy.faucet` (over the
    world's cap), and the verdict is `fail`.
  - `faucet`: a time trigger every tick giving a diamond, with a declared `per_hour` the
    world's grants allow. It is caught by `economy.faucet_capped` or `economy.faucet` and
    by `budget.suspended`.
  - `softlock`: the quest's NPC is spawned by a trigger that fires once, at tick 100, and
    despawns at 200, and the quest starts at 300. The static checks pass (the NPC kind has
    a spawner). It is caught by `progress.softlock`, naming the quest and the objective.
  - `crash` (DEV, `--crash-at 500`): `engine.crash`, exit code 3, `crash.tick` 500 or the
    last progress before it, a log tail.
  - The same pack and seed twice give byte-identical reports once timing fields are
    removed.
- `server/pack_install_test.odin`:
  - installing an unsigned pack where `packs.unsigned` is 0 is refused;
  - a forged and an altered pack are refused at install;
  - `require_dryrun` refuses a missing report and a report for another hash;
  - install writes the marker and the `packs.jsonl` line;
  - `test_revert_restores_hash`: a still world. The hash is taken, the lighthouse pack is
    installed, the quest is completed by one bot, so the lamp edits, the spawner's sheep,
    the lantern and the quest state all exist. Revert, and the world's state hash equals the
    install hash, the bot's inventory has no lantern, and the ledger audit balances;
  - a conflict: a player breaks a lamp block after the pack lit it. Revert leaves the
    player's air, and counts one conflict.
- `dedicated` end-to-end, `test_pack_pipeline_end_to_end`. In a temporary directory:
  - `pack keygen`;
  - `pack sign` the lighthouse;
  - `pack verify` with a trust list holding the key;
  - `pack check --json`, verdict `pass`;
  - `pack dryrun --json --ticks 6000 --bots 2`, verdict `pass`, the report valid under
    `dryrun-report.schema.json` (M54's schema checker);
  - `pack install` into a universe;
  - a server started on it, two bots over UDP finishing the quest;
  - `/pack revert`, and the world's hash equals the install hash.

**Exit check:**

- `test_pack_pipeline_end_to_end` passes. An altered and a forged pack are refused at
  install.
- The `loop` and `faucet` dry runs fail with their codes. The `softlock` dry run names its
  quest.
- `test_revert_restores_hash` passes. The determinism and bandwidth tests are unchanged on
  the bot harness.
- The suite, `build check`, and CI green on the three OSes.

**Check by hand:**

- Read one dry-run report of the lighthouse pack. It tells you what the bots did and why it
  passed, without the source.
