# M54b: bots (a headless client package on the harness, the test clients folded into it)

The first of three rows (M54b, [M54j](M54j.md), [M54k](M54k.md); split by #88 at the joints
the old M54b spec already had: its steps 1, 2-4 and 5-7). In the order of 2026-10-30 it
comes after M49d; M54j and M54k follow it, then M55.

**Why.** Static checks cannot see whether a quest can be finished by playing, whether an
item faucet runs away once triggers interact, or whether a script's cost under real events
fits the budget: M54j's dry run plays a pack with bots. M55d's hostile client, M55e's 200-bot
load run and Q7's soak are bots too. Today there are five clients that are not the game's, each
written for one use: the mirror (`Mirror`,
`server/determinism_test.odin`: on the pipe, predicts and reconciles), the network client
(`Net_Client`, `server/net_test.odin`: a `netcode.Link` on the harness's `Simnet`, about 70
fields of what tests look at) and the scenario runner's `Bot` (`server/scenario_test.odin`, a
`Net_Client` with sequence numbers) and the LAN party run's `Bot` (`server/party_test.odin`,
a `Net_Client` that walks and fights), all private to `server`'s tests; and the benchmark's
`Bot` (`dedicated/bench.odin`, `build bench server` and `party`: the real handshake over UDP
on the loopback, flying out or fighting, `bot_input` and `party_input`). This row makes one package of the protocol part they
share, which a process of its own can run (M55e), and moves the five onto it with every
baseline unchanged: that is the proof the move is faithful.

## Checked against the code (2026-10-30, #88; corrections to the old M54b text)

- **There is a harness now** (T2, `server/harness.odin`): a stepped server, `Simnet`
  (`common/netcode/simnet.odin`) as every remote player's network, an optional local pipe,
  and *parties* (`harness_add(h, tick, data)`) run each tick before the server in the order
  added. Remote players already connect as a dedicated server's would, over `Simnet` through
  `netcode.Link`. So the old design's `server.Config.bots: []game.Endpoint`, several local
  pipes and a multi-pipe `receive_messages` are **not built**: a bot is a harness party with
  a `netcode.Link` on `Simnet` (or on UDP, M55e), and the one pipe stays the local player's.
- **T3's scenario runner** (`server/scenario_test.odin`): player 0 is the mirror, players
  1..`SC_BOTS` are `Net_Client`s; it checks no desync, the ledger every second, chunk and
  position agreement, replay (every tick's hash twice) and leaks. Its `Bot` moves onto
  `bot.Bot`; the six scenarios are this row's regression net beside the determinism roots and
  the bandwidth baseline (`assets/baselines/net/bandwidth.txt`).
- **The protocol a bot speaks** (`common/game/protocol.odin`, `Client_Message`): `Hello`,
  `Proof`, `Choose`, `Input`, `Edit`, `Use_Block`, `Use_Entity`, `Attack`, `Fire`, `Shoot`,
  `Reload`, `Command`, `Chat`, `Inventory_Request`, `Respawn`, `Pack_Want`, `Packs_Ready`,
  `Prediction_Check`, and the rest. M53b's dialogue choice is added to the verbs when M53b
  has built its message (it is before this row in the order).
- **Account keys:** tests derive theirs with `test_key(name)` (`server/account_test.odin`);
  `game.Account_Key` (`common/game/account.odin`). `bot_key` uses the same derivation under
  the context `voxiverse bot v1` (M54's list of signing contexts names it).
- **No timing in tests (T5):** the old spec had none in tests; the bot cost is a `build
  bench budgets` scene (below).

## Layout

Added to the plan's Layout:

```
bot/        headless clients: a link (pipe, Simnet or UDP), the replica, behaviours (tests, dry runs, load)
```

`bot/` imports `base`, `common/game` and `common/netcode`, never `server`, so a process of
its own can run bots (M55e), and `check`'s package list gains it.

## Design

### The bot (`bot/bot.odin`)

`Bot` is what the mirror and `Net_Client` share:

- `link: Bot_Link :: union {game.Endpoint, ^netcode.Link}`;
- `name`, `key` (`bot_key(name)`: an `Account_Key` from the seed
  `SHA-256("voxiverse bot v1" || name)`, the same on every run);
- `state: Bot_State :: enum {Connecting, Proving, Fetching_Packs, Playing, Rejected, Closed}`
  and `rejected: string` (the server's reason);
- `schema`, `rx: game.Receiver` (M39's records: its own player, other players, entities,
  inventory, rules, clock, mode, and M53's quest, objective and dialogue records once built);
- `chunks` and `arrays` (only with `keep_chunks`: as the mirror's);
- `prediction: Maybe(game.Prediction)` (with `predict`: the mirror's reconciling client);
- `seq`, `inv_seq`, `edit_id`, `server_tick`, `welcome`, `address`;
- `notices` and `chat` (rings of the last 32), `results` (edit results by id);
- `fetch: ^game.Pack_Fetch` and `pack_cache` (the packs handshake, as `Net_Client` does);
- `rng: base.Rng` (seeded from the name);
- `behaviour: Behaviour`;
- `stats: Bot_Stats` (`inputs`, `messages_out`, `bytes_in`, `bytes_out`, `edits_refused`,
  `corrections`, `rejected`).

Procs: `bot_init(b, name, link, options: Bot_Options{keep_chunks, predict, ask}, allocator)`;
`bot_pump(b)` (what arrived, applied: `net_apply`'s and the mirror's receive, merged);
`bot_step(b)` (one input: the behaviour decides it and any actions, which are sent);
`bot_close(b, clean: bool)` (a goodbye, or a dropped link for churn tests);
`bot_destroy(b)`; `bot_party(b) -> (proc(rawptr), rawptr)` for `harness_add`.

The verbs behaviours use, each building exactly the message the game's client sends, its
`after` the last input sent: `bot_move(right, forward, yaw, pitch, buttons)`, `bot_look_at`,
`bot_break(pos)`, `bot_place(pos, face, item)`, `bot_attack(entity)`, `bot_fire`,
`bot_shoot(target)`, `bot_reload`, `bot_use_entity(id)`, `bot_use_block(pos)`,
`bot_command(text)`, `bot_chat(text)`, `bot_inventory(kind, slot, arg)`, `bot_respawn`,
M53b's `bot_choose_option(node, option)`, and M52d's `bot_script_send(pack, channel, value)`
(encoded with `message_encode` against the channel's schema, as a client script's send is).

`Behaviour :: struct {name: string, data: rawptr, step: proc(b: ^Bot, data: rawptr)}`.
Shipped here: `script` (M38's pure function of the tick: the determinism session's script
moves here unchanged as `bot.determinism_script`), `idle`, and `replay` (the inputs of a
recorded list, for the scenario runner's steps). M54j adds `explorer`, M55d `hostile`, M55e
`wander`, Q7 `builder`, `fighter`, `churner`.

### The test clients on it

- `Mirror` becomes `Mirror :: struct {using bot: bot.Bot, ...}` with only its test fields
  (mismatches, updates, first fix, the entity order): the determinism session's roots must not
  move.
- `Net_Client` becomes `{using bot: bot.Bot, ...}` with what only tests look at (shorn sheep,
  hit confirms, counts, worn items, captures); `net_connect`, `net_pump`, `net_send` call the
  bot's procs. Every `server` test that uses it compiles and passes unchanged in meaning; a
  field a test reads moves to `Bot` only if a behaviour needs it too.
- The scenario runner's `Bot` is a `bot.Bot` with the `replay` behaviour.
- The LAN party run's `Bot` (`server/party_test.odin`: walks, turns, jumps, changes weapon,
  shoots, waits at the death screen, counts deaths) becomes a `bot.Bot` with a behaviour local
  to the test (`party`); its walk and aim (`roll`, `aim`) are what Q7's `fighter` starts from.
  `test_party` keeps its checks (settle, flat memory, the downstream baseline, kills and deaths
  agreeing) unchanged.
- The benchmark's `Bot` (`dedicated/bench.odin`) becomes a `bot.Bot` on a UDP `netcode.Link`
  with two behaviours of the benchmark's own (`fly_out`, `party`; its `pump`, `bot_input`,
  `party_input` and `send` go). This is the UDP path M55e's bot process uses. The `server`
  and `party` scenarios' counts (players, bytes, chunks) are unchanged; their times are
  compared with `build bench compare <before> server` and `party` and must not get worse
  (p < 0.05 is a regression; the commit gives the numbers).

## The order of the steps

1. `bot/` with `Bot`, `bot_init`, `bot_pump` (from `net_apply`), the handshake and packs,
   the verbs, `idle`; `bot_test.odin` against the harness.
2. `Net_Client` on `Bot`; the `server` suite green.
3. `Mirror` on `Bot` with `predict`; `build determinism` roots and the bandwidth baseline
   unchanged.
4. The scenario runner's and the party run's bots; the six scenarios and `test_party` green.
   The benchmark's bots on UDP; `build bench compare` on `server` and `party`.
5. `test_four_bots_deterministic`, the property and fuzz tests, the `bots` budget scene;
   docs (`docs/determinism.md`'s harness section: bots), history.md.

## Tests

- `server/bot_test.odin` (the harness is `server`'s and `bot` cannot import it, so the bot's
  tests are a `server` test file importing `bot`; `bot/` keeps unit tests of what needs no
  server, `bot/bot_unit_test.odin`: `bot_key`, verbs encoding):
  - a bot joins a stepped server over `Simnet` and is `Playing` within 60 ticks; refused when
    the server is full, with the reason in `rejected`;
  - `bot_key` is stable (a fixed name's key byte for byte) and distinct per name;
  - a bot with `predict` sees no corrections over 600 quiet ticks and over 600 ticks of the
    determinism script;
  - every verb sends one message of the expected kind with `after` equal to the last input
    (`netcode.Capture` of the link, decoded);
  - a bot with a pack fetch reaches `Playing` on a server with a test pack, the archive's hash
    checked.
- `server/determinism_test.odin`, `bandwidth_test.odin`: on bots, roots and baseline unchanged
  (the commit says so with the numbers).
- `server/scenario_test.odin`: the six scenarios unchanged and green.
- `test_four_bots_deterministic`: two harnesses side by side, four `script` bots each (four
  different scripts), every tick's state hash equal for 2 000 ticks, and equal again on a
  second run (the replay check), under `netcode.Conditions` of 5% loss and 2 ticks of jitter.
- `test_bot_churn_property`: 200 seeds; a seed draws joins, clean and dropped leaves, rejoins
  under the same and new names over 3 000 ticks for up to 8 bots; after each: the server's
  client count equals the bots `Playing`, no leak (tracking allocator), every hash equal on a
  replay of the seed.
- **Fuzzing (Q1):** the bot decodes what a server sends; Q2's protocol targets cover the
  messages, and this row adds `bot_receive` (`build fuzz`'s target list and
  `docs/fuzzing.md`): random and mutated server datagrams into a `Playing` bot never crash,
  never allocate past the receiver's bounds, and leave the bot `Playing` or `Closed`.

## Budgets (`build bench budgets`; T5)

A budget is a `base.Metric` (`base/metrics.odin`) with its limit in `BUDGET_LIMITS`
(`tools/bench/budgets.odin`), measured by a scene in `server/budgets.odin` as the others are
(`budget_flood`, `budget_journal`).

`budget_bots`: 32 `idle` bots and 32 `script` bots on one harness for 600 ticks, CPU time of
the stepping thread (`base.thread_cpu_us`) split into the bots' side (pump and step) and the
server's tick. Metrics: `Bot_Tick` (the bots' side per bot per tick, us) limit **40**, so
M55e's 200 bots cost at most 8 ms of a tick's 33 ms on the bot process; `Bots_Server_Tick`
(the server's slowest tick with 64 bots, us) reported, with no limit until M55e sets one. The
scene's test calls it for what it does (every bot `Playing`, no correction).

## Left out

Navigation (bots teleport or walk straight); bots that fight well (Q7's `fighter` is simple);
behaviours other than `script`, `idle` and `replay` (their rows); a bot process (M55e).
