# M55b: a thread per world (phases in the tick; each world's simulation, scripts and bodies on its own thread)

The first of two rows (M55b, [M55e](M55e.md); split by #88 at the joint the old M55b spec
had: its steps 1-2 and 3-6). After M55d; M55e (bandwidth budgets, raised limits and the
200-bot load run) follows it, then Q7.

**Why.** One server thread ticks every world in turn (`server/server.odin`'s `tick`), so a
universe's capacity is one core however many worlds it has. The worlds share nothing during
their simulation but the server's own fields, so each can tick on its own thread if every
write to universe state is moved out of the world's part of the tick. Since #83 a world's
part also runs its scripts (M52, one VM per pack per world) and its moving bodies (M50c), so
they move with it.

## Checked against the code (2026-10-31, #88; corrections to the old M55b text)

- **The tick today** (`tick`, in order): `calls_run`; `tick_summary`; `save_poll`,
  `save_slice`, autosave; per world `chunks_collect` and `naturals_take`; `receive_messages`
  (the pipe, then the network: every handler); per world the clock; per playing client
  `simulate_player`, `health_tick`, `weapons_tick`, `place_tick`, `stats_tick`, `drop_far`;
  `worlds_unload_idle`, `audit_tick`; `unload_left`; per world `unload_unwanted`,
  `updates_run`, `random_ticks`, `entities_tick`, `containers_tick`, `rewind_record`,
  `gates_tick`, `rollback_tick`, `changes_flush`, `journal_tick`; per playing client
  `replicate_tick`, `stream`, `replica_flush`; `kick_due`, `packs_tick`,
  `packs_reload_tick`; `update_info`, `host_flush`.
- **World code that reaches the universe today:** `gates_tick` calls `travel`
  (`server/gates.odin`); a death writes a chat line (`chat_system`, `server/damage.odin`);
  item gains and losses write `s.ledger` (`server/ledger.odin`); `send_message` encodes
  through the one `s.writer` (`server.odin`); `weapons_tick`'s `shot_trace` walks
  `s.clients` (reading only those in its world). Each becomes a request, a delta or a
  per-client buffer (below).
- **Shared services:** metrics are atomic rings (`common/base/metrics.odin`: safe from any thread);
  the profiler's state is `thread_local` (`common/base/profile.odin`: a world thread is a named
  thread of its own); telemetry's sink copies under a mutex (`common/telemetry`); the
  temporary allocator is per thread (each world thread frees its own at the end of phase 2).
- **The stepped server and the harness** (`server/stepped.odin`, `server/harness.odin`)
  start no thread; this row keeps that by default (phase 2 inline) and adds
  `Config.parallel_step` for the tests that prove the threads change nothing.
- **Scripts and bodies (not built yet; their specs):** M52's points A (after the players)
  and B (after `entities_tick` and `containers_tick`, before `gates_tick`), per world, with
  a world pool and per-player buckets; M52d's message events queued when a message is
  handled and delivered at point A; M50c's `bodies_tick` right after `entities_tick`;
  M53's triggers and spawners delivered with the scripts. All of it is phase 2.
- **No timing in tests (T5):** the parallel speedup is a `build bench budgets` scene.

## Design

### A tick in three phases

1. **Universe, worlds parked** (the server thread): `calls_run`, the summary, saving;
   network in, decoding, handshakes, every message handler (they touch worlds directly, as
   today: nothing else runs; M52d's `Script_Send` events are queued on the world's script
   queue here); commands, travel, joins and leaves, loading and unloading worlds; each
   world's `w.players: [dynamic]int` rebuilt.
2. **Worlds, in parallel.** Each loaded world on its own thread runs `world_tick(w)`, the
   per-world code above moved into one procedure in today's order:
   - `chunks_collect`, `naturals_take`, the clock;
   - its players: `simulate_player`, `health_tick`, `weapons_tick`, `place_tick`,
     `stats_tick`, `drop_far`; then `unload_left` for them;
   - **point A** (M52: region membership, events since the last point, M52d's messages);
   - `unload_unwanted`, `updates_run`, `random_ticks`, `entities_tick`, **`bodies_tick`**
     (M50c), `containers_tick`;
   - **point B** (M52: timers, `tick` events, events since point A);
   - `rewind_record`, `gates_tick`, `rollback_tick`, `changes_flush`, `journal_tick`;
   - for each of its players: `replicate_tick`, `stream`, `replica_flush`, into that
     client's outbox.
3. **Universe, worlds parked.** In world order: each world's requests are applied, its
   ledger deltas merged, the audit run (`worlds_unload_idle`, `audit_tick`). Outboxes are
   drained into the pipe and `host_send` in client order. `kick_due`, `packs_tick`,
   `packs_reload_tick`, `update_info`, `host_flush`, stats.

### The rules for phase 2

- A world's thread writes only its own `World` (chunks, entities, bodies, its scripts' VMs
  and stores, its journal), the clients whose `c.world` is that world, those clients'
  outboxes, and its own `w.requests`, `w.ledger_delta` and `w.events`.
- It reads, and nobody writes during phase 2: `s.config`, `s.schema`, `s.registry`,
  `s.perms`, `s.community`, `s.store.characters`, `s.tick`, other clients' `world` field.
- It never touches: `s.host`, `s.writer` (it goes: each client's outbox has its own encode
  buffer), `s.ledger`, `s.store` writes, chat, another world.
- What world code did to the universe becomes a request (`Universe_Request :: union
  {Disconnect, Travel, Chat_System, Save_Player, Notice_All, Kick}`), applied in phase 3 in
  world order, then the order made. A disconnect from world code marks the client and stops
  its simulation that tick. A death's chat line, a gate's travel and a kick all go this way.
- **Scripts:** a native that writes universe state (a chat line to every player, a travel,
  a kick, an item gain or loss through the ledger) makes the same request or delta; what it
  reads of the universe is in the read-only list. A VM, its heap and its store belong to one
  world (M52: one VM per pack per world), so nothing is shared between world threads. A
  parked call (M52's `Throttled`) resumes on its world's thread. `channel.send` and
  `broadcast` (M52d) write into the outboxes of the world's own players; a send to a player
  in another world is already refused by M52d.
- **Bodies:** a body and its riders are in one world; a rider leaving the world goes through
  a `Travel` request.
- Each procedure that writes universe state starts with `phase_check(s, #caller_location)`.
  During phase 2 it does not panic in tests (the plan's rule: refusals are values): it counts
  the breach with its location in `s.phase_breaches`, logs an error, and the harness's stop
  fails the test with the locations; a DEV build outside tests asserts. TSan is a no-op in
  this toolchain, so these checks are the race check.
- Each world thread is made when the world loads and joined when it unloads, named `world
  <address>`, with two semaphores (`go`, `done`). Each world keeps its own chunk workers.
- Stepped servers run phase 2 inline, worlds in `s.worlds` order; `Config.parallel_step`
  (tests) runs them on their threads behind the same barrier. Both give the same hash: the
  rules leave nothing order-dependent, and the ledger's hash section is a sum merged in
  world order.
- `Stats` gains `world_tick_ms` per loaded world; the tick summary log line gains the
  slowest world and the phase 1 and phase 3 times; metrics `Server_Phase1`,
  `Server_Phase3` and `Server_World_Tick` (each world's, on its thread).

## The order of the steps

1. Phases in the tick: `world_tick`, `w.players`, outboxes, requests, ledger deltas,
   `phase_check` with its counter. Still one thread; the suite, `build determinism` and the
   bandwidth baseline unchanged.
2. Scripts and bodies inside `world_tick` at their points (or, if M52 or M50c changed where
   they run, wherever their specs put them in the world loop); their natives' universe writes
   as requests.
3. World threads and `Config.parallel_step`; the hash tests; the budget scene; docs
   (`docs/determinism.md`: phases and the rules); history.md.

## Tests

- `server/worlds_test.odin`, `test_parallel_worlds_same_hash`: a stepped universe of three
  worlds with two `script` bots each (M54b), a travel every 300 ticks, and a test pack
  enabled in every world whose server script edits blocks on a timer, gives an item to a
  player in a region (the ledger), says a chat line every 100 ticks, answers a channel
  message with a broadcast (M52d; the bots send on the channel), and drives a body back and
  forth (M50c); run inline and with `parallel_step` side by side: the roots agree every tick
  for 3 000 ticks, and the ledger audits balance.
- `test_parallel_worlds_property`: 100 seeds; a seed draws 2 to 5 worlds, 1 to 4 bots each,
  joins, leaves, travels, gate dials, deaths and script events over 2 000 ticks; inline and
  parallel give the same hash every tick and no phase breach.
- The whole suite with `phase_check` on every OS: `phase_breaches` 0 in every harness (the
  harness's stop checks it).
- `test_phase_breach_counted`: a test-only native that writes `s.ledger` from point B is
  counted as a breach with its location, and the harness's stop reports it (the check works).
- `server/bandwidth_test.odin` and `build determinism`: unchanged (the move is faithful).

## Budgets (`build bench budgets`; T5)

`budget_worlds` (`server/budgets.odin`): four worlds, each with M11's flood (as
`budget_flood`) and 16 entities, ticked 300 times inline and 300 times with
`parallel_step`; wall time per tick (a benchmark may read the clock; a test may not).
Metrics: `Worlds_Parallel_Ratio` (the parallel tick's median over the inline one's, %)
limit **50** (four worlds on CI's 4-core runner: the ideal is 25); `Server_Phase_Overhead`
(phases 1 and 3 with four idle worlds and no client, us a tick, CPU) limit **300**.

## Left out

Worlds on more than one thread each (regions in parallel); several server processes; one
shared pool of chunk workers; scripts of one world spread over threads.

## Exit check (M55b)

**Gated in CI:** `test_parallel_worlds_same_hash`, `test_parallel_worlds_property`,
`test_phase_breach_counted`; the suite with no phase breach; `build determinism` roots and
the bandwidth baseline unchanged; `build bench budgets -check` with `Worlds_Parallel_Ratio`
and `Server_Phase_Overhead` in budget; `build check` and CI green on the three OSes.
