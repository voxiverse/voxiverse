# M55b: scale of one server (a thread per world, bandwidth budgets, 200 bots)

**Why.** One server thread ticks every world in turn (`server.odin`'s `tick`), so a universe's
capacity is one core however many worlds it has. Sends are bounded only by
`SEND_BUDGET_BYTES` for chunks, `SNAPSHOT_PARTS` for motion and the connection rate. There is
no per-client budget across them and no fair share of the server's upstream.
`game.MAX_PLAYERS` is 32. The only load test is `dedicated/bench.odin`'s 8 flying bots for 30
seconds.

**Design.**

*A thread per loaded world, with phases.* A tick has three phases:

1. **Universe, worlds parked** (the server thread):
   - network in, decoding, handshakes, every message handler (they touch worlds directly, as
     today: nothing else runs);
   - `calls_run`, commands, travel, joins and leaves, autosave, loading and unloading
     worlds.
2. **Worlds, in parallel.** Each loaded world on its own thread runs `world_tick(w)`:
   - `chunks_collect`, `naturals_take`, the clock;
   - its players: simulate, health, stats, drop far, unload left;
   - updates, random ticks, entities, containers, gates, `changes_flush`;
   - for each of its players: replicate, stream, replica flush, into that client's outbox;
   - the rewind frame (M55).
3. **Universe, worlds parked.** In world order: each world's requests are applied, its ledger
   deltas merged, the audit run. Outboxes are drained into the pipes and `host_send` in
   client order. `kick_due`, `host_flush`, stats.

The rules for phase 2:

- A world's thread writes only its own `World`, the clients whose `c.world` is that world
  (`w.players: [dynamic]int`, rebuilt in phase 1), those clients' outboxes, and its own
  `w.requests`, `w.ledger_delta` and `w.events`.
- It reads, and nobody writes during phase 2: `s.config`, `s.schema`, `s.perms`,
  `s.community`, `s.store.characters`, `s.tick`, other clients' `world` field.
- It never touches: `s.host`, `s.writer` (it goes: each client's outbox has its own encode
  buffer), `s.ledger`, `s.store` writes, chat, another world.
- What world code used to do to the universe becomes a request (`Universe_Request :: union
  {Disconnect, Travel, Chat_System, Save_Player, Notice_All}`), applied in phase 3 in
  order. A disconnect from world code marks the client and stops its simulation that tick.
  A death's chat line, a gate's travel and a kick all go this way.
- Telemetry `emit` is already thread-safe (a mutex). Its order across worlds is not state.
- Each proc that writes universe state starts with `phase_check(s)`, which asserts
  `s.phase != .Worlds` (an atomic set by the tick driver). Running the suite finds every
  call that breaks the rules. TSan is a no-op in this toolchain, so the asserts are the race
  check.
- Each world thread is made when the world loads and joined when it unloads. Two semaphores
  per world: `go` and `done`. It is named `world <address>`. Each world keeps its own chunk
  workers, as today.
- Stepped servers run phase 2 inline, worlds in `s.worlds` order. Test-only
  `Config.parallel_step` runs them on their threads with the same barrier. Both give the
  same hash, because the rules leave nothing order-dependent. The Ledger hash section is a
  sum, merged in world order.
- `Stats` gains `world_tick_ms` per loaded world. The tick summary log line gains the
  slowest world and phase 1 and phase 3 times.

*Bandwidth budgets and priorities* (`server/send.odin`).

- Each tick each client gets a byte budget `client_rate / TICK_RATE`, where `client_rate =
  min(net.client_rate, fair share)`.
- `net.client_rate` (a server variable, default 512 KiB/s) and `net.server_rate` (default
  48 MiB/s) are config variables, `--client-rate` and `--server-rate` on the dedicated
  server.
- The fair share is `net.server_rate` divided by the playing clients. What a client left
  unused last tick is shared among the others the next tick, at most double a share.
- The order within a client's budget:
  1. Control and answers: Welcome, Reject, Edit_Result, Pong, Characters, Challenge. These
     are never deferred. They count against the budget.
  2. The reliable lane (M39). Never deferred: its deltas build on each other. It counts.
  3. The snapshot lane. `sender_flush` gains `snapshot_limit` bytes: the remaining budget,
     clamped to between one part and `SNAPSHOT_PARTS` parts. Records that do not fit wait,
     and M39's nearest-first and waiting priority picks them next tick.
  4. Chunks. `stream()`'s budget is `min(SEND_BUDGET_BYTES, remaining)`. `MAX_BACKLOG`
     stays.
  5. Bulk (`Stats_Text`, M27 answers) only if bytes remain, else next tick.
- `Conn.rate` is set to 1.25 × `client_rate`, so resends fit and the connection never drops
  what the scheduler chose.
- Counted per client: bytes sent per lane per second. The new metrics
  `Server_Sent_Client_KiB_P99` and `Server_Budget_Overruns` (ticks where control and
  reliable alone exceeded the budget, counted, never refused).

*Limits raised.*

- `game.MAX_PLAYERS :: 256`. The `--max-players` help text says it.
- `Config.max_players` keeps the default of 8.
- Chunk capacity per world becomes `min(per_player × max_players + workers ×
  MAX_IN_FLIGHT_PER_WORKER, MAX_WORLD_CHUNKS)`, with `MAX_WORLD_CHUNKS :: 131072`. A chunk
  that does not fit waits in the stream, nearest first, and is logged once a minute as
  "world full".
- `players_put` walks `w.players`, not every client.

*The load harness.*

- Bots in a process of their own: `voxiverse-server --bots <n> --connect <host:port>
  [--seconds s] [--threads k] [--report <file>]` (`dedicated/load.odin`).
- `n` bots on `netcode.Link`s, split over `k` threads (default 4), each thread pumping its
  bots as `bench.odin` does. Bots keep no chunks and do not predict, so a bot costs its
  decoding only.
- Each bot is a `wander` bot (`bot/wander.odin`):
  - it walks in a direction from its RNG, changing every 5 to 15 s, within 160 blocks of
    its world's spawn (it turns back past that);
  - it jumps at random and looks around;
  - every 20 s it places stone ahead or breaks the block it placed;
  - every 60 s it says a chat line;
  - every 120 s it travels (`/travel <address>`) to another of the load universe's four
    worlds.
- Bots join 10 a second.
- `build load [--bots 200] [--minutes 10]` (`tools/build/load.odin`):
  1. Makes a fresh `build/load/universe` with four worlds (the home and three addresses
     fixed in the tool) and a `permissions.cfg` giving the role `bot` `travel`, `chat.send`
     and `world.edit`.
  2. Starts `voxiverse-server --universe build/load/universe --max-players 256
     --view-radius 6 --view-height 3 --stats-out build/load/server.jsonl`.
  3. Starts the bot process, and stops both at the end.
- `--stats-out` is a new server flag: a JSON line every 10 s, with tick p50, p99 and max for
  the last 10 s, per world tick p99, phase 1 and 3 times, clients, bytes sent per client
  (p50, p99, max), budget overruns, crypto µs per tick (M55), arena used and reserved, and
  the "behind" count.
- The bot process's report holds per bot: joined, disconnects with reasons, bytes in and
  out, edits refused.
- The tool writes `build/load/result.json`, `{"verdict", "thresholds", "measured", "minutes",
  "bots"}`. It exits 1 when a threshold fails.
- The thresholds, over the measured span (after the last bot joined, plus 60 s of warm-up),
  are budgets, not machine numbers:
  - tick p99 ≤ 33.3 ms in every 10 s window, and the mean ≤ 16 ms;
  - zero "server behind" lines;
  - every world's tick p99 ≤ 33.3 ms;
  - mean server send ≤ 40 KiB/s per bot, no client over its budget by more than 5% in any
    10 s window, total ≤ `net.server_rate`;
  - zero bot disconnects, all 200 playing throughout;
  - the arena's used bytes over the last five minutes grow less than 2% (memory flat);
  - crypto ≤ 3% of tick time.
- CI: a `load` job on ubuntu-latest (`needs: build`, timeout 25 minutes) runs `build load`
  and uploads `build/load/` as an artifact. The 4-core runner shares its cores between the
  server and the bots, which is the harder case.
- If a threshold fails there, the session profiles the run (`build trace` on the server
  under the bots) and fixes the cost it finds, the way M19 did. A threshold is not loosened
  without the owner.

**The order of the steps:**

1. Phases in the tick: `world_tick`, `w.players`, outboxes, requests, ledger deltas,
   `phase_check`. Still one thread, and the suite passes.
2. World threads and `Config.parallel_step`. The two-world hash test.
3. The send scheduler, rates, `snapshot_limit`, metrics.
4. Limits raised, the capacity cap.
5. `bot/wander.odin`, `--bots`, `--stats-out`, `build load`, the CI job.
6. The 200-bot run, and whatever it finds.

If the session must split, the remainder is M55c (or M55d if M55 split already): steps 5 and
6, with the 200-bot run as its exit check.

**Left out:**

- Worlds on more than one thread each (regions in parallel).
- Several server processes.
- Moving a world's chunk workers into one shared pool.
- Priority by what a player looks at.
- Bandwidth estimation from loss (the rate is configured, not discovered).
- Bots that predict at scale.

**Tests:**

- `server/worlds_test.odin`, `test_parallel_worlds_same_hash`: a stepped universe of three
  worlds with two `script` bots each and a travel every 300 ticks, run inline and with
  `parallel_step` side by side. The roots agree every tick for 3 000 ticks.
- The whole suite with `phase_check`: no assert, on every OS.
- `server/send_test.odin`:
  - with a 64 KiB/s client rate on a stepped server, the bytes sent per second stay within
    5% of it while streaming;
  - control messages are never deferred;
  - snapshot records deferred one tick arrive the next, nearest first;
  - two clients under a small `server_rate` each get half, and the unused share moves to
    the busy one.
- `server/bandwidth_test.odin`: the baseline. With the default rates nothing in it hits a
  budget, so it is unchanged. Any change is explained in the commit.
- `dedicated` test: `--bots 20 --seconds 30` against a test server: all 20 play, with a
  report.

**Exit check:**

- `build load --bots 200 --minutes 10` passes every threshold locally and in CI's `load` job.
- `test_parallel_worlds_same_hash` passes. The suite and `build check` pass.
- CI green on the three OSes.

**Check by hand:**

- `build load` on a desktop: watch `server.jsonl` and `htop`. Four world threads are busy,
  and the server thread is not the bottleneck.
