# Q4: published, reproducible benchmarks (`./build.sh bench public`)

**Why.** The owner (#84): the engine's performance claims are numbers anyone can rerun. One
command runs a fixed suite and writes a report a stranger can read and reproduce on their own
machine. **The owner's answers (2026-10-30):** we publish our own numbers only, with the
command that reproduces them; no comparisons with other engines. **No hardware of ours goes
in the repository or the docs:** the report describes the machine it ran on, and it is written
to `build/`, never committed.

**What this builds on:** the benchmark results (`common/base/bench_result.odin`: `Bench_Result`,
`machine_info` with the CPU, cores, threads, OS, GPU and driver, `bench_result_write` into
`build/benchmarks/<scenario>/` and `history.jsonl`); the metrics (`common/base/metrics.odin`:
`Metric` with `Frame`, `Gpu_Frame`, `Generate_Chunk`, `Light_Chunk`, `Mesh_Chunk`,
`Server_Tick`, ...; `metric_summary` with `avg`, `p50`, `p99`, `max`); the scenarios
`build bench chunks` (`tools/bench`, one thread), `flight` (the game, release build, fixed
settings, 1280x720), `server` (`dedicated/bench.odin`: `BENCH_BOTS` simulated players over
UDP, 3 repetitions); `resident_memory` (`common/base/memory_linux.odin`; `memory_other.odin` returns
0); `build bench compare`; CI's tag-only jobs (`Package`, `Draft release`, on `v*.*.0`).

**The suite** (`tools/build/bench_public.odin`; the scenarios' code is reused, not copied):

| Part | How | Numbers reported |
|---|---|---|
| Frames | the `flight` scenario, release build, 1280x720, its fixed settings and seed, 3 repetitions | frame time median, p95 and worst (ms), over all frames of the measured spans; GPU frame median and p95 where the GPU gives timestamps |
| Chunks | `bench chunks`, one thread, 3 repetitions | chunks generated a second, chunks lit a second, chunks meshed a second; median per chunk (ms) of each |
| Server | the `server` scenario at 8 and at 32 bots (a `-bots:N` option on it; 32 is `game.MAX_PLAYERS`), 3 repetitions each | tick time median, p95 and worst (ms); bytes sent a second per bot |
| Memory | sampled during the frames part (the game) and the 32-bot server part | peak resident memory (MiB) of each process |

- `metric_summary` gains `p95` (the report's percentile; `p99` stays for the other
  scenarios). Frame and tick percentiles are over every frame or tick of every repetition's
  measured span, not a median of per-repetition percentiles; the spread between repetitions
  is reported as the lowest and highest repetition median.
- `resident_memory` on Windows (`GetProcessMemoryInfo`'s `PeakWorkingSetSize`; peak is what
  the report wants, so Linux reads `VmHWM` from `/proc/self/status` and macOS
  `task_info(MACH_TASK_BASIC_INFO)`'s `resident_size_max`), as `peak_resident_memory`.
- The scenarios' versions do not change (their own results stay comparable); the public suite
  has its own version, `PUBLIC_VERSION :: 1`, in the report, raised whenever a part changes
  what it measures.
- `--quick`: one repetition of each part, shorter spans (for checking that it runs; its
  report says "quick: not for publishing" at the top).
- Without a Vulkan device, the frames part is skipped and the report says so; the rest runs.

**The report** (`build/benchmarks/public/report.md` and `report.json`, overwritten each run):

- Header: "Voxiverse benchmarks", the version and commit (`base.COMMIT`), the build profile,
  the date (UTC), the suite version.
- "Machine": what `machine_info` reads (CPU, cores and threads, OS, GPU, driver) and total
  memory: the machine the run happened on, whoever's it is.
- "Results": one table per part, numbers with their units, and per number one sentence on
  what it measures (in a table `PUBLIC_EXPLAIN` in the code, so the JSON and the Markdown
  say the same).
- "Method": the settings (resolution, the scenario's seed and route, the bot counts, the
  repetitions, the measured spans) and "lower is better" or "higher is better" per number.
- "To reproduce": exactly the commands, `git clone https://github.com/voxiverse/voxiverse`,
  `git checkout <commit>`, `./build.sh bench public`, and "Numbers depend on the machine:
  compare runs on one machine, or the same machine across commits with `build bench compare`."
- Nothing else: no comparison with other engines or other machines, no claims beyond the
  numbers.

**Published where.** On each named release (a `v*.*.0` tag), CI runs `./build.sh bench public`
on the Linux runner (job "Benchmarks · public", ubuntu-latest, after Package) and attaches
`report.md` and `report.json` to the draft release. The runner's machine is GitHub's, named in
the report by what it reads (and its GPU is Mesa's CPU driver, `llvmpipe`, so the frames part
measures software rendering; the report's "Machine" says so plainly, and its "Method" says
frame numbers from a CPU driver are not GPU numbers). The owner, reviewing the draft, may add
a report run on any other machine by hand; that is the owner's publication and never enters
the repository. `docs/benchmarks.md` (new) describes the suite, the method, how to read the
report and how to rerun it, with no numbers in it.

**Tests:**

- `tools/build`: the report writer on a fixed set of results gives byte-exact Markdown and
  JSON (a golden test with made-up numbers and a made-up machine named "Example CPU"); a
  missing GPU skips the frames part with its sentence; `--quick`'s banner.
- `base`: `p95` of a known series; `peak_resident_memory` is non-zero and at least
  `resident_memory` on Linux and Windows and macOS (in the suite: the CI test jobs on the three
  OSes).
- A lint in `check` (`tools/build/lints.odin`, beside T1's): `docs/benchmarks.md` and the report's template contain no numbers with units
  of time, rate or memory (a regular expression over the text), so numbers never land in the
  docs.

**Steps, in order:** `p95` and peak memory; `-bots:N` on the server scenario; the suite and
the report with its tests; `docs/benchmarks.md`; the CI job on tags.

**Left out:** comparisons with other engines (the owner's answer); a results website or
history across releases (each release's report stands alone); GPU timing on CI (no GPU there);
Windows and macOS runs in CI (the command runs there; CI publishes Linux's only, since the
tag's other jobs package); a "score" combining numbers.

**Open questions** (none blocks this row): whether the owner wants a report from a machine
with a real GPU attached to each release (by hand, never committed).

**Exit check:** `./build.sh bench public --quick` runs on Linux and writes both files, the
report's tests pass; `./build.sh bench public` runs once in full locally and its report is
read through for the sections above (quoted in the session's report minus the machine
section); the suite, `build check` and CI green (the tag job is checked when the next
`v*.*.0` tag runs: listed under *Check by hand*).

**Check by hand:** on the next Friday Alpha's draft release, `report.md` and `report.json`
are attached and the report's "To reproduce" commit is the tag's.
