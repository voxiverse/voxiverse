# R10: uploads off the graphics queue (a transfer queue, a staging ring, a timeline)

Arc rules: [R.md](R.md#rules-for-every-r-milestone). One session; not split (#87).

**Why.** Chunk meshes are copied at the start of the frame's own command buffer (`world_upload`,
label `upload chunk meshes`, metric `gpu_upload`) from a per-frame-slot staging buffer of 8 MiB
(`World_Settings.staging_size`); a mesh that does not fit waits a frame (`.Busy`). The copies
compete with drawing on the one queue, and a flight's burst of meshes is spread over frames by
the staging size, not by what the GPU can do.

**Checked against the code (2026-10-30, #87; corrections to the old R10 text):**

- The graphics command buffer also copies the chunk draw records (`draw_copies`, into
  `chunk_draws`), the cull records (`cull_dispatch`'s dirty places, from `cull_staging`) and,
  once and after a pack change, the texture array (`upload_setup`). Moved by R10: the meshes
  and their chunk draw records. Not moved: the cull records (they must be ordered with this
  frame's cull dispatch, and are a few hundred bytes), the texture array (an image: kept off
  the transfer queue so no image ever changes queue family).
- R9b's growth copy reads the arena that uploads write; R10 moves it onto the transfer queue
  too, so the two are ordered by that queue.
- There are no timeline semaphores and no second queue today (`usable_queue_family`: one family
  for graphics and present). Lavapipe exposes one queue family with one queue, so **CI can only
  run the fallback** (the transfer work on the graphics queue, in its own submissions, with the
  same timeline): the code path is the same by design (the old text's rule), and what differs
  across families is isolated in one tested function (below).
- **Ownership transfers are avoided rather than written.** The old text named queue-family
  ownership transfers; the buffers the transfer queue writes (the arena, `chunk_draws`) are
  created with `SHARING_MODE_CONCURRENT` over the two families when they differ, which Vulkan
  allows for buffers with no cost the drivers document for buffers (the cost of concurrent
  sharing is for compressed images). Decided here (engineering): no release/acquire barrier
  pairs to get wrong.

## Design (R10)

### The queue (`client/gpu/gpu.odin`, `transfer.odin`)

`transfer_queue_pick(families) -> (family, index, kind)`, a pure function over
`vk.QueueFamilyProperties`: (1) a family with `TRANSFER` and neither `GRAPHICS` nor
`COMPUTE` (a copy engine), else (2) a family with `TRANSFER` and `COMPUTE` but not `GRAPHICS`,
else (3) a second queue of the graphics family when its `queueCount` is 2 or more, else (4)
the graphics queue itself. `kind` (`.Copy_Engine`, `.Async_Compute`, `.Second_Graphics`,
`.Same_Queue`) is logged at start-up. `timelineSemaphore` (Vulkan 1.2 core) is required
(rule 5) and enabled. Timestamps on the transfer queue only when its family has
`timestampValidBits` (copy engines may not): label `transfer`, metric `gpu_transfer`.

### The staging ring (`client/gpu/staging.odin`)

`Staging_Ring`: one host-visible buffer of `STAGING_RING` (32 MiB, through R9's allocator),
written front to back and wrapping; each submission's span is tagged with its timeline value
and reclaimed when `vkGetSemaphoreCounterValue` reaches it. `ring_reserve(n) -> (offset, ok)`
fails only when the unreclaimed spans leave no room: the mesh waits a frame (`.Busy`, as now,
counted as `upload_waits`). A mesh is at most 24 576 quads x 3 layers x 16 bytes (1.2 MiB),
always below the ring.

### Submissions and the timeline

- Per frame (in `world_upload`, which now records nothing on the graphics command buffer for
  meshes): when meshes were staged, one transfer command buffer (a pool of `TRANSFER_BUFFERS`
  (4) command buffers, each reused once its value is reached) records the copies into the arena
  and `chunk_draws` and is submitted on the transfer queue, signalling `upload_timeline =
  next_value`. Each mesh added remembers that value (`Mesh.upload`).
- **Shown only when uploaded:** `world_apply`/`world_show_mesh` put a mesh in `live` (its cull
  record, its water entry) only once `upload_timeline`'s counter has reached its value;
  until then it is `hidden` with a new flag `in_flight` (a group's meshes are shown together
  only once every one of them has arrived, extending today's rule). So no frame ever draws a
  range the transfer queue is still writing.
- **Made visible to the graphics queue:** the frame's graphics submission waits on
  `upload_timeline` at the highest value among the meshes first shown this frame, at stages
  `VERTEX_SHADER | COMPUTE_SHADER` (the arena's readers). The value is already reached (the CPU
  saw it), so the wait never stalls; it is the memory dependency the queues need (a host's view
  of a semaphore is not one).
- **Write-after-read:** a freed range (`World_Frame.freed`) is reused only once the frame slot
  that last drew it has come round (as now) **and** the graphics queue's work up to that frame
  is known complete (its fence, already waited in `begin_frame`); the transfer submission that
  writes a reused range waits on nothing more. Stated here because a second queue is where
  this breaks: a test below covers it.
- **Same queue** (`kind == .Same_Queue`, CI): the transfer command buffer is submitted on the
  graphics queue before the frame's, with the same timeline signal and the same wait, so CI
  exercises every line except the queue handle.

### Metrics

`gpu_upload` leaves the graphics queue's sections (its label is no longer recorded there);
`gpu_transfer` (when timed), `upload_bytes` (per frame), `upload_waits` (meshes that waited a
frame for the ring), `upload_latency_frames` (frames from a mesh job's result taken to the mesh
shown; its p99 is the measure of the ring and the queue together).

## The order of the steps (R10)

1. `transfer_queue_pick` and its tests; the queue and `timelineSemaphore` at device creation;
   the log line.
2. `Staging_Ring` and its tests.
3. The transfer command buffers, the timeline, `in_flight` meshes, the graphics wait; R9b's
   growth copy on the transfer queue; `CONCURRENT` sharing when families differ.
4. `--check uploads`, the CI step; metrics; docs (debugging.md: the queues, the timeline, how
   to read `transfer` in a trace); history.md.

## Tests (R10)

- `client/gpu/transfer_test.odin`: `test_transfer_queue_pick` over tables of families as
  lavapipe, RADV, ANV, NVIDIA and MoltenVK report them (the tables written from their
  documented queue families, in the test): the pick and the kind for each; a family with
  `TRANSFER` but no timestamps.
- `client/gpu/staging_test.odin` (no device, the ring's bookkeeping with a fake counter):
  wrapping; a reserve that does not fit until a value is reached; spans reclaimed in order
  only; never two live spans overlapping (property, fixed seed 87, 100 000 operations).
- `client/render/render_test.odin`: `test_mesh_shown_only_when_uploaded`: with a fake timeline,
  a mesh is not in `live` before its value; a group is shown only when all of its meshes'
  values are reached.
- `--check uploads` (`client/upload_check.odin`, a row of `CHECKS`, a CI step on lavapipe under
  validation, synchronization included): (1) teleport 2 000 blocks into unloaded land and
  wait for it to load: every mesh is shown, `upload_latency_frames` p99 at most 3 while the
  ring is not full; (2) `debug.staging_kib 512` (a ring smaller than one frame's meshes): every
  mesh still shown, `upload_waits` above zero, and the debug assert that no drawn slot has an
  upload value above the timeline's counter never fires; (3) `debug.arena_start_kib 1024`
  during (1): growths on the transfer queue interleaved with uploads, verified by R9b's
  `debug.arena_verify`.
- `images`: pictures and counts unchanged.

## Benchmarks (R10)

`bench compare <the commit before R10> flight` and `edits`, `load`:

| Metric | Target |
|---|---|
| `flight` frame p99 and worst | at most 80% of the commit before R10's (p < 0.05): the old text's target, kept |
| `flight` `gpu_frame` p99 | lower or within noise (the copies off the graphics queue) |
| `flight` `upload_latency_frames` p99 | reported (at most 3) |
| `edits` frame p99 | within noise or better |
| `load` | within noise or better |

On the development machine the queue kind is reported (a copy engine is expected on a desktop
GPU); a same-queue run (`VX_TRANSFER=same`, an environment switch beside `VX_VALIDATION` that
forces kind 4) is measured too, so the gain of the second queue is separated from the gain of
the ring and the timeline.

## Left out (R10)

The texture array and every image upload on the transfer queue (images would need ownership
transfers); async compute (the cull and pyramid passes on another queue); uploads from a
worker thread (the job writes the ring directly: measured only if `world_apply`'s copy into
the ring shows in a profile).

## Exit check (R10)

**Gated in CI:** `--check uploads` (all three parts) under validation with synchronization
validation, on the same-queue path; the pick, ring and showing tests; `images` unchanged;
`build check` and the suite. **Measured** (development machine, reported, under
`VX_VALIDATION=1` once with the second queue to see synchronization validation clean on it):
`flight` frame p99 and worst at most 80% of the commit before R10's; `gpu_upload` absent from
the graphics queue's sections.
