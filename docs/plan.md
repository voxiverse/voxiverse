# Voxiverse rewrite plan

A from-scratch rewrite on the orphan `rewrite` branch. The old prototype (`main`) stays
readable next to it as a reference; nothing is copied over, ideas are re-typed on purpose.

## Why

The audit of the prototype found that its problems are architectural, not local:

- One ~130-field `State` mixing process, session, gameplay, per-frame and debug lifetimes;
  leaving a world reset only half of it.
- "Subsystems" that reach into each other (a 14-pointer `Sim_Ctx`, `rawptr` console
  callbacks, a UI library importing the renderer, the world package driving the network).
- A server that is called authoritative but accepts client positions, damage and spawns.
- Mutable objects stored by value in maps, so edits land on copies and are lost.
- No memory strategy: the server never frees its temp allocator or unloads chunks.
- Broken frame model: double-counted timestep, CPU writing GPU buffers still in use,
  validation-layer messages silently discarded, whole-world re-upload on any edit.

The rules below exist to make those mistakes structurally hard to repeat.

## Ground rules

1. **Lifetimes are structure.** Three tiers, each owning its memory and torn down in one place:
   - `App` (process): settings, platform, GPU device, UI, audio device.
   - `Session` (one world, client or server side): arena-backed; leaving a world frees the arena.
   - `Frame`/`Tick`: scratch arena reset every frame/tick, on every thread that uses one.

   Lower tiers may point into higher ones, never the reverse.
2. **Handles, not pointers or map values, for game objects.** Generational `u32` handles into
   pools (entities, chunks, GPU resources, audio voices). Maps only map keys to handles.
   UUIDs exist only in save files.
3. **Allocating procedures take `allocator := context.allocator, loc := #caller_location`.**
   Enforced in review; no implicit `context.allocator` in long-lived data.
4. **No mutable globals.** Constant tables only; no lazy-initialised globals (they race once
   the server runs on its own thread).
5. **Packages depend downward only** (see layout). A UI or renderer package never imports game
   code; game code never imports platform or GPU code.
6. **Untrusted input is validated at the edge.** Every decoded enum is range-checked, every
   length capped; handlers receive validated types only.
7. **Nothing fails silently.** No silent truncation or dropped work; Vulkan validation on in
   debug and routed to the real logger; asserts on invariants.
8. **One source of truth per fact.** Physics, block rules and RNG live once in shared code;
   the server decides, the client predicts and reconciles.

## Layout

```
base/              handles + pools, arenas, math, rng, log, machine facts (depends on nothing)
common/            what the client and the server share (never imports client/ or server/)
  game/            the shared simulation: blocks, chunk storage, lighting, physics,
                   entities, rules, protocol (+ codec), the state model
  worldgen/        world generators
  netcode/         the UDP layer: connections, links, captures
  telemetry/       one event stream for everything that measures play
client/            the game: app, session, prediction, screens, main; and what only it uses:
  platform/        window, events, keep-awake (one file per OS: win32, x11, cocoa)
  gpu/             Vulkan: device, swapchain, frames in flight, buffers, images, bindless
  render/          passes: world (chunks), sky, entities, debug lines, UI
  ui/              immediate-mode UI -> vertices + texture ids (no GPU import)
  font/            TrueType parsing and rasterizing
  audio/           device (miniaudio) + mixer, voices, buses, streams, DSP, capture
  mesh/, sfx/      chunk meshing; generated sound effects
server/            the authoritative server: tick, handlers, streaming, saves; and
  collector/       the telemetry collector (M27; client and dedicated run it in-process)
dedicated/         the dedicated server's executable
tools/             build driver and dev tools (each its own executable)
assets/            fonts, shader sources, data (generated output goes to build/, not git)
docs/              the plan, milestone specs, history, debugging and design notes
```

Packages depend downward only: `base` <- `common/*` <- `server`, `client/*` <- `client`,
`dedicated`. Nothing built is committed: `build check` fails on a tracked executable.

## Core designs

### Main loop
`App` owns platform, GPU, UI, audio. A `Session` exists only inside a world. Each frame:
poll events → map to actions → run fixed ticks (accumulator added once, capped at a few ticks
per frame) → build the UI → each pass records its draws from the session and the UI → render. Tick rate is one constant in
`game/` (30 Hz), announced by the server in the handshake.

### World data
- Chunks 16³, `u16` block ids (room past 256 blocks). In memory a chunk is one block (all
  air, all stone: most chunks) or a flat array from a region reserved for the session's
  maximum, so memory has a hard ceiling; palette + runs on the wire (and on disk). Light
  stored separately.
- One chunk pool plus a coordinate → handle map; explicit chunk states
  (generating, ready, meshed, …) and a dirty-chunk event queue.
- Generation, lighting and meshing run as jobs on worker threads, on immutable padded
  snapshots (18³ for meshing), never on live data.
- Lighting is a pure function in `game/`: a chunk's sky and block light, computed whole from
  its 3x3x3 neighbourhood and the column heights (light travels at most 15 blocks, so that is
  all it depends on), inside the mesh job. No stored light, so no removal pass and nothing to
  go stale: an edit re-meshes the chunks within 15 blocks. (Changed from incremental add and
  removal passes in M4: same results, far fewer ways to be wrong.) The server sends column
  heights (`Column`), since the client cannot see above what it has loaded.
- Interest is a cylinder around each player's chunk, sent nearest first; the client drops
  chunks one past it and the server frees them two past it (hysteresis). Both sides size
  their storage from it once, at join.

### Authority and netcode
- Client sends tick-stamped input commands; the server simulates every player with the shared
  physics and sends snapshots; the client predicts its own player and reconciles.
- Block edits are requests: predicted locally, confirmed or rolled back by the server. Each
  names the input it follows, and the server applies it right after that input, so reach is
  judged from the same position however late it arrives.
- Transport is an interface. First implementation: in-process queues, with the server on its
  own thread (singleplayer keeps a separate client replica on purpose, so authority stays
  honest). Later: UDP (own reliability layer on `core:net`, or ENet behind the interface).
- Protocol has a version handshake, validated decoding, and palette + RLE chunk encoding.

### Renderer
- Retained resources: chunk meshes sub-allocated in one device-local buffer, uploaded per
  chunk through per-frame staging (no whole-world rebuild); textures and meshes by handle.
  Positions relative to the camera's chunk; reverse-Z infinite projection. Greedy meshing
  later (it must respect AO).
- Per frame: a scene buffer (camera, sky, clouds; read by address in the shaders) and each
  pass's own per-frame-in-flight buffers (entity boxes and particles, debug lines, UI
  vertices).
- Swapchain recreation touches only the swapchain and size-dependent images.

### UI
- Immediate mode, one hashed id system with an id stack.
- Hover, keyboard focus and active are separate states; clicks fire on release over the same
  widget.
- Layers (base, popup, modal, tooltip) decide input priority and draw order.
- Per-command scissor clipping; a layout cursor (rows/columns) instead of hand-placed rects.
- Input is a generic event stream (keys, text, pointer, and navigation: up, down, left, right,
  confirm, back, previous and next tab, from a pad or the keyboard: M42), not game actions.
- Output is vertices + texture ids; the renderer draws them.
- One look (the `Theme`), no player-chosen themes; a call site overrides it for the widgets it
  draws with a scoped `theme_scope` (colours, metrics, an `opacity` for everything inside: M40).

### Input
Platform events (keyboard, mouse, gamepads: M41) → action map (rebindable, per context: in the
world, in a menu) → per-tick input command. Analog values (sticks, triggers) are actions too.
Text input is a separate event stream for UI and console.

### Console and variables
Not a global registry (Quake's cvars, Call of Duty's dvars): every tunable value is a field
of a typed struct with one owner, described once in a table (name, type, range, default,
help) that the console, the tuning panel and save files all use. Code reads plain fields.

| Kind | Examples | Owner | Saved | Changed by |
|---|---|---|---|---|
| Client settings | sensitivity, FOV, UI scale, view distance, volume | App | settings file | the user; never sent |
| Game rules (`game.Rules`) | gravity, speeds, jump, reach, flying | server session | world save | the server only; sent in Welcome and as tick-stamped changes so prediction uses them |
| Debug switches | chunk borders, net trace, simulated latency | the side they affect | no | console, dev builds |

Singleplayer changes rules by sending a command message to its own server, never by writing
server memory. A value becomes a variable only when someone tunes it; design decisions
(tick rate, chunk size, protocol limits) stay constants. Cheat/dev commands only in dev
builds.

### From Quake 3: kept and dropped
Kept: authoritative server, client prediction of its own movement from tick-numbered input
commands, one movement code path for both sides, a local server for singleplayer, fixed
server tick, interpolated (not predicted) remote entities, console + config scripts.
Dropped: global string cvars (see above); everything-on-unreliable-snapshots (chunks and
edits need a reliable ordered stream; entities get snapshots); client-reported frame times
in commands (speed hacks; we tie inputs to server ticks and cap them); sending every entity
to everyone (interest management); QVM; lag-compensated hits until there is combat.

### Assets
Generated by code at startup, deterministic on every machine: block textures (procedural,
palette-quantized), sounds (synthesized; `build sfx` writes them out to listen to), the font
atlas (JetBrains Mono, rasterized by our own `font/` as glyphs are needed). Shaders are the
one build-time asset (SPIR-V, hot reloaded in dev builds).

### Tooling
Setting up a fresh machine is: install odinup, then run `build`. Nothing else.

- The build driver is an Odin program (`tools/build`); `build.sh` / `build.bat` only hand off
  to it.
- **Shader compiler, zero setup:** on first use the driver downloads the pinned official
  glslang release for the host OS (Khronos GitHub release, Windows x64 / Linux x86_64 /
  macOS universal) with the `curl` and `tar` every supported OS ships, verifies its SHA-256
  against hashes committed in the repo, and unpacks it into `build/tools/`. Everyone compiles
  with the same version; bumping it is a one-line change plus hashes.
- Override for unusual hosts (e.g. Linux arm64): `GLSLANG=/path/to/glslangValidator`.
- Shaders recompile only when their source changes; compile errors point at the GLSL file
  and line.
- CI uses exactly the same path, cached between runs.
- CI's Linux checks are split into two parallel jobs, "Test · Linux x64" (check, tests, determinism,
  the optimized tests) and "Game · Linux x64" (everything that runs the game or tools under
  xvfb), because the one Linux job alone set CI's length (17 min median, 38 worst). Every
  check still runs on every push. The tests run once, with `ODIN_TEST_RANDOM_SEED` set to the
  run number (a re-run repeats it). `./build.sh test` turns `ODIN_TEST_RANDOM_SEED` and
  `ODIN_TEST_THREADS` from the environment into `-define:` flags (Odin reads them only as
  defines), so `ODIN_TEST_RANDOM_SEED=n ./build.sh test` reproduces a CI failure. A budget a test asserts is read from `base.thread_cpu_us` (the thread's CPU time), not a wall clock: the suite runs tests on several threads, and a core taken from the measured one is not the work's cost (`test_save_200_characters` failed once on a 27 ms wall-clock capture of a few ms of work). On Windows it is the thread's cycle count over a rate measured against the wall clock: `GetThreadTimes` advances once per 15.6 ms scheduler tick, and read a 2 ms slice as 15625 us (CI run 40590622700). Ubuntu packages come from a cache of their `.deb` files
  (`.github/actions/apt`), because the package mirror twice took over 20 minutes.

### Saves
Region files (e.g. 32×32 chunk columns per file), palette + RLE per chunk, versioned, written
only by the server.

the milestone that changes it is named.

**Renames these imply:** M16 turns player files into characters
(`characters/<account>/<character>.json`). M17 renames the client's Worlds screen and
`world <name>` command to universes (the singleplayer list is a list of universes), moves
`world.cfg`'s universe-wide parts to `universe.cfg`, and gives each world its own

## Milestones

Each one is a vertical slice with an exit check; nothing moves on with failing checks.
Each open milestone has its spec in [milestones/](milestones/) (`M<n>.md`: why, the design decided, the steps in order, what is left out, the tests, the exit check); the table below links them. Specs of finished milestones are appended to [history.md](history.md).

**How a milestone is sized (from M22; revised after M25: see "Why the plan changed").** The work is done by an AI assistant on a plan
with a usage limit. Measured over M19-M21: nearly all of the usage was the assistant
re-reading its own conversation on every step (a session that ran for days, about half a
million tokens re-read per step), not the code it wrote. So:

- **One milestone, one fresh session.** "On to M<n>" starts a new conversation that reads
  its spec, `milestones/M<n>.md`, and the code it names. A spec therefore carries every
  decision: what to build, where, the numbers, what is left out, and the exit check. A
  milestone with an open design question is not ready; the question is settled first, in
  conversation.
- **Small enough to finish in one sitting:** one new system, or one system and the content
  that proves it. Bigger ideas are split (M20, done the old way, would be three).
- **Checked locally first,** with the tests the milestone touches (`odin test <package>
  -define:ODIN_TEST_NAMES=...`), then the whole suite once; pushed once at the end, and CI
  waited on once (a blocking `gh run watch`), not polled.
- **Windows-only code is kept together** (one milestone of it, checked on a Windows
  machine), because each mistake there costs a round trip through CI.
- **No `testing.expect_assert*` in tests.** Its panic capture killed the Windows test
  runner silently (CI run 40361408335: the `game` package printed no result, exit 1). A
  refusal a test must see is returned as a value (`game.hash_refusal`), not caught.
- **Done means:** the exit check passes, the table row says what was done, a line is
  added to the cost table below, committed and pushed; then the session ends. The next
  milestone is the next session. A finished milestone's spec is appended to history.md and
  its file removed.
- **The model:** a milestone whose spec is complete is implemented with a faster,
  cheaper model (Sonnet); planning sessions, design questions and debugging that has
  stalled use the strongest (Opus), whose usage counts several times as much.
- **A milestone that outgrows one usage window stops:** what works is committed, the rest
  becomes a milestone of its own. A long session is the costliest kind.
- **The week:** a planning session first (Opus, about an hour, no code) that settles one
  open question into a milestone spec and checks the order; then a milestone a session;
  at the end, a Windows check if anything needs one and a release tag. About a fifth of
  the budget is left free for what players report.
- **The mix:** at least one milestone a week is something only this game has (from the
  open questions: worlds, their peoples and histories). Something Minecraft already has is
  built only when one of those needs it, never for completeness.
- **No more infrastructure** (CI, benchmarks, tooling) unless something breaks or measurably
  slows the work.
- **Unattended sessions (decided 2026-10-26).** Milestones also run back to back with nobody
  watching, a fresh session each. Then:
  - **The order (revised after the first playtest, 2026-10-26; renumbered so the numbers are
    the order):** the playtest fixes (M40); controllers (M41 actions and pads, M42 menus);
    music (M43 pipeline, M44 director: the owner listens while playtesting); then the
    foundation in the order each builds on the last: the edit journal (M45), persistence v2
    before anything changes the save format (M46), registries and data packs (M47), block
    states and shapes (M48), voxel layers and the simulation framework (M49), entities v2
    with the spatial query service (M50), the script VM (M51), the sandbox over packs,
    journal and entities (M52), the declarative gameplay layer (M53), packs, signing, the
    bot harness and the dry run (M54), scale and security (M55); then the rest of audio:
    space on entities v2's queries and block shapes (M56), sound design (M57), the sound of
    the world (M58). The table's order is the order.
  - **Renumbered (2026-10-26):** M51→M40, M52→M41, M53→M42, M33→M43, M34→M44, M40→M45,
    M49→M46, M41→M47, M47→M48, M46→M49, M48→M50, M42→M51, M43→M52, M44→M53, M45→M54,
    M50→M55, M35→M56, M36→M57, M37→M58. history.md and older commits use the old numbers.
  - **Checks by hand do not block:** a milestone is done when its tests pass and CI is green
    on the three OSes. What only a person can check (listening, looking, a real Windows or
    macOS machine) is listed under "Check by hand" in the report and collected in one standing
    issue; what the person reports back becomes work of its own.
  - **Finish rather than split:** a session works on to the exit check (up to four hours).
    It splits a milestone at most once, and the remainder gets an exit check of its own,
    not "the rest". A milestone that is already a remainder (a letter after its number) is
    finished, not split again.
  - **Who pushes:** the session commits; the loop pushes, waits for CI on that commit and
    hands any failure to a fix session. A failure that passes on a re-run is a bug, written down.
  - **Models:** as above (Opus writes a missing spec, Sonnet builds).
  - **Specs written ahead (2026-10-26):** every open milestone's spec was written at once,
    before the code it builds on exists. A session first checks its spec against the code
    as it now is (names, files, what earlier milestones actually built) and corrects the
    spec where they differ, in the same commit, saying so in its report; it does not
    reopen a decision the spec records.

## The audio milestones (M32 to M32f done; music M43-M44 done; M56-M58b): an engine that stands next to FMOD and Wwise

Today's `audio/` is 403 lines: one mono one-shot per voice, 32 voices, linear resampling,
a soft clip, one master volume, no loops, no streaming, no buses, no filters, no way to
stop or change a sound once started (`play` returns only a bool), and `spatial_gain` as
the whole of 3D. The effects are synthesized at 16 kHz and 8 bits (`client/sfx`). There
is no music. The goal is what FMOD and Wwise give a game, built the way the rest of the
game is (our own, data-driven, tested offline, nothing beside the executable), plus what
only a voxel world can do: sound that hears the blocks.

### Decisions (locked; change them only by editing this list)

### What the engine has (the feature list the milestones build)

- **Buses.** A tree: Master <- Music, Ambience, Effects (<- World, Player, UI). Per bus
  gain, mute, solo (debug), low-pass, send to the reverb, and **ducking**: a bus lowers
  others while it plays (side-chain), with attack and release. Snapshots: named sets of bus
  settings crossfaded in (Underwater, Paused menu, Death, Loading) the way FMOD does.
- **Voices.** 128 virtual voices, 64 real. A voice is a generational handle (ground rule 2)
  the game keeps to stop it, move it, change its parameters or fade it. Priority and
  audibility decide who is kept; a virtual voice keeps its place in time and resumes when
  it becomes audible again. Sample-accurate start times, loops with a loop point and a
  crossfade, fade in and out, per-voice low-pass, gains smoothed per block (no zipper
  noise), pitch with cubic resampling.
- **Sources.** Memory sounds (effects, mono or stereo, any rate) and **streams** (music,
  long ambience): a decoder thread fills ring buffers from the Ogg in memory; an underrun
  is counted, never silent.
- **DSP.** Biquad filters, delay lines, a feedback-delay-network reverb (8 lines, damping,
  early reflections, RT60 set live), a compressor and the limiter, all on buses or sends.
- **Events, not files.** The game says `event(.Block_Break, {material = .Stone})`; a
  table of event definitions says what plays: variations with no-repeat, pitch and gain
  ranges, the bus, priority, attenuation curve, cooldown and instance limit, and
  parameters (speed, material, intensity, depth) driving gain, pitch and filter by curves
  (FMOD's parameters). Dev builds reload the table while the game runs.
- **Spatial.** A listener with velocity and head; emitters as voices with positions;
  attenuation curves per class, Doppler, air absorption (distance dulls high
  frequencies); a head model for stereo (inter-aural delay, head shadow, an elevation
  cue), no third-party HRTF data.
- **Acoustics from the blocks** (what only this game can do): occlusion from a voxel ray
  from emitter to listener through the client's chunks (each block's material absorbs
  its own amount: wool a lot, glass little), an open path around corners found among a few
  extra rays; the reverb from rays cast around the listener (room size, how much of the
  sky is open, what the walls are), smoothed; underwater and in lava muffled by snapshots.
- **Music.** A director (states, silences, crossfades, stingers, tracks chosen by place,
  time and world) over the stream voices, plus music made of layers for later use.
- **Tools (M32, M32b).** Capture files and `build audiodump`, baselines and cost scenarios in CI, the freeze-and-solo inspector (see M32b); `build audio` renders a scenario to a WAV to listen to; `build music`
  renders scores; an in-game audio overlay (voices with their buses and priorities, bus
  meters and LUFS, the reverb's room, occlusion rays drawn as debug lines); a benchmark
  scenario for the mixer's cost.

## The foundation arc (M38-M39, M45-M47a, M47b, M47d, M47e, M47i and M48 done; M48b-M55b): an engine agents can write games for

Direction (decided): Voxiverse's product is **gameplay written for each player by AI
agents, as they play** (a world with its rules, content and scripts, adapted to what the
player does), sold by credits. The agent service is a separate product built against this
engine; the engine's job is to make that safe, cheap and good. So the foundations come
first, and game content (survival, crafting, combat, villages, machines, ...) comes after
as data and scripts on top of them: the "After M29" list below is content, not
foundation, and waits for M55.

### First principles

The engine is a replicated, deterministic simulation of a voxel field and its entities,
driven by data and scripts, in which every change has a cause and a history. It protects
five freedoms: **rules** (any mechanic is data and script, not an engine change), **world**
(scale, physics and generation are properties of a world), **content** (added without
code), **society** (one server process to many players, trust and an economy built in)
and **truth** (every change journaled: replay, rollback, audit, test).

### Threat model (what the script and agent surface must survive)

Untrusted: (1) generated scripts, buggy or hostile (a jailbroken or prompt-injected
agent); (2) player input, which reaches the agent as chat and behaviour ("give me
infinite diamonds" is an attack); (3) generated text and names (offensive or illegal
content); (4) the pack's transport (a forged pack). Defences, in layers, each built by
a milestone below:

- **A world is the unit of isolation.** A pack's content belongs to its universe (fixed while
  it runs) and its behaviour is enabled per world (M17's address); its scripts can touch only
  the worlds it is enabled in. The worst a script can do is ruin the worlds it is enabled in,
  which are reverted from the journal (M45).
- **Capabilities, not permissions.** A script has no ambient authority: its pack declares a
  manifest and the server grants it per world (edit blocks in a region, spawn N
  entities, give items from a budgeted faucet, show UI, send chat, read these events).
  Nothing else exists to call (M52).
- **Hard metering.** Per script, per tick and per second: instructions, memory, block
  edits, spawns, messages, events. Over budget suspends that script and logs it; the tick
  never stalls (M51, M52).
- **Economy containment.** Script-made items go through M31's ledger under their own reason
  with per-world caps and the script as their cause (M52); tagging the items themselves with
  their origin, and rules on where they may travel, wait for the economy's content wave (it
  changes stacks, merging and the inventory protocol).
- **Validation before anything runs:** static checks (capabilities used = declared,
  bounded loops, schemas), a headless dry run with bots measuring crashes, budgets, ledger
  balance and softlocks, moderation of generated text and of the images and sounds in packs,
  then a staged rollout (M54).
- **Signed packs.** The agent runs off-server; a server accepts only packs signed by
  a key it trusts (M54).
- **Journal and replay.** Every script effect carries its cause (M45); a bad script's
  changes are undone, and a bug replays deterministically (M38).
- **Telemetry is the agent's eyes** (M26-M27): it reads aggregate behaviour, not raw chat.
  The consent question (M27) is off by default (issue #2): `telemetry.ask` (0) turns it back
  on, all its code is kept, and while it is off nothing is sent (unanswered = no). It stays
  off until it is redesigned.
- **Fuzzing from the first VM:** the VM, the packs' parsers and the protocol are fuzzed in
  CI from M51 on, not at the end.

### Decisions (locked)

| Area | Decision |
|---|---|
| Script language | Our own Lua-like language and VM in Odin (parser, bytecode compiler, register VM, incremental GC), close enough to Lua 5.4 that models write it well (tables, closures, metatables-lite, no `goto`, integer and float numbers, optional type annotations as in Luau). No C in the sandbox: memory-safe by construction, deterministic (no ambient clock, random, hash-order or I/O), metering built in, state serializable. `vendor:lua` is not used (its vendored builds lack macOS, and its C surface is what we avoid) |
| Live adaptation | Left open until play-testing shows what agents can do. Kept possible, not built: script state is serializable (snapshot and restore) and packs are versioned and hot-swappable at a tick boundary, so a revision can arrive between visits or, later, during one |
| Scale | Minecraft's architecture: one server process per universe, worlds on their own threads; scaling beyond is the owner's problem later. No distributed universe now (the handoff protocol is not designed here) |
| Authoring surface | Mostly declarative data interpreted by the engine (quests, objectives, spawners, triggers, dialogue, loot: M53); scripts only for logic data cannot say. The engine API is small, typed, versioned, with machine-readable schemas and errors written for a model to act on |
| Content vs foundation | No gameplay decisions (survival, crafting, combat, economy numbers) are made in the foundation arc (M38-M39, M45-M55b). Anything that needs one waits for the content waves. No new gameplay mechanics, and no polish of existing ones (health and death, M28, stay as they are), before the foundation arc is done: gameplay is rewritten on the script VM and the declarative layer, so polishing it now is done twice Fixes from playtests to menus, comfort and defaults (M40) are not gameplay and are fine. |
| Hosting, payments | Out of the engine's scope (the credit ledger, billing, age gates and legal review belong to the service). The engine provides pack signing, metering and the ledger hooks |
| Numbers (M38) | Three tiers, written in `docs/determinism.md`: **state** (server simulation, prediction, worldgen, light, rules, RNG) is bit-identical on every OS and optimization level; **replayable** (the audio mixer and its capture, client visuals) is bit-identical on one OS and optimization level, which is why the audio baselines keep a checksum per OS; **free** (rendering, UI, timing). State uses `base.sin`, `base.cos`, `base.exp` (ours), never `core:math`'s sin, cos, tan, pow, exp or fmuladd (LLVM intrinsics: each OS's libm, folded differently by `-o:speed`), and `base.Rng` (ours, xoshiro256**), never `core:math/rand` (ChaCha8, 1 KiB of state, its stream the toolchain's to change) |
| What determinism means (M38) | The simulation is a function of what reaches it at each tick boundary. A live server is not lockstep: inputs and chunk jobs arrive when they arrive. A stepped server (no thread, inline chunk jobs, inputs given per tick) is the reproducible form, used by tests and the cross-OS job now, and by replay and the journal later (M45). No map iteration order and no thread completion order reaches state or the wire |
| State model (M39) | Server-to-client state is **records** of typed **state kinds** (a value type, a key, a lane) and one-off **events**, encoded by one codec derived by reflection from the value types (field tags give string limits and the `acked` field), with a schema hash checked on joining. Two lanes: reliable records are deltas against the last value sent; snapshot records (motion) are deltas against the client's last acknowledged snapshot (a ring of 32). Values travel exactly (quantization waits for M50). The handshake, answers to one client's requests and the bulk chunk streams stay messages; client-to-server messages are not state |
| Authorship (owner's decision, 2026-10-27) | One agent authors a universe's shared experience. New worlds behind gates are purely procedural (an address's parameters, and later worldgen graphs), not authored per world or per player |
| Packs per universe (2026-10-27) | A universe's packs are fixed while it runs. Its registry never grows at runtime, and packs aren't sent in the middle of a session. Joining sends every pack in the universe, cached by hash, whether or not the player visits the worlds that use it. Content is per universe, as M47 already says; a pack's *behaviour* is enabled per world |
| Pack sides (2026-10-27) | A pack has three folders. `assets/` is client-only: textures, sounds, music, later UI text. `data/` is for both sides: block and item definitions, tags, recipes, data rules. `server/` is server-only: scripts, quests, loot, worldgen graphs. The server sends `assets/` and `data/` only. The content check covers what both sides build from `data/`. A custom item's definition lives in `data/` (the client must show it); its scripted behaviour may live in `server/`. The base pack's files are laid out this way already |
| Prediction (2026-10-27) | Behaviour written as data rules is deterministic, runs on both sides, and is predicted. Prefer it. Scripts are server-only and can't be predicted, so use them only where a round trip's delay is acceptable (custom quests, item behaviour, AI, events) |
| Worldgen as data (2026-10-27) | Worldgen in packs is graphs of native building blocks (density functions, noise, splines, carvers, placement). A pack only wires them together. Scripts never run per voxel |
| Scripts stay in the VM (2026-10-27) | Scripts are never transpiled or compiled to native code. When a script pattern is hot, the engine gains a reviewed native building block or function for it instead |
| Accounts and remotes (2026-10-27) | Identity and ownership (skins, owned things) come from a central source of truth: an auth service reached through *remotes* in `settings.cfg`. The default remote is `voxiverse.net`, with services at `auth.voxiverse.net` and `api.voxiverse.net` (the remote format allows other hosts). The website and service are closed source; the game sees only the API. As with Minecraft: singleplayer and LAN work offline with a local key. A server is either **online** (it requires a token signed by its remote's auth service) or **offline** (local keys, as today). Online becomes the default once it's built; until then servers are offline. The keypair of the glossary's Account stays as a device key an account vouches for when online. Built in "Auth client and online servers" (the next tier) |
| Pack media moderation (2026-10-27) | Images and sounds in packs go through a moderation hook before players see them, like generated text. M54 owns the hook; the service does the moderation |
| Before 1.0, no compatibility (2026-10-27) | Saves and the protocol carry no migrations and no compatibility. A new build may require a fresh world, and older clients must update. Specs drop their migration and compatibility work (a world of an older format is refused with a message). Existing migration code can stay until it is in the way |
| macOS port, one pass (2026-10-27, #35) | The port is M47d (window, input, MoltenVK, renderer) and M47e (gamepads, audio, keep-awake, icon, `.app`), first in the order, each written once. Their exit check is `build check`, build and link on the macOS CI runner with the existing unit tests, and the `.app` as a CI artifact. No macOS-specific tests, offscreen game checks, screenshots or benchmarks; what only hardware shows is under "Check by hand" for occasional testers, and what they find becomes an issue then, with no sessions spent chasing behaviour nobody here can see. Unchanged: the loop's checks before a push, the weakened-test guard, CI on every push |
| Platforms (2026-10-27) | Follow [platforms.md](platforms.md): Tier 1 (blocks a release: CI builds it, runs the full tests and the game, packages ship) is Windows x86_64, Linux x86_64 and macOS arm64 (a target: it builds and packages in CI and is not tested on hardware by the project; port: M47d-M47e); Tier 2 (CI builds and runs the unit tests) is Linux arm64 and macOS x86_64 (its CI jobs are "Tier 2 CI" in the next tier); Tier 3 is best effort. The Tier 1 list is one constant in `tools/build` (`TIER1_TARGETS`), checked against that document by a test |

## Why the plan changed (after M25)

- **Sizing was wrong by a factor of ten.** Milestones planned as a week each took one to two
  hours (M22 to M25: 60 to 160 assistant steps each). A milestone section may now be several
  times bigger, and a session may take two or three that belong together.
- **What was being built was the content that sits on top of foundations that did not exist
  yet**: sheep genetics, crops and a chest came before any way to know how people play, or to
  reach the developer's eyes without copying files. Content is cheap now, and cheap to
  re-order; measuring is the thing that makes every later decision better, and it is the part
  that cannot be added later for the time already played.
- **Stats were planned as counters for display; an MMO RPG needs them as a stream** (events
  that counters, logs, progression and economy analysis all read), plus the character state
  progression changes (attributes, health, xp). Hence M26 and M28 share one design.
- **Deferred, in the order they will come back**, below: blocks that hold things (chests,
  signs: infrastructure for teleporter blocks and shops), the Windows pass (needs a Windows
  machine), sky and time. Then, as before, the list after M30 (minimap, throwables, ...) and
  nothing from it before the foundation above is done.

## Deferred until a Windows machine is at hand: Windows behaviour (was M27)

Everything that needs a Windows machine, together, checked there once at the end.

- **The icon:** done in M40 (a clean black cube with a JetBrains Mono question mark); on the
  Windows machine, only seen in the taskbar and Explorer at each size.
- **Landing dust:** falling three blocks or more and landing kicks up puffs of the block
  landed on, more for a harder landing; for every player in view (seen from their
  snapshots). Visual only until there is fall damage.
- **Native Windows behaviour** (what SDL3 and GLFW do that we do not yet; per-monitor DPI,
  raw mouse input, cursor clipping and UTF-16 pairs are done):
  - `WM_DPICHANGED`: take the suggested rectangle when moved to a monitor of another scale.
  - `WM_SYSCOMMAND`/`SC_KEYMENU`: Alt and F10 must not open the window menu (which
    freezes the loop until a key).
  - Moving and resizing: Windows runs a modal loop while the frame is dragged and the
    game stops; keep it rendering through it (a timer during the move, as SDL3 does) or
    run the game loop off the window's thread.
  - A dark title bar (`DwmSetWindowAttribute`, `DWMWA_USE_IMMERSIVE_DARK_MODE`).
  - Precise frame pacing: a high-resolution waitable timer
    (`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`) for the menu frame cap, not `Sleep`'s 15 ms.
  - Not slowed in the background: power throttling off for the process
    (`SetProcessInformation`, `ProcessPowerThrottling`); the render thread registered
    with MMCSS as "Games".
  - An AppUserModelID (the taskbar groups the game's windows under its icon).
  - No system error dialogs (`SetErrorMode`); started from a console, logs to it
    (`AttachConsole(ATTACH_PARENT_PROCESS)`).
  - Each checked on a Windows machine (some only show there).
- **Exit check:** the Windows list ticked off on a Windows machine; the icon at every size
  in the taskbar and Explorer; landing dust seen for every player in view; M41's XInput pads
plugged in and played.

## Deferred: sky and time (was M28)

Cheap, deterministic astronomy, so a world implies a sky worth observing (one could keep a
lunar calendar by watching): a few trigonometric terms per frame from the world clock.

- **Each world's astronomy** (from its address; the home world Earth-like): day length,
  days in a year, axial tilt, one or more moons with their periods, and a star catalogue.
- **The sun's path:** its height and bearing from the time of day, the day of the year
  (declination from the tilt) and the latitude (from z): longer days in summer, a lower
  sun in winter. Light follows the sun's height as today.
- **Moons:** each at its own period; the phase from the sun and moon's angle, drawn as a
  pixel disc with its lit part; rising and setting at their own times.
- **Stars:** fixed per world (its seed), on a sphere that turns once per sidereal day
  (slightly shorter than a solar day), so the night sky shifts through the year.
- **The calendar:** `calendar` reads the day, month (by the first moon), year and moon
  phases; the server's clock is the only input, so every client sees the same sky.
- **Not here:** seasons changing the land (snow cover, leaves) would mean block updates
  across the world: later, if ever.
- **Exit check:** golden values for the sun, moons and calendar at chosen moments on every
  platform; a moon's phase repeats on its period; star positions drift by the sidereal
  difference night to night; sky screenshots at a few dates.
### After M29 (not planned in detail yet), in this order

Content, not foundation: all of this waits for the foundation arc (M38-M39, M45-M55b) and is then
built as data and scripts on it.

Each becomes a milestone spec, sized as above, before it starts.

- **A minimap:** the map in a corner as Xaero's minimap draws it (the tops of the columns
  around, shaded by height, players and animals as marks), but drawn as part of the game:
  its own frame and pixels, no settings wall; a full map on a key. From the columns the
  client already has.
- **Throwables:** dynamite (thrown, a fuse, the rocket's explosion) and a glowing stone
  that lights where it lands (a light block that crumbles after a while); then a bow.
- **Teleporter blocks:** placed by a player, named, they are the only places the full map
  can send one to (fast travel from block to block, not from anywhere). Built on M26's
  blocks that hold things and the minimap.
- **Villages and traders:** villages as M12 structures; villagers (a big crooked nose,
  beady eyes) who wander their village; using one (M23) opens a trade overlay of offers,
  the server checking and swapping the items; gold as the currency (an item, found as
  ore). No professions, no sleeping.
- **Flying animals:** a flock of birds steering by the three boids rules (separation,
  alignment, cohesion) with the terrain as an obstacle; server-simulated, cheap per bird.
- **Sound, again:** done as M57 (the sound-design pipeline).
- **Tools:** a pickaxe for soil and stone, an axe for wood (whether hands can break and
  whether breaking takes time is decided then).
- **Itemization (Diablo II style, not enchantments):** items that can be unique get an
  instance of their own (rarity, affixes and suffixes rolled from a seed, flavour text),
  which means stacks carry data (the wire, the player files) and such items stack one. The
  data is there from the first drop but shown only once the character has learned of it
  (a knowledge flag a later mechanic sets). Needs tools and equipment worth rolling;
  the stack data change goes in with tools.
- A dungeon's boss: a boss bar across the top, and its loot thrown out in a burst when it
  dies.
- Lava as a second liquid; greedy meshing and low-detail far terrain for long view
  distances; macOS: M47d-M47e.

### Open questions (to settle in conversation before they become milestones)

- **Music:** settled in the audio milestones (scores and MIDI rendered offline by our SF2 renderer to
  Ogg). Still open: what each world's music sounds like beyond the tags (M58 starts it).
- **Worlds that change while you are away:** what happens in a world over the time a
  player spends elsewhere (wars, growth, ruin), how it is computed cheaply when the world
  is loaded again, and whether worlds have histories generated from their seed.
- **Peoples between worlds:** factions and a player's standing with each, per world or
  across worlds; whether worlds near each other by address can be neighbours a people
  spans ("the next world over").
- **A lesson per world:** each world with its own puzzle to solve.
- **Kinds of world:** more generators, and what they are called (scientific names, or
  invented ones).
- **Moving faster:** dash, double jump, a grappling hook: from items, or from something a
  character learns.
- **Items and slots:** how many slots, how that changes as a character goes on, and how
  items stay simple to use as there are more of them.
- **Learning the game in the game:** everything a player needs to know found in the world
  itself (no tutorial, no wiki).
- **Machines:** something to build working machines from (as Minecraft's redstone with its
  slime-block flying machines), but fewer, denser parts.
- **The download site:** voxiverse.net with one Download button that picks the visitor's
  system (M21 has the way there), and the project going private with it.

### From notes, changed or not taken

- Gates are dialed, not built (no portal frames to light), and they are found, one by
  every spawn: discovery is reading and sharing addresses, which needs the address to
  mean something, hence an address decides a world's kind.
- Square slots needed icons more than a new shape: names do not fit squares.
- Landing dust before fall damage is decoration; kept small.
- Real stars and calendars are kept, but computed, not simulated: no orbits integrated,
  no seasons in the blocks.
- Villagers and itemized loot wait for the systems they stand on (attributes, tools); a
  trader without things worth trading would be a stub.
